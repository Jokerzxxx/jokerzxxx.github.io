CAN 协议阅读与信号解析笔记

这篇笔记用于快速阅读 CAN 通信矩阵，并把一条信号从原始报文转换成业务可以使用的物理值。

阅读协议时可以沿着下面这条主线进行：

找到报文 → 确认发送方式 → 定位信号位 → 解析原始值 → 换算物理值 → 判断有效性 → 交给业务使用

实际项目中，不同主机厂对起始位、组合发送类型和特殊值的定义可能不同，最终应以当前项目的协议说明为准。

一、阅读协议总览

CAN 通信矩阵通常包含两个层级：

  • 报文（Message）：定义谁在什么时间发送一组数据。
  • 信号（Signal）：定义这组数据中每一段二进制位的含义。

一个报文可以包含多个信号。排查问题时，应先确认报文是否正确收发，再检查具体信号是否正确解析。

二、报文属性

协议字段 中文含义 说明
Msg Name 报文名称 用于标识报文业务含义
Msg Type 报文类型 常见类型有 Normal、NM、Diag
Msg ID 报文标识符 CAN 总线上用于区分报文的 ID
Msg Send Type 报文发送类型 常见类型有 Cycle、Event、IfActive、CE、CA
Msg Cycle Time (ms) 报文周期 周期报文的发送间隔
Msg Length (Byte) 报文长度 报文数据区长度，经典 CAN 通常不超过 8 Byte
Msg Cycle Time Fast (ms) 快速发送周期 事件触发后进入快速发送阶段时使用
Msg Nr. Of Repetition 快速发送次数 快速周期连续发送的次数
Msg Delay Time (ms) 报文延时 相同 ID 报文两次发送之间的最小间隔

常见报文类型

类型 含义
Normal 常规应用报文
NM 网络管理报文
Diag 诊断报文

常见发送方式

发送方式 典型行为
Cycle 按固定周期持续发送
Event 数据变化或事件发生时发送
IfActive 功能激活期间发送

组合发送方式的触发条件、快速周期和重复次数，应结合当前协议中的补充说明确认。

数值换算

状态与特殊值

Inactive Value (Hex) 非使能值 功能未激活时使用，常见于 IfActive 或组合发送方式

四、字节序与数值换算

字节序决定多字节信号在报文中的排列顺序。对于单字节信号，Intel 和 Motorola 不会造成字节交换；差异主要出现在信号跨越两个或更多字节时。

常见名称对照

协议写法 常见别名 第一个字节保存
Intel Little Endian、小端 低有效字节（LSB）
Motorola Big Endian、大端、Network Order 高有效字节（MSB）

Intel（Little Endian）

Intel 通常表示小端字节序：低有效字节放在低地址位置。

Intel 格式比较适合直接映射到常见小端 CPU 的整数存储，但解析 CAN 信号时仍应根据协议提取位段，不能直接假设整段内存布局完全一致。

Motorola（Big Endian）

Motorola 通常表示大端字节序：高有效字节放在低地址位置。

同样以 0x1234 为例：

字节序和位编号不是同一件事

协议或工具中还可能出现下面两种位编号方式：

位编号方式 含义
LSB0 每个字节的最低有效位编号为 Bit 0
MSB0 每个字节的最高有效位编号为 Bit 0

Intel/Motorola 描述多字节数据的排列方式，LSB0/MSB0 描述一个字节中的 Bit 编号方式。两者不能互相替代。

解析跨字节信号时不能只交换字节，还要同时确认：

  1. 协议中的 Bit 0 从哪一侧开始编号。
  2. Start Bit 表示最高有效位还是最低有效位。
  3. 信号跨字节后的位增长方向。
  4. 当前解析库采用 DBC 定义还是自定义矩阵定义。

同样写着“Motorola + Start Bit”，不同工具导出的矩阵可能采用不同编号方式。最好使用一条已知报文进行反向验证。

混合字节序

少数历史协议可能使用 Middle Endian、Mixed Endian 或自定义字节交换，例如先交换 16 位字，再按大端排列。它们不是 CAN 通信矩阵中的通用标准，不能仅凭名称推断。

遇到混合字节序时，笔记中应直接记录：

  • 报文中的实际字节序列。
  • 交换前后的完整示例值。
  • 每一步移位与组合公式。
  • 一条经过实车或日志验证的原始报文。

例如协议明确规定字节顺序为 Data[1] Data[0] Data[3] Data[2] 时，应按该顺序显式重组，不能套用普通 Intel 或 Motorola 解析方法。

五、接收解析流程

  1. 根据 Msg ID 找到报文。
  2. 检查报文长度是否符合协议。
  3. 根据字节序、起始位和位长度提取 Raw。
  4. 如果是有符号类型，先完成符号扩展。
  5. 判断 Raw 是否为 Initial、Invalid 或 Inactive。
  6. 根据 Resolution 和 Offset 计算物理值。
  7. 检查物理值是否在有效范围内。
  8. 将有效数据交给业务层或界面。

特殊值应在物理值换算前判断，否则无效编码可能被换算成看似正常的数值。

枚举信号

并不是所有信号都需要使用精度和偏移量换算。开关、档位和状态类信号通常直接查询 Signal Value Description。

例如：

Raw 状态
0x0 关闭
0x1 开启
0x2 预留
0x3 无效

上表只用于说明枚举信号的阅读方式，实际编码必须以具体协议为准。

六、车机外发、反馈接收与方式选择

前面的 Cycle、Event、IfActive、CE 和 CA 描述的是一条 CAN 报文在总线上的调度方式。实际开发中还需要确定两个不同的问题：

  1. 用户操作后，车机应该发送目标值、增减动作，还是完整控制帧。
  2. 界面应该等待真实反馈，还是先显示目标状态再等待确认。

这两个问题不能混为一谈。例如“设置温度为 24 ℃”属于绝对值控制，但承载它的报文仍然可能是周期报文、事件报文或周期加事件组合报文。

6.1 推荐的软件链路

为了让 UI、车型差异和实际 CAN 报文解耦，推荐把收发链路分层：

UI 层负责表达用户意图，不直接拼接 CAN 字节；车型控制层根据当前车型选择 CAN ID、信号定义、发送次数、有效位、计数器和校验。这样在高低配协议不同时，可以替换车型控制实现，而不用重写界面逻辑。

6.2 车机外发控制方式

控制方式 车机发送的内容 适用条件 主要风险
绝对值设置 明确的目标值，如 24 ℃、5 档、内循环 协议提供目标值信号 编码、范围或单位换算错误
增减/按键模拟 加、减、按下、释放等动作 协议只定义动作命令 丢帧后车机与 ECU 状态可能不同步
状态翻转 根据当前反馈发送相反状态 协议只有 Toggle，或明确要求反向控制 初始反馈无效时容易发反
完整控制帧 包含多个控制字段的整帧数据 协议要求整帧、周期、有效位、Counter 或 Checksum 覆盖其他字段、计数器或校验错误
请求—应答 发送请求，等待执行结果或实际状态 协议提供响应、确认或失败状态 超时、重复请求和迟到响应处理不当

绝对值设置

协议允许时优先发送确定目标，而不是发送 Toggle：

绝对值命令通常具有幂等性。相同目标重复发送，最终状态仍然一致，比较适合开关、温度、风量和模式控制。

增减或按键模拟

只有协议明确提供 Increase、Decrease、Press、Release 等动作时才使用。车机发送的是操作，不是最终结果，因此不能仅通过发送次数推断 ECU 的实际状态。

对于按下/释放协议，还应确认：

  • 按下与释放是否必须成对发送。
  • 长按是否需要周期保持。
  • 两次操作之间是否有最小间隔。
  • 丢失释放帧后 ECU 是否会自动超时。

状态翻转

只有同时满足下面条件时，才能根据当前值发送相反状态：

  1. 当前反馈已经收到，并且不属于 Initial、Invalid 或超时状态。
  2. 没有上一条同类命令正在等待确认。
  3. 协议没有提供更可靠的绝对值控制。

页面刚打开、反馈尚未初始化时，不应拿代码默认值执行 Toggle，否则可能把“开启”错误地发送成“关闭”。

完整控制帧

出现下面任意情况时，应按完整报文处理，不能只修改并发送一个孤立字节：

  • 报文需要固定周期发送。
  • 报文包含 Alive Counter。
  • 报文包含 Checksum、CRC 或校验和。
  • 控制信号旁边还有有效位、控制源或授权位。
  • 一帧同时承载温度、风量、模式和循环等多个控制量。
  • 协议规定事件发生后进入快速周期并重复发送多次。

实现时应缓存同一报文中其他字段的最新合法值，只修改目标位，然后更新计数器、重新计算校验并按协议发送。高配自动空调比低配手动空调更容易采用这种方式。

6.3 接收与状态更新方式

CAN 接收端常见有下面几种数据获取方式：

接收方式 行为 适用场景
周期/事件推送 ECU 主动周期发送，或状态变化时发送 大多数实时状态
请求后响应 车机查询，ECU返回当前状态或执行结果 低频配置、诊断和确认类状态
首次查询＋持续推送 页面或节点启动时查询一次，后续监听周期/事件报文 需要可靠初始状态的设置页面
超时失效 一段时间未收到报文后，把状态标记为无效 防止 UI 长期显示陈旧数据

6.4 UI 根据反馈显示的方式

UI 策略 点击后的显示行为 适用条件
纯反馈显示 发送后不改变最终状态，收到 ECU 反馈才更新 实际设备状态、反馈较快、不能接受误显示
乐观显示＋反馈纠正 立即显示目标并标记等待，收到反馈后确认或校正 反馈可靠但存在延迟，交互要求较快
发送值回显 根据刚发送的目标值更新 UI 只能作为临时目标显示，不能代表执行成功
瞬时按压显示 只显示按钮按下动画，不保持最终状态 没有状态反馈，只能模拟物理按键
组合反馈显示 多个反馈字段统一计算一个 UI 状态 AUTO、吹风组合、同步和优先级状态

纯反馈显示

空调开关、AC、AUTO、除霜等真实设备状态优先采用这种方式。优点是不会出现“界面显示开启但车辆实际没有开启”，缺点是反馈较慢时用户可能觉得按钮没有响应。可以立即显示短暂的按压动画，但永久选中状态仍由反馈决定。

乐观显示加反馈纠正

超时时间应根据报文周期决定，通常至少覆盖 3～5 个反馈周期。还需要给每次操作增加序号或 Pending 标记，避免上一条命令的迟到反馈覆盖用户刚进行的新操作。

发送值回显

发送值回显只能证明车机完成了软件调用，不能证明报文已经上总线，更不能证明 ECU 已经执行。没有真实反馈时，可以显示“指令已发送”或目标值的临时样式，但不应把它标记为实际状态。

6.5 方式选择流程

选择方式前应按顺序确认：

  1. 在通信矩阵中确认发送节点、接收节点、CAN ID 和总线通道。
  2. 判断协议给的是目标值信号、动作信号还是 Toggle。
  3. 检查报文发送类型、周期、快速周期和重复次数。
  4. 检查有效位、控制源、Counter、Checksum 和前置条件。
  5. 找到真实状态反馈、响应结果和超时判定依据。
  6. 使用原车操作日志或实车报文验证，不根据 UI 名称猜测协议含义。

6.6 高低配空调问题的快速判断

当低配控制正常、高配没有反应时，可以对相同操作抓取车机调用日志、发送帧和反馈帧：

观察结果 优先排查方向
高配没有产生外发 CAN 帧 车型配置、监听注册、发送路由或控制接口
高低配发送完全相同，但只有低配执行 高配 CAN ID、总线、有效位、完整帧、Counter、Checksum 或控制前提
高配车辆已经执行，但 UI 没变化 高配反馈 ID、信号位、有效值解析或 Observer 绑定
UI立即变化，但车辆没有执行 把发送值回显误当成真实反馈
只有部分按钮无效 对应信号的枚举、偏移、模式组合或前置条件
页面刚进入第一次点击经常发反 默认值被当成真实反馈执行 Toggle

排查时应分别证明四件事：用户操作已经进入控制接口、控制接口生成了正确报文、报文确实出现在目标总线上、ECU 返回了真实状态。只看到 UI 变化或发送函数日志，不能证明空调已经执行。

八、排查与记录模板

排查清单

当信号值或界面状态不正确时，按下面的顺序检查：

  • 报文 ID 是否正确，标准帧和扩展帧是否匹配。
  • 报文长度是否符合协议。
  • 接收周期是否正常，是否已经超时。
  • Intel/Motorola 字节序是否正确。
  • Start Byte、Start Bit 和 Bit Length 是否正确。
  • Signed/Unsigned 类型是否正确。
  • Resolution 和 Offset 是否正确。
  • Initial、Invalid、Inactive 是否被单独处理。
  • 枚举值是否完整映射。
  • 相同报文中的其他信号是否被意外覆盖。
  • UI 是否订阅并使用了正确的业务字段。
