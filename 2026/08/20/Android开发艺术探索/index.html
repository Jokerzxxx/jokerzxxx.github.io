第1章 Activity的生命周期和启动模式

1.1 Activity的生命周期全面分析

1.1.1 典型情况下的生命周期

Activity在正常情况下的生命周期回调顺序：

  1. onCreate：Activity正在创建，做初始化工作（加载布局、绑定数据）
  2. onStart：Activity正在启动，已可见但不在前台，无法交互
  3. onResume：Activity已可见且在前台，可交互
  4. onPause：Activity正在停止，应存储数据、停止动画，但不能做耗时操作
  5. onStop：Activity即将停止，可做稍微重量级的回收工作
  6. onDestroy：Activity即将销毁，做最终资源释放
  7. onRestart：Activity从停止状态重新启动，后接onStart

关键结论：onPause和onStop中都不能执行耗时操作。onPause中尤其不能做耗时操作，因为新Activity的onResume必须等旧Activity的onPause执行完才会调用。

1.1.2 异常情况下的生命周期

资源相关的系统配置发生改变（如屏幕旋转）或系统内存不足时，Activity可能被异常销毁重建。

异常销毁的数据保存与恢复：

  • onSaveInstanceState：在onStop之前调用（不一定在onPause之前还是之后），用于保存临时数据
  • onRestoreInstanceState：在onStart之后调用，用于恢复数据
  • 系统默认会为每个View保存状态（如EditText的输入内容、ListView的滚动位置），前提是View需要指定id

避免重建：通过AndroidManifest中配置android:configChanges="orientation|screenSize"，可在配置变化时不重建Activity，转而回调onConfigurationChanged。

1.2 Activity的启动模式

1.2.1 Activity的LaunchMode

启动模式 行为 典型应用
standard 每次启动都创建新实例，谁启动它就运行在谁的任务栈中 默认模式，大多数Activity
singleTop 栈顶复用：若新Activity已在栈顶，则不重建，回调onNewIntent；否则创建新实例 通知栏点击启动的Activity、搜索页
singleTask 栈内复用：若任务栈中已存在则清除其上所有Activity并回调onNewIntent；可指定taskAffinity运行在指定栈中 应用首页、主界面
singleInstance 单实例模式：独占一个任务栈，全局唯一 来电界面、系统Launcher

1.2.2 Activity的Flags

常用Flag（通过Intent.addFlags设置）：

  • FLAG_ACTIVITY_NEW_TASK：为singleTask模式效果，需配合taskAffinity
  • FLAG_ACTIVITY_SINGLE_TOP：为singleTop模式效果
  • FLAG_ACTIVITY_CLEAR_TOP：清除目标Activity之上的所有Activity，常与singleTask配合
  • FLAG_ACTIVITY_EXCLUDE_FROM_RECENTS：不出现在最近任务列表中

1.3 IntentFilter的匹配规则

隐式Intent启动Activity时，需同时匹配action、category、data三个过滤规则。

  • action匹配：Intent中的action必须与过滤规则中的某一个action完全匹配（区分大小写）
  • category匹配：Intent中的每个category都必须在过滤规则中存在；Intent不设置category时系统默认添加android.intent.category.DEFAULT，因此隐式调用的Activity必须在filter中声明DEFAULT
  • data匹配：由mimeType和URI组成，URI包含scheme、host、port、path等部分；data匹配要求Intent中data的各部分与过滤规则一致

第2章 IPC机制

2.1 Android IPC简介

IPC（Inter-Process Communication）即跨进程通信，Android中基于Binder实现。

2.2 Android中的多进程模式

通过在AndroidManifest中为四大组件指定android:process属性即可开启多进程。

多进程的运行机制问题：Android为每个进程分配独立的虚拟机，不同进程之间内存不共享。这会导致：

  • 静态成员和单例模式完全失效
  • 线程同步机制完全失效（不同进程的锁不是同一把）
  • SharedPreferences的可靠性下降（不支持多进程并发读写）
  • Application会多次创建（每个进程启动时都会创建自己的Application）

2.3 IPC基础概念介绍

2.3.1 Serializable接口

Java提供的序列化接口，使用简单但开销大，会产生大量临时对象引起频繁GC。通过serialVersionUID标识序列化版本，反序列化时若版本不一致会抛出InvalidClassException。

2.3.2 Parcelable接口

Android提供的序列化方式，效率高，是Android推荐的序列化方式。通过writeToParcel写入、CREATOR读取。Parcelable主要用于内存序列化，Serializable可用于网络传输和持久化存储。

2.3.3 Binder

Binder是Android中实现IPC的核心机制，是一种开放的、轻量级的高性能架构。从机制上看，Binder是一种跨进程通信方式；从模型上看，Binder采用C/S架构，由Client、Server、ServiceManager和Binder驱动组成。

2.4 Android中的IPC方式

IPC方式 原理 适用场景 优缺点
Bundle 四大组件间通过Intent传递Bundle数据 Activity/Service/BroadcastReceiver间通信 简单易用，仅支持可序列化数据类型
文件共享 通过读写同一个文件交换数据 无并发场景下的数据交换 简单，不适合高并发，不支持即时通信
Messenger 基于AIDL的轻量级IPC，串行处理消息 低并发、简单的跨进程消息传递 实现简单，串行处理无法高并发，仅支持消息传递
AIDL 基于Binder的接口定义语言，支持并发 需要跨进程调用方法、高并发场景 功能强大，支持并发和实时通信，实现稍复杂
ContentProvider 以表格形式对外暴露数据，底层也是Binder 跨进程数据共享，如通讯录、媒体库 适合结构化数据共享，提供CRUD操作
Socket 通过网络套接字通信，不限于本机 跨设备/跨网络通信 灵活通用，需要处理网络权限和线程

2.5 Binder连接池

当应用中需要多个AIDL接口时，为每个接口单独创建Service会浪费资源。Binder连接池的思想是：统一一个Service，通过一个Binder连接池（BinderPool）来管理所有AIDL的Binder，客户端通过queryBinder方法根据不同的code获取对应的Binder。

2.6 选用合适的IPC方式

  • 四大组件间传递小数据 → Bundle
  • 简单的跨进程消息传递 → Messenger
  • 需要跨进程调用方法且有并发需求 → AIDL
  • 结构化数据跨进程共享 → ContentProvider
  • 无并发的简单数据交换 → 文件共享
  • 跨网络通信 → Socket

第3章 View的事件体系

3.1 View基础知识

3.1.1 什么是View

View是Android中所有控件的基类，ViewGroup继承自View，是控件的容器。

3.1.2 View的位置参数

  • left/top/right/bottom：View相对于父容器的原始左上右下坐标（getLeft()等）
  • x/y：View左上角的当前坐标，x = left + translationX，y = top + translationY
  • translationX/translationY：View左上角相对于父容器的偏移量，默认为0
  • elevation：View的Z轴高度（Android 5.0+）

3.1.3 MotionEvent和TouchSlop

MotionEvent典型事件：

  • ACTION_DOWN：手指刚接触屏幕
  • ACTION_MOVE：手指在屏幕上移动
  • ACTION_UP：手指从屏幕松开
  • ACTION_CANCEL：事件被中断（如被父View拦截）

TouchSlop：系统识别的最小滑动距离，通过ViewConfiguration.get(context).getScaledTouchSlop()获取。小于这个距离的移动不被认为是滑动。

3.1.4 VelocityTracker、GestureDetector和Scroller

  • VelocityTracker：速度追踪器，用于追踪手指在滑动过程中的速度（水平和垂直方向）。使用时需在onTouchEvent中添加追踪，computeCurrentVelocity计算速度，recycle回收资源。
  • GestureDetector：手势检测，辅助检测用户的单击、滑动、长按、双击等行为。通过OnGestureListener和OnDoubleTapListener回调。
  • Scroller：弹性滑动对象，用于实现View的弹性滑动（平滑移动）。本身不能让View滑动，需配合View的computeScroll方法使用。

3.2 View的滑动

滑动方式 原理 特点
scrollTo/scrollBy 改变View内容的位置（mScrollX/mScrollY），不改变View在布局中的位置 操作简单，只能滑动View内容，不能滑动View本身
动画 通过View动画或属性动画改变View的位置 属性动画可真正改变View位置；View动画只是影像移动，点击事件仍在原位置
改变布局参数 修改LayoutParams的margin等参数使View位置变化 真正改变View位置，适合需要交互的滑动

3.3 弹性滑动

弹性滑动的核心思想是将一次大的滑动拆分成多次小的滑动，在一段时间内完成。

  • 使用Scroller：startScroll开始滑动 → invalidate触发重绘 → computeScroll中获取当前scroll值并scrollTo → postInvalidate继续重绘，直到滑动完成
  • 通过动画：使用ValueAnimator的addUpdateListener，在动画更新时获取当前进度并执行scrollTo
  • 使用延时策略：通过Handler的postDelayed或View的postDelayed，在每次延时中scrollTo一小段距离

3.4 View的事件分发机制

3.4.1 点击事件的传递规则

事件分发的三个核心方法：

  1. **dispatchTouchEvent(MotionEvent ev)**：进行事件分发。如果事件能传递给当前View，则此方法一定会被调用。返回值受当前View的onTouchEvent和下级View的dispatchTouchEvent影响。
  2. **onInterceptTouchEvent(MotionEvent ev)**：在dispatchTouchEvent内部调用，判断是否拦截某个事件。如果拦截，则同一事件序列中此方法不再被调用，转而调用onTouchEvent。
  3. **onTouchEvent(MotionEvent ev)**：处理点击事件。返回false表示不消费当前事件，返回true表示消费。

3.5 View的滑动冲突

3.5.1 常见的滑动冲突场景

  1. 外部滑动方向和内部滑动方向不一致（如ViewPager嵌套ListView）
  2. 外部滑动方向和内部滑动方向一致（如ScrollView嵌套ListView）
  3. 上述两种情况的嵌套

3.5.2 滑动冲突的处理规则

对于场景1，根据滑动是水平还是竖直来判断谁来拦截事件。判断依据：滑动过程中水平距离大则为水平滑动，竖直距离大则为竖直滑动。

3.5.3 滑动冲突的解决方式

  • 外部拦截法：在父容器的onInterceptTouchEvent中处理。DOWN事件不拦截（否则子元素无法收到事件），MOVE事件根据需要决定是否拦截，UP事件不拦截（拦截UP会导致子元素无法触发点击事件）
  • 内部拦截法：在子元素的dispatchTouchEvent中处理，配合父容器的requestDisallowInterceptTouchEvent方法。子元素在DOWN时调用requestDisallowInterceptTouchEvent(true)禁止父容器拦截，在MOVE时根据需要调用false允许父容器拦截

第4章 View的工作原理

4.1 初识ViewRoot和DecorView

  • ViewRoot：对应ViewRootImpl类，是连接WindowManager和DecorView的纽带。View的三大流程（measure、layout、draw）均通过ViewRoot完成。
  • DecorView：顶级View，本质是FrameLayout，包含一个竖直方向的LinearLayout（标题栏+内容栏）。内容栏id为android.R.id.content，setContentView就是将布局添加到内容栏中。

Activity的Window创建后，DecorView尚未被WindowManager识别，直到ActivityThread的handleResumeActivity中调用wm.addView(decor, l)后，DecorView才真正完成创建和显示。

4.2 理解MeasureSpec

4.2.1 MeasureSpec

MeasureSpec代表一个32位int值，高2位代表SpecMode（测量模式），低30位代表SpecSize（测量大小）。

SpecMode 含义 对应LayoutParams
UNSPECIFIED 父容器不对View做任何限制，要多大给多大 一般用于系统内部，如ScrollView
EXACTLY 父容器已检测出View所需的精确大小，View的最终大小就是SpecSize match_parent或具体数值
AT_MOST 父容器指定了一个可用大小SpecSize，View的大小不能大于这个值 wrap_content

4.2.2 MeasureSpec和LayoutParams的对应关系

系统通过父容器的MeasureSpec和View自身的LayoutParams来确定View的MeasureSpec。对于顶级View（DecorView），其MeasureSpec由窗口尺寸和自身LayoutParams决定。

4.3 View的工作流程

4.3.1 measure过程

  • View的measure：通过onMeasure方法完成。setMeasuredDimension设置测量宽高。getDefaultSize方法中，对于AT_MOST和EXACTLY模式都返回specSize，这意味着如果自定义View不重写onMeasure，wrap_content和match_parent效果相同。
  • ViewGroup的measure：除了完成自己的measure，还会遍历调用所有子元素的measure方法。ViewGroup是抽象类，没有重写onMeasure，具体测量逻辑由各子类（如LinearLayout、FrameLayout）实现。

自定义View处理wrap_content：重写onMeasure时，当widthMode或heightMode为AT_MOST时，需要给View设置一个默认的内部宽高（如指定一个mWidth/mHeight），否则wrap_content会表现为match_parent。

4.3.2 layout过程

layout方法确定View的位置。通过setFrame方法设定View的四个顶点位置（mLeft、mTop、mRight、mBottom），然后调用onLayout确定子元素的位置。View的onLayout是空实现，ViewGroup的onLayout是抽象方法。

4.3.3 draw过程

draw过程将View绘制到屏幕上，步骤如下：

  1. 绘制背景（drawBackground）
  2. 绘制自己（onDraw）
  3. 绘制子元素（dispatchDraw）
  4. 绘制装饰（滚动条等，onDrawForeground）

View的绘制通过dispatchDraw来遍历调用子View的draw方法。setWillNotDraw(true)可优化：如果一个View不需要绘制任何内容（如纯容器ViewGroup），设置此标志后系统不会执行onDraw。

4.4 自定义View

4.4.1 自定义View的分类

  1. 继承View重写onDraw方法：实现不规则效果，需自己支持wrap_content和padding
  2. 继承特定ViewGroup（如LinearLayout）：实现组合布局，不需要自己处理measure和layout
  3. 继承特定View（如TextView、Button）：扩展已有控件功能
  4. 继承ViewGroup重写onMeasure和onLayout：实现自定义布局，需处理测量和布局逻辑

4.4.2 自定义View须知

  • 支持wrap_content：重写onMeasure处理AT_MOST模式
  • 支持padding：在onDraw和onLayout中考虑padding
  • 尽量不要在View中使用Handler：View内部已提供post系列方法
  • View中如有线程或动画，在onDetachedFromWindow中停止
  • 处理滑动冲突：根据场景使用外部拦截或内部拦截

4.4.3 自定义View示例

书中给出了一个圆形进度条的自定义View示例，通过继承View重写onDraw绘制圆弧和文字。

4.4.4 自定义View的思想

掌握自定义View的核心在于理解measure、layout、draw三大流程，以及事件分发机制。多数需求可以通过组合现有控件实现，真正需要继承View的场景主要是不规则绘制和自定义布局。

第5章 理解RemoteViews

5.1 RemoteViews的应用

RemoteViews表示一种可以在其他进程中显示的View结构，主要用于通知栏和桌面小部件。

5.1.1 RemoteViews在通知栏上的应用

通过NotificationCompat.Builder构建通知，使用setContent设置RemoteViews自定义通知布局。RemoteViews通过setTextViewText、setImageViewResource等方法设置控件内容，通过setOnClickPendingIntent设置点击事件。

5.1.2 RemoteViews在桌面小部件上的应用

桌面小部件通过AppWidgetProvider实现（本质是BroadcastReceiver）。在onUpdate中通过RemoteViews更新小部件界面，通过AppWidgetManager更新。

5.1.3 PendingIntent概述

PendingIntent表示一种处于待定状态的Intent，在未来某个时刻被触发。三种获取方式：

  • getActivity：获取一个用于启动Activity的PendingIntent
  • getService：获取一个用于启动Service的PendingIntent
  • getBroadcast：获取一个用于发送广播的PendingIntent

PendingIntent的匹配规则：Intent相同且requestCode相同则认为是同一个PendingIntent。Intent的匹配考虑componentName和intent-filter（data不参与匹配）。flags常用值：

  • FLAG_ONE_SHOT：只能使用一次
  • FLAG_NO_CREATE：若不存在则返回null
  • FLAG_CANCEL_CURRENT：若已存在则取消当前的并创建新的
  • FLAG_UPDATE_CURRENT：若已存在则更新其extra数据

5.2 RemoteViews的内部机制

RemoteViews的工作流程：

  1. RemoteViews在本地进程中通过一系列set方法设置操作（这些操作被封装成Action对象存入列表）
  2. 通过Binder将RemoteViews传递到远程进程（SystemServer中的通知服务或桌面进程）
  3. 远程进程通过apply方法执行所有Action，完成界面更新

RemoteViews不支持所有View和方法，仅支持部分布局（FrameLayout、LinearLayout、RelativeLayout、GridLayout等）和部分控件（TextView、Button、ImageView、ProgressBar等），且不支持findViewById直接操作控件。

5.3 RemoteViews的意义

RemoteViews的核心价值在于跨进程更新UI。它通过Action列表的方式将UI操作序列化后跨进程传递，避免了大量Binder调用。除了通知栏和桌面小部件，也可用于应用内跨进程UI更新（如两个进程通过RemoteViews交换界面）。

第6章 Android的Drawable

6.1 Drawable简介

Drawable是一种可绘制对象的抽象概念，可以是图片、颜色、图形等。Drawable的优点：使用简单，比自定义View成本低；非图片类型的Drawable占用空间小。

Drawable的内部宽高通过getIntrinsicWidth/getIntrinsicHeight获取，图片Drawable有原始尺寸，纯颜色Drawable无固有尺寸（返回-1）。Drawable没有大小概念，作为View背景时会被拉伸至View大小。

6.2 Drawable的分类

Drawable类型 XML标签 用途
BitmapDrawable <bitmap> 引用一张图片，可设置tileMode平铺、gravity对齐等
ShapeDrawable <shape> 通过XML绘制图形（矩形/椭圆/线/环），支持solid渐变、stroke描边、corners圆角、padding
LayerDrawable <layer-list> 分层叠加多个Drawable，每层可设置left/top/right/bottom偏移
StateListDrawable <selector> 根据View状态切换不同Drawable（如按钮按下/正常/禁用）
LevelListDrawable <level-list> 根据level值切换Drawable，通过setLevel设置（如电量显示）
TransitionDrawable <transition> 两层Drawable之间的淡入淡出切换，startTransition/reverseTransition
InsetDrawable <inset> 将Drawable内嵌并设置四周留白，常用于需要比View小的背景
ScaleDrawable <scale> 根据level将Drawable缩放到一定比例，level=0时不可见，需设置level>0才显示
ClipDrawable <clip> 根据level裁剪Drawable，level从0到10000，0表示完全裁剪（不可见）

6.3 自定义Drawable

继承Drawable重写以下方法：

  • **draw(Canvas canvas)**：绘制内容
  • **setAlpha(int alpha)**：设置透明度
  • **setColorFilter(ColorFilter cf)**：设置颜色滤镜
  • **getOpacity()**：返回透明度模式（PixelFormat.TRANSLUCENT等）

自定义Drawable的优势在于可以用代码绘制复杂效果，且占用内存小。在onBoundsChange中获取Drawable的尺寸。

第7章 Android动画深入分析

7.1 View动画

7.1.1 View动画的种类

动画类型 XML标签 效果
平移动画 <translate> 移动View位置，fromXDelta/toXDelta等
缩放动画 <scale> 放大缩小View，pivotX/pivotY指定缩放中心
旋转动画 <rotate> 旋转View，fromDegrees/toDegrees
透明度动画 <alpha> 改变View透明度，fromAlpha/toAlpha

通过AnimationUtils.loadAnimation加载XML动画，view.startAnimation启动。也可通过代码创建Animation对象。setFillAfter(true)保持动画结束后的状态。

7.1.2 自定义View动画

继承Animation，重写initialize和applyTransformation方法。在applyTransformation中通过Matrix变换实现自定义动画效果，interpolatedTime参数表示动画当前进度（0~1）。

7.1.3 帧动画

通过<animation-list>定义一系列Drawable，按顺序播放。使用AnimationDrawable，注意不能在onCreate中调用start（此时View还未完全附着到窗口），应在onWindowFocusChanged中或通过post方式启动。

7.2 View动画的特殊使用场景

7.2.1 LayoutAnimation

用于为ViewGroup的子元素设置出场动画，每个子元素按一定顺序和延迟播放动画。通过android:layoutAnimation属性或LayoutAnimationController设置。delay属性指定每个子元素动画的延迟比例（如0.5表示每个子元素延迟前一个动画时长的50%）。animationOrder可选normal（顺序）、reverse（逆序）、random（随机）。

7.2.2 Activity的切换效果

通过overridePendingTransition(int enterAnim, int exitAnim)在startActivity或finish之后调用，设置Activity的进入和退出动画。Fragment的切换通过FragmentTransaction的setCustomAnimations设置。

7.3 属性动画

7.3.1 使用属性动画

属性动画（Android 3.0+引入）可以对任意对象的任意属性做动画，不仅仅是View。核心类：

  • ValueAnimator：属性动画的核心，负责计算属性值的变化，不直接操作对象
  • ObjectAnimator：继承ValueAnimator，可直接对对象的属性做动画（需属性有getter/setter）
  • AnimatorSet：动画集合，可编排多个动画的先后/同时关系

常用方法：ofFloat、ofInt、ofArgb、ofObject。通过setDuration设置时长，setInterpolator设置插值器，addListener设置监听器。

7.3.2 理解插值器和估值器

  • 插值器（Interpolator/TimeInterpolator）：根据时间流逝的百分比计算出当前属性值改变的百分比。如AccelerateDecelerateInterpolator（先加速后减速）、LinearInterpolator（匀速）、DecelerateInterpolator（减速）。
  • 估值器（TypeEvaluator）：根据当前属性改变的百分比计算改变后的属性值。如IntEvaluator、FloatEvaluator、ArgbEvaluator。自定义估值器可实现对任意类型的动画。

7.3.3 属性动画的监听器

  • AnimatorListener：监听动画的开始、结束、取消、重复
  • AnimatorUpdateListener：监听动画的每一帧更新，在onAnimationUpdate中可获取当前属性值

7.3.4 对任意属性做动画

ObjectAnimator要求动画属性有getter和setter方法。如果属性没有setter（如View的width），有三种解决方法：

  1. 给对象加上get/set方法（如果有权限）
  2. 用一个类来包装原始对象，间接为其提供get/set方法
  3. 采用ValueAnimator，监听动画过程，自己实现属性的改变

7.3.5 属性动画的工作原理

属性动画通过不断调用set方法改变对象属性值来实现动画。系统内部维护一个动画处理器（AnimationHandler），通过Choreographer（与VSYNC同步）驱动动画帧的计算。每帧计算当前的fraction（进度），通过插值器转换为插值后的fraction，再通过估值器计算出当前属性值，最后调用set方法设置。

7.4 使用动画的注意事项

  • OOM问题：帧动画图片过多过大时容易OOM，尽量避免使用大量大图的帧动画
  • 内存泄漏：属性动画中有无限循环动画（如旋转），应在Activity退出时停止动画，否则Activity无法释放
  • 兼容性问题：属性动画在Android 3.0以下不兼容，可使用nineoldandroids兼容库（其内部在低版本上实际是通过View动画代理实现）
  • View动画问题：View动画是对View影像做动画，View的真实位置不变，点击事件仍在原位置。属性动画则真正改变View属性。
  • 不要使用px：动画中尽量使用dp，避免不同分辨率设备效果不一致
  • 开启硬件加速：动画过程中建议开启硬件加速（android:hardwareAccelerated=”true”），提升流畅度

第8章 理解Window和WindowManager

8.1 Window和WindowManager

Window是一个抽象类，具体实现是PhoneWindow。WindowManager是外界访问Window的入口，Window的具体实现位于WindowManagerService中，二者交互是IPC过程。

WindowManager继承自ViewManager，提供三个核心方法：

  • **addView(View view, LayoutParams params)**：添加Window
  • **updateViewLayout(View view, LayoutParams params)**：更新Window参数
  • **removeView(View view)**：移除Window

WindowManager.LayoutParams的关键参数：

  • type：Window类型，分为应用Window（199）、子Window（10001999）、系统Window（2000~2999）。层级越高越靠上显示。
  • flags：Window标志位，控制Window的显示特性。如FLAG_NOT_FOCUSABLE（不获取焦点）、FLAG_NOT_TOUCH_MODAL（区域外事件传递给下层Window）、FLAG_SHOW_WHEN_LOCKED（锁屏上显示）。
  • gravity：Window的对齐方式
  • x/y：Window的位置

8.2 Window的内部机制

Window的添加、删除、更新均通过WindowManagerImpl实现，而WindowManagerImpl又委托给WindowManagerGlobal（单例模式）处理。

8.2.1 Window的添加过程

  1. WindowManagerGlobal.addView：创建ViewRootImpl，将View、LayoutParams、ViewRootImpl存入对应列表
  2. ViewRootImpl.setView：通过requestLayout触发异步刷新，然后通过WindowSession（IWindowSession Binder对象）调用WindowManagerService的addWindow方法完成最终添加

8.2.2 Window的删除过程

通过WindowManagerGlobal.removeView → ViewRootImpl.die → dispatchDetachedFromWindow → WindowSession.removeWindow完成。removeView是异步删除，removeViewImmediate是同步删除（不推荐使用，可能导致问题）。

8.2.3 Window的更新过程

通过updateViewLayout → ViewRootImpl.setLayoutParams → scheduleTraversals触发View重绘 → WindowSession.relayout更新Window参数。

8.3 Window的创建过程

8.3.1 Activity的Window创建过程

  1. ActivityThread.performLaunchActivity中创建Activity，调用attach方法
  2. attach中创建PhoneWindow（mWindow = new PhoneWindow），并设置WindowManager
  3. setContentView中：PhoneWindow.installDecor创建DecorView，inflate加载布局到mContentParent
  4. handleResumeActivity中调用wm.addView(decor, l)，DecorView正式显示

8.3.2 Dialog的Window创建过程

  1. Dialog构造方法中创建PhoneWindow
  2. show方法中：创建DecorView，通过WindowManager.addView添加DecorView
  3. dismiss方法中：通过ViewRootImpl的die方法移除DecorView

Dialog必须使用Activity的Context，不能用Application的Context（因为需要应用Window token），除非是系统级Dialog（需要SYSTEM_ALERT_WINDOW权限）。

8.3.3 Toast的Window创建过程

Toast基于NotificationManagerService（NMS）实现，通过IPC调用NMS的enqueueToast方法。NMS内部通过ToastRecord维护Toast队列，通过回调ITransientNotification（TN，Binder对象）的show/hide方法显示/隐藏Toast。TN的show方法中通过handle发送消息，在Handler中通过WindowManager.addView添加Toast的View。Toast有两类：普通Toast（内部有Handler，需在有Looper的线程中使用）和系统级Toast。

第9章 四大组件的工作过程

9.1 四大组件的运行状态

四大组件中除了BroadcastReceiver可以在代码中动态注册外，其他三种（Activity、Service、ContentProvider）都必须在AndroidManifest中注册。四大组件的启动都离不开ApplicationThread（ActivityThread的内部类，Binder对象，用于与AMS通信）。

9.2 Activity的工作过程

  1. 调用startActivity → Instrumentation.execStartActivity → 通过ActivityManagerService（AMS）的代理对象调用startActivity
  2. AMS内部通过ActivityStackSupervisor和ActivityStack管理Activity栈，检查调用者权限、创建ActivityRecord等
  3. AMS通过ApplicationThread（Binder回调）调用scheduleLaunchActivity
  4. ActivityThread的H（Handler）收到LAUNCH_ACTIVITY消息，调用handleLaunchActivity
  5. handleLaunchActivity中：performLaunchActivity（通过ClassLoader加载Activity类、调用attach创建Window、调用onCreate）→ handleResumeActivity（调用onResume、wm.addView显示DecorView）

9.3 Service的工作过程

9.3.1 Service的启动过程

  1. startService → ContextImpl.startService → AMS.startService
  2. AMS通过ActiveServices处理，创建ServiceRecord，通过ApplicationThread回调scheduleCreateService
  3. ActivityThread的H收到CREATE_SERVICE消息 → handleCreateService：加载Service类、创建实例、调用attach、调用onCreate
  4. 随后AMS通过ApplicationThread回调scheduleServiceArgs → handleServiceArgs → onStartCommand

9.3.2 Service的绑定过程

  1. bindService → ContextImpl.bindService → AMS.bindService
  2. AMS通过ActiveServices处理，若Service未启动则先启动（同启动过程）
  3. Service创建后，AMS调用publishService（通过Service的onBind返回的IBinder）
  4. AMS通过ApplicationThread回调scheduleBindService → handleBindService → onBind（若首次绑定）→ onServiceConnected（ServiceConnection回调）

9.4 BroadcastReceiver的工作过程

9.4.1 广播的注册过程

静态注册：在AndroidManifest中声明，应用安装时由PackageManagerService解析并注册，无需应用启动即可接收广播。

动态注册：通过Context.registerReceiver注册，最终通过AMS的registerReceiver完成。动态注册的广播必须在组件销毁时unregisterReceiver，否则会内存泄漏。

9.4.2 广播的发送和接收过程

  1. sendBroadcast → ContextImpl.sendBroadcast → AMS.broadcastIntent
  2. AMS通过BroadcastQueue处理广播，区分有序广播和普通广播
  3. AMS遍历匹配的BroadcastReceiver，通过ApplicationThread回调scheduleRegisteredReceiver
  4. ActivityThread通过LoadedApk的ReceiverDispatcher调用onReceive（动态注册）；静态注册则通过scheduleReceiver启动进程后调用onReceive

9.5 ContentProvider的工作过程

  1. 应用启动时，ActivityThread.handleBindApplication中：创建Application → installContentProviders（启动ContentProvider）→ Application.onCreate
  2. installContentProviders中：遍历providers列表，通过AMS.publishContentProviders发布
  3. ContentProvider创建时调用onCreate（注意：ContentProvider的onCreate先于Application的onCreate执行）
  4. 其他应用通过ContentResolver的query/insert/update/delete访问ContentProvider，ContentResolver通过AMS获取ContentProvider的Binder代理（IContentProvider），然后通过IPC调用对应方法

重要顺序：应用启动时的执行顺序为：ContentProvider.onCreate → Application.onCreate。ContentProvider的onCreate中应避免耗时操作，因为它会阻塞应用启动。

第10章 Android的消息机制

10.1 Android的消息机制概述

Android的消息机制主要指Handler的运行机制，Handler的运行需要底层的MessageQueue和Looper支撑。MessageQueue是消息队列，采用单链表数据结构存储消息；Looper是消息循环，不断从MessageQueue中取出消息并处理。ThreadLocal用于在每个线程中存储Looper实例。

10.2 Android的消息机制分析

10.2.1 ThreadLocal的工作原理

ThreadLocal是一个线程内部的数据存储类，通过它可以在指定线程中存储数据，数据存储后只有在指定线程中才能获取到。对于Handler来说，它需要获取当前线程的Looper，不同线程的Looper不同，通过ThreadLocal可以轻松实现。

ThreadLocal的内部实现：每个线程（Thread）内部有一个ThreadLocalMap成员变量，ThreadLocal的set方法将值存入当前线程的ThreadLocalMap中（key为ThreadLocal的弱引用，value为存储的值），get方法从当前线程的ThreadLocalMap中取值。

10.2.2 消息队列的工作原理

MessageQueue虽然叫队列，但内部实现是单链表（便于插入和删除）。两个核心操作：

  • enqueueMessage：插入一条消息，按时间（when）排序插入链表
  • next：从消息队列中取出一条消息并移除。next方法是一个无限循环，若没有消息则阻塞（nativePollOnce），等待新消息到来时唤醒。

10.2.3 Looper的工作原理

  • 构造方法：创建MessageQueue，保存当前线程引用
  • **prepare()**：为当前线程创建Looper并存入ThreadLocal。一个线程只能有一个Looper，重复调用会抛异常。prepareMainLooper为主线程创建Looper。
  • **loop()**：进入消息循环，无限调用MessageQueue.next获取消息，然后调用msg.target.dispatchMessage(msg)分发消息（target即发送消息的Handler）。如果next返回null则退出循环。loop方法中调用msg.recycleUnchecked回收消息。
  • **quit()**：直接退出Looper；quitSafely()：设定退出标记，等消息队列中已有消息处理完后退出。子线程的Looper使用完后应主动quit。

10.2.4 Handler的工作原理

Handler的工作包括消息发送和消息接收两部分。

消息发送：通过post/send系列方法发送消息，最终调用enqueueMessage → MessageQueue.enqueueMessage将消息插入队列。enqueueMessage中会将msg.target设为当前Handler。

消息接收：Looper的loop中调用dispatchMessage，处理流程：

  1. 若msg.callback（Runnable对象）不为空，调用handleCallback（执行Runnable）
  2. 否则若Handler的mCallback（Callback接口）不为空，调用mCallback.handleMessage，返回true则结束
  3. 否则调用Handler自身的handleMessage方法

Handler的构造方法：Handler会通过ThreadLocal获取当前线程的Looper，如果当前线程没有Looper则会抛出”Can’t create handler inside thread that has not called Looper.prepare()”。因此在子线程中使用Handler前必须先调用Looper.prepare()。

10.3 主线程的消息循环

Android的主线程就是ActivityThread，主线程的入口方法为main。在main方法中：

  1. Looper.prepareMainLooper()：创建主线程的Looper和MessageQueue
  2. 创建ActivityThread对象（其内部的H是一个Handler，处理四大组件的生命周期等消息）
  3. Looper.loop()：进入主线程消息循环

主线程的消息循环一旦停止，应用就会ANR或退出。四大组件的生命周期调用都是通过H（Handler）来调度的。

第11章 Android的线程和线程池

11.1 主线程和子线程

主线程（UI线程）：负责界面的交互和绘制，Android 3.0+禁止在主线程中进行网络访问（NetworkOnMainThreadException）。主线程中不能执行耗时操作，否则会ANR（Activity 5秒、BroadcastReceiver 10秒、Service 20秒）。

子线程：用于执行耗时任务。Android中线程形态包括传统Thread、AsyncTask、HandlerThread、IntentService等。

11.2 Android中的线程形态

11.2.1 AsyncTask

AsyncTask是一个轻量级的异步任务类，封装了线程池和Handler，可以在线程池中执行后台任务，然后将执行进度和结果传递到主线程更新UI。

三个泛型参数：

  • Params：执行任务时传入的参数类型
  • Progress：后台任务执行进度的类型
  • Result：后台任务返回结果的类型

四个核心方法：

  • onPreExecute：主线程执行，任务开始前的准备工作
  • doInBackground：线程池中执行，具体的后台任务，可调用publishProgress更新进度
  • onProgressUpdate：主线程执行，更新进度
  • onPostExecute：主线程执行，任务结束后处理结果

AsyncTask的使用条件和限制：

  • AsyncTask的类必须在主线程中加载（Android 4.1+已自动完成）
  • AsyncTask的对象必须在主线程中创建
  • execute方法必须在主线程中调用
  • 不要在程序中直接调用onPreExecute/onPostExecute/doInBackground/onProgressUpdate
  • 一个AsyncTask对象只能执行一次execute，否则会抛异常
  • Android 1.6之前串行执行，1.6~2.3并行执行，3.0+默认串行执行（可通过executeOnExecutor指定并行）

11.2.2 AsyncTask的工作原理

AsyncTask内部有两个线程池（SerialExecutor和THREAD_POOL_EXECUTOR）和一个Handler（InternalHandler）。

  • SerialExecutor：默认的串行执行器，将任务按顺序排队，一个接一个执行
  • THREAD_POOL_EXECUTOR：真正执行任务的线程池，核心线程数为CPU核心数+1，最大线程数为CPU核心数*2+1，队列容量128
  • InternalHandler：将执行环境从线程池切换到主线程，用于发送进度更新和结果

执行流程：execute → executeOnExecutor → SerialExecutor.execute（将任务加入队列）→ 取出任务调用THREAD_POOL_EXECUTOR.execute → FutureTask.run → doInBackground → publishProgress → InternalHandler发送消息 → onProgressUpdate/onPostExecute。

11.2.3 HandlerThread

HandlerThread是一种自带Looper的Thread，继承自Thread。在run方法中调用Looper.prepare()和Looper.loop()，创建了消息循环。通过getLooper获取其Looper，然后可创建Handler与之绑定。

特点：HandlerThread的run方法是无限循环，使用完后需通过quit或quitSafely终止。适合用于需要在子线程中处理消息队列的场景（如IntentService内部就使用了HandlerThread）。

11.2.4 IntentService

IntentService是一个特殊的Service，继承自Service，内部使用HandlerThread和ServiceHandler来处理异步请求。

工作流程：

  1. onCreate中创建HandlerThread并启动，获取其Looper创建ServiceHandler
  2. onStartCommand中调用onStart，将Intent封装为Message发送给ServiceHandler
  3. ServiceHandler的handleMessage中调用onHandleIntent（抽象方法，子类实现）
  4. onHandleIntent执行完后调用stopSelf(msg.arg1)，尝试停止Service（若还有未处理的消息则不停止）

特点：IntentService按顺序处理请求，处理完所有请求后自动停止，无需手动调用stopService。适合执行后台耗时任务，任务执行完自动结束。

11.3 Android中的线程池

11.3.1 ThreadPoolExecutor

线程池的优点：复用线程减少创建销毁开销、控制最大并发数避免资源竞争、对线程进行简单管理（定时/周期执行）。

核心参数：

  • corePoolSize：核心线程数，默认情况下核心线程会一直存活（即使闲置），allowCoreThreadTimeOut(true)时核心线程也会超时回收
  • maximumPoolSize：最大线程数，活动线程数不能超过此值
  • keepAliveTime：非核心线程闲置超时时长，超过则回收。allowCoreThreadTimeOut(true)时也作用于核心线程
  • unit：keepAliveTime的时间单位
  • workQueue：任务队列，通过线程池的execute方法提交的Runnable对象存储在此
  • threadFactory：线程工厂，为线程池创建新线程
  • rejectedExecutionHandler：拒绝策略，当队列满且达到最大线程数时的处理策略（AbortPolicy默认抛异常、CallerRunsPolicy用调用者线程执行、DiscardPolicy直接丢弃、DiscardOldestPolicy丢弃队列中最早的任务）

任务执行规则：

  1. 线程数 < corePoolSize → 启动核心线程执行任务
  2. 线程数 ≥ corePoolSize且队列未满 → 任务加入队列等待
  3. 队列满且线程数 < maximumPoolSize → 启动非核心线程执行任务
  4. 队列满且线程数 ≥ maximumPoolSize → 执行拒绝策略

11.3.2 线程池的分类

线程池类型 创建方法 特点
FixedThreadPool Executors.newFixedThreadPool 核心线程数=最大线程数，无超时，队列无界。所有线程都是核心线程，适合执行长期任务。
CachedThreadPool Executors.newCachedThreadPool 核心线程数0，最大线程数Integer.MAX_VALUE，超时60秒，队列SynchronousQueue。线程数按需创建回收，适合执行大量耗时少的任务。
ScheduledThreadPool Executors.newScheduledThreadPool 核心线程数固定，最大线程数Integer.MAX_VALUE，队列DelayedWorkQueue。支持定时和周期任务。
SingleThreadExecutor Executors.newSingleThreadExecutor 核心线程数=最大线程数=1，单线程串行执行所有任务，保证任务按顺序执行。

第12章 Bitmap的加载和Cache

12.1 Bitmap的高效加载

Bitmap在Android中指的是一张图片。加载Bitmap的核心是通过BitmapFactory的四个方法：decodeFile、decodeResource、decodeStream、decodeByteArray。其中decodeFile和decodeResource间接调用decodeStream。

高效加载的核心思想——采样率压缩（inSampleSize）：

  1. 将BitmapFactory.Options的inJustDecodeBounds设为true，此时只加载图片的原始宽高信息（outWidth/outHeight），不真正加载图片到内存
  2. 根据目标View的尺寸和图片原始尺寸计算inSampleSize（采样率）。inSampleSize必须是2的指数（如1、2、4、8），系统会向下取整到最近的2的指数。inSampleSize=2表示宽高都变为原来的1/2，像素数变为1/4，内存占用变为1/4。
  3. 将inJustDecodeBounds设为false，设置计算好的inSampleSize，重新加载图片

采样率计算规则：如果inSampleSize大于1，则按inSampleSize的比例缩小宽高。例如原图1024×1024，inSampleSize=4，加载后为256×256。计算时取max(原宽/目标宽, 原高/目标高)，然后取最接近的2的指数。

12.2 Android中的缓存策略

12.2.1 LruCache

LruCache是Android 3.1+提供的缓存类，采用LRU（Least Recently Used，最近最少使用）算法。内部通过LinkedHashMap（accessOrder=true，访问顺序排序）实现，当缓存满时，优先淘汰最近最少使用的缓存对象。

使用要点：

  • 构造方法传入缓存总大小（通常为进程可用内存的1/8）
  • 重写sizeOf方法计算每个缓存对象的大小（Bitmap的大小用getByteCount或getRowBytes*getHeight）
  • put添加缓存，get获取缓存，remove移除缓存
  • 可重写entryRemoved方法在缓存被移除时做资源回收

12.2.2 DiskLruCache

DiskLruCache用于实现磁盘缓存（存储设备缓存），不是Android官方SDK的类，需手动引入源码。

使用要点：

  • open方法：创建DiskLruCache实例，参数包括目录、版本号、每个key对应的值的数量（通常为1）、总缓存大小
  • 写入缓存：通过Editor编辑，editor.newOutputStream获取输出流写入数据，editor.commit提交，editor.abort放弃
  • 读取缓存：通过get方法获取Snapshot，snapshot.getInputStream获取输入流读取
  • key的处理：key只能包含字母、数字、下划线和横线，不能有特殊字符。通常将URL通过MD5或SHA-256哈希后作为key
  • remove/delete/flush：remove删除指定缓存，delete清空并关闭缓存，flush将缓存日志写入磁盘（建议在Activity的onPause中调用）

12.2.3 ImageLoader的实现

一个完整的ImageLoader应包含：

  1. 图片压缩：根据ImageView尺寸对图片进行采样率压缩
  2. 内存缓存：LruCache作为一级缓存
  3. 磁盘缓存：DiskLruCache作为二级缓存
  4. 网络加载：从网络下载图片，写入磁盘缓存
  5. 同步加载：loadBitmap方法，按内存→磁盘→网络的顺序查找
  6. 异步加载：bindBitmap方法，在线程池中执行同步加载，通过Handler切换到主线程设置图片
  7. 列表错位问题：给ImageView设置tag（图片URL），加载完成后检查tag是否匹配，避免列表复用时图片错位

12.3 ImageLoader的使用

12.3.1 照片墙效果

使用GridView或RecyclerView展示大量图片，通过ImageLoader异步加载图片。在getView/onBindViewHolder中调用bindBitmap加载图片。注意在滚动时（onScrollStateChanged中SCROLL_STATE_FLING状态）暂停加载，停止滚动后恢复加载，可提升流畅度。

12.3.2 优化列表的卡顿现象

  • 不要在getView/onBindViewHolder中做耗时操作
  • 控制异步任务的执行频率，列表滑动时暂停加载
  • 开启硬件加速
  • 使用ViewHolder/RecycledViewPool复用视图
  • 避免过度绘制

第13章 综合技术

13.1 使用CrashHandler来获取应用的crash信息

通过实现Thread.UncaughtExceptionHandler接口，在uncaughtException方法中捕获崩溃信息并存储到SD卡，可上传到服务器。

实现步骤：

  1. 创建CrashHandler类实现UncaughtExceptionHandler
  2. 在init方法中通过Thread.setDefaultUncaughtExceptionHandler(this)设置为默认异常处理器
  3. 在uncaughtException中：收集崩溃信息（设备信息、系统版本、崩溃堆栈）→ 写入文件 → 可通过Thread.sleep等待写入完成 → 调用原默认处理器的uncaughtException（或直接杀死进程）
  4. 在Application的onCreate中初始化CrashHandler

13.2 使用multidex来解决方法数越界

Android中单个DEX文件的方法数不能超过65536（64K）。当应用方法数超过限制时，需要使用multidex方案将应用拆分成多个DEX文件。

使用步骤：

  1. build.gradle中添加multiDexEnabled true和依赖com.android.support:multidex
  2. Application继承MultiDexApplication（或在attachBaseContext中调用MultiDex.install(this)）

局限性：

  • Android 4.0以下可能因Dalvik的linearAlloc限制（5MB）而启动失败
  • 首次启动时因需要加载多个DEX可能导致ANR（主DEX中的类不能太多）
  • 需要通过–multi-dex-keep-list配置主DEX中必须包含的类（Application、四大组件等）

13.3 Android的动态加载技术

动态加载（插件化）技术允许应用在不安装新APK的情况下加载并运行外部的DEX/APK文件。核心技术点：

  • 类加载：通过DexClassLoader加载外部DEX中的类。DexClassLoader需要一个optimizedDirectory（odex文件输出目录）。
  • 资源加载：通过AssetManager的addAssetPath方法（反射调用）将外部APK的资源加入AssetManager，然后创建新的Resources对象加载外部资源。
  • Activity生命周期管理：插件Activity需要由宿主的代理Activity（ProxyActivity）来管理生命周期。通过反射调用插件Activity的生命周期方法。
  • 占坑式启动：在AndroidManifest中预先声明一些占坑Activity，启动插件Activity时先启动占坑Activity，然后在Instrumentation或ActivityThread的Handler中替换为真正的插件Activity。

常见的动态加载框架：DynamicLoadApk、DL、Small、RePlugin等。

13.4 反编译初步

13.4.1 使用dex2jar和jd-gui反编译apk

  1. 将APK改名为.zip解压，取出classes.dex
  2. 使用dex2jar工具：d2j-dex2jar.bat classes.dex，生成classes-dex2jar.jar
  3. 使用jd-gui打开jar文件，查看Java源代码

13.4.2 使用apktool对apk进行二次打包

  1. apktool d xxx.apk：反编译APK，得到smali代码、资源文件、AndroidManifest等
  2. 修改smali代码或资源
  3. apktool b xxx：重新打包成APK
  4. 使用jarsigner或apksigner对APK签名
  5. zipalign对齐优化

注意：反编译需遵守法律法规，仅用于学习和安全研究目的。

第14章 JNI和NDK编程

14.1 JNI的开发流程

JNI（Java Native Interface）是Java与Native代码（C/C++）交互的桥梁。

开发步骤：

  1. 在Java中声明native方法（如public native String getStringFromNative();）
  2. 编译Java文件生成.class文件（javac）
  3. 使用javah生成C/C++头文件（javah -jni com.example.Test），头文件中包含native方法的函数声明
  4. 实现C/C++源文件，实现头文件中的函数
  5. 编译C/C++代码生成动态链接库（.so文件）
  6. 在Java中通过System.loadLibrary(“xxx”)加载so库
  7. 调用native方法

14.2 NDK的开发流程

NDK（Native Development Kit）是Android提供的工具集，用于在Android中开发C/C++代码。

传统NDK开发（Android.mk + Application.mk）：

  1. 在项目中创建jni目录
  2. 编写Android.mk（描述编译规则、源文件、库名等）和Application.mk（指定ABI平台、STL等）
  3. 编写C/C++源文件
  4. 在jni目录下执行ndk-build编译生成so库
  5. so库自动放入libs/对应ABI目录

现代NDK开发（CMake + build.gradle）：

  1. 在build.gradle中配置externalNativeBuild { cmake { path “CMakeLists.txt” } }
  2. 编写CMakeLists.txt（描述编译规则）
  3. 编写C/C++源文件
  4. 通过Android Studio编译运行

14.3 JNI的数据类型和类型签名

14.3.1 基本数据类型映射

Java类型 JNI类型 C/C++类型
boolean jboolean unsigned char
byte jbyte signed char
char jchar unsigned short
short jshort short
int jint int
long jlong long long
float jfloat float
double jdouble double
void void void

14.3.2 引用数据类型

Java的引用类型在JNI中都以jobject为基类，如jclass（Class）、jstring（String）、jarray（数组）、jobjectArray（对象数组）、jbooleanArray等基本类型数组。

14.3.3 类型签名

JNI中通过类型签名标识Java类型：

  • 基本类型：Z(boolean)、B(byte)、C(char)、S(short)、I(int)、J(long)、F(float)、D(double)、V(void)
  • 引用类型：L + 全限定名 + ; （如Ljava/lang/String;）
  • 数组：[ + 类型签名 （如[I表示int[]，[Ljava/lang/String;表示String[]）
  • 方法签名：(参数类型签名)返回值类型签名 （如(ILjava/lang/String;)V表示void method(int, String)）

14.4 JNI调用Java方法的流程

Native代码中调用Java方法的步骤：

  1. 通过FindClass获取Java类的jclass引用
  2. 通过GetMethodID获取方法ID（需传入类引用、方法名、方法签名）
  3. 通过CallObjectMethod/CallIntMethod/CallVoidMethod等调用方法（需传入对象引用、方法ID、参数）
  4. 对于静态方法，使用GetStaticMethodID和CallStaticXxxMethod
  5. 对于字段，使用GetFieldID/GetStaticFieldID和GetXxxField/SetXxxField

JNIEnv：JNI环境指针，是Native代码调用Java功能的入口。每个线程有独立的JNIEnv，不能跨线程使用。在Native线程中需要通过JavaVM的AttachCurrentThread获取JNIEnv，使用完后DetachCurrentThread。

第15章 Android性能优化

15.1 Android的性能优化方法

15.1.1 布局优化

  • 减少布局层级：布局层级越深，测量和绘制越耗时。优先使用ConstraintLayout或RelativeLayout减少嵌套，避免不必要的嵌套。
  • **使用<include>**：复用布局文件，减少重复代码。
  • **使用<merge>**：当include的根布局与父布局相同时，使用merge减少一层布局。merge必须作为根标签，被include时直接合并到父布局中。
  • **使用<ViewStub>**：延迟加载布局。ViewStub是轻量级View，不占用布局位置，初始不可见，inflate时才加载目标布局。适合用于网络错误页、加载更多等不常显示的布局。
  • 使用Hierarchy Viewer：分析布局层级，找出性能瓶颈。

15.1.2 绘制优化

  • 避免在onDraw中执行耗时操作：onDraw会被频繁调用，不应创建新对象（会导致频繁GC）、不应做循环计算。
  • 避免过度绘制：通过手机开发者选项中的”调试GPU过度绘制”查看。蓝色为1次过度绘制（可接受），绿色2次，淡红3次，深红4次及以上（需优化）。优化方法：移除不必要的背景、使用clipRect减少绘制区域。

15.1.3 内存泄露优化

常见的内存泄露场景：

  • 静态变量持有Activity/Context：静态变量生命周期与进程一致，会导致Activity无法回收。应使用Application Context或弱引用。
  • 单例模式持有Context：单例应使用Application Context而非Activity Context。
  • 非静态内部类/匿名内部类：非静态内部类默认持有外部类引用。如Handler、AsyncTask、Thread作为非静态内部类持有Activity，在Activity销毁时任务未完成会导致泄露。应使用静态内部类+弱引用。
  • 未取消注册的广播/事件总线：动态注册的BroadcastReceiver、EventBus等在组件销毁时必须unregister。
  • 资源未关闭：Cursor、File、Socket、Stream等使用完后必须关闭。
  • 属性动画未停止：无限循环的属性动画在Activity销毁时必须cancel。
  • WebView：WebView存在内存泄露问题，应在独立进程中使用，销毁时调用WebView.destroy并从父布局中移除。

15.1.4 响应速度优化和ANR日志分析

ANR（Application Not Responding）：应用无响应。触发条件：

  • Activity：前台5秒内无响应（输入事件或BroadcastReceiver）
  • BroadcastReceiver：onReceive 10秒内未执行完（前台）/ 60秒（后台）
  • Service：前台20秒/后台200秒内未执行完

ANR优化：主线程中不做耗时操作，将耗时操作放到子线程。使用StrictMode（严格模式）检测主线程中的磁盘读写和网络访问。

ANR日志分析：ANR发生后系统会在/data/anr/traces.txt中记录堆栈信息。通过分析traces.txt找到主线程的阻塞点。关键信息包括：进程名、主线程状态、各线程堆栈、CPU使用率。

15.1.5 ListView和Bitmap优化

  • ListView优化：使用ViewHolder复用convertView；getView中避免耗时操作和创建对象；滑动时暂停图片加载；使用硬件加速；分页加载数据。
  • Bitmap优化：使用inSampleSize压缩图片；使用LruCache和DiskLruCache缓存；及时recycle不再使用的Bitmap（Android 3.0+Bitmap像素数据存放在堆中，GC可自动回收，但大图片仍建议主动recycle）；使用inBitmap复用Bitmap内存（Android 3.0+）。

15.1.6 线程优化

  • 使用线程池代替直接new Thread，减少线程创建销毁开销，控制并发数
  • 避免在主线程中执行耗时操作
  • 合理设置线程池参数，避免线程过多导致CPU资源竞争
  • AsyncTask适用于短时间的异步任务，长时间任务建议使用IntentService或线程池

15.1.7 一些性能优化建议

  • 避免创建过多对象：尤其是在循环和onDraw中，减少GC频率
  • 避免过度使用枚举：枚举比静态常量占用更多内存（可用@IntDef/@StringDef替代）
  • 使用SparseArray代替HashMap：SparseArray是Android提供的高效数据结构，key为int，避免了自动装箱，内存更紧凑。类似的有SparseBooleanArray、SparseIntArray、LongSparseArray。
  • 避免在循环中调用getSystemService：应在初始化时获取一次
  • 使用Intent传递数据时避免大数据：Intent中传递大数据可能导致TransactionTooLargeException（Binder缓冲区限制约1MB）
  • 合理使用多进程：将WebView、推送服务等放到独立进程，减少主进程内存占用
  • 优化启动速度：Application的onCreate中不做耗时操作，延迟初始化非必要组件；使用冷启动预览主题（windowBackground）减少白屏

15.2 内存泄露分析之MAT工具

MAT（Memory Analyzer Tool）是Eclipse提供的Java堆内存分析工具，用于分析内存泄露。

使用步骤：

  1. 通过DDMS或Android Studio的Memory Monitor导出HPROF文件（堆转储文件）
  2. 使用hprof-conv工具将Android HPROF转换为标准Java HPROF格式
  3. 用MAT打开转换后的HPROF文件
  4. 使用Histogram视图查看对象数量和占用内存
  5. 使用Dominator Tree查看最大的对象和引用链
  6. 使用Path to GC Roots查看对象到GC Root的引用路径，定位泄露原因
  7. 对比两个HPROF文件（操作前和操作后），找出增长的对象

关键概念：

  • Shallow Heap：对象自身占用的内存大小
  • Retained Heap：对象被GC回收后能释放的总内存（包括它引用的对象）
  • GC Root：可达性分析的根节点，包括线程栈中的引用、静态变量、JNI引用等。从GC Root不可达的对象可被GC回收。

15.3 提高程序的可维护性

  • 代码风格统一：遵循统一的命名规范、代码格式，使用Lint检查代码
  • 合理的架构设计：使用MVP/MVVM/MVI等架构模式，分层清晰，职责单一
  • 模块化/组件化：将应用拆分为多个模块，降低耦合，便于团队协作和维护
  • 注释和文档：关键代码添加注释，公共接口编写文档
  • 单元测试：为核心逻辑编写单元测试，保证代码质量和重构安全
  • 版本控制规范：合理使用Git分支策略，规范提交信息
  • 错误处理统一：统一的异常处理、错误码定义、日志规范
  • 配置管理：将常量、配置项集中管理，避免硬编码
