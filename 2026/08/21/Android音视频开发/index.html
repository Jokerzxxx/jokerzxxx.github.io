Android音视频开发

Android音视频开发

作者：何俊林
全书共11章，606页，系统讲解Android音视频系统架构，从MediaPlayer到StageFright/NuPlayer，从OMX框架到FFmpeg，从直播技术到H.264/H.265编码和视频格式分析。

第1章 音视频基础知识

1.1 视频编码

视频编码的核心目标是压缩数据量。原始视频数据量巨大（如1080P@30fps，每帧约6MB，每秒约180MB），必须通过编码压缩才能存储和传输。

常见视频编码标准：

  • H.264/AVC：目前应用最广泛的编码标准，压缩效率高，兼容性好
  • H.265/HEVC：H.264的继任者，同等画质下码率降低约50%，但编码复杂度高
  • VP8/VP9：Google推出的开源编码标准
  • AV1：AOMedia推出的新一代开源编码，压缩效率优于H.265

视频编码的核心技术：

  • 帧内预测：利用空间相关性，用相邻像素预测当前块
  • 帧间预测：利用时间相关性，通过运动估计和运动补偿消除时间冗余
  • 变换编码：将空间域信号变换到频率域（如DCT），便于量化压缩
  • 量化：降低变换系数的精度，是有损压缩的主要来源
  • 熵编码：对量化后的系数进行无损压缩（如CAVLC、CABAC）

1.2 音频编码

常见音频编码标准：

  • AAC：Advanced Audio Coding，MP3的继任者，同等码率下音质更好
  • MP3：MPEG-1 Audio Layer 3，最经典的音频编码格式
  • Opus：开源、低延迟、高音质，适合实时通信
  • PCM：未压缩的原始音频数据，WAV文件的核心

音频编码的核心参数：

  • 采样率：每秒采样次数，常见44100Hz、48000Hz
  • 采样位深：每个采样点的位数，常见16bit、24bit
  • 声道数：单声道、立体声、5.1声道等
  • 码率：每秒数据量，决定音质和文件大小

1.3 多媒体播放组件

Android平台：

  • MediaPlayer：Android原生播放器，支持本地和网络音视频播放
  • AudioTrack：底层音频播放接口，直接播放PCM数据
  • MediaCodec：Android 4.1+引入的硬编解码接口
  • SurfaceView/TextureView：视频渲染视图

iOS平台：

  • AVPlayer：iOS原生播放器
  • AVAudioPlayer：音频播放
  • VideoToolbox/AudioToolbox：底层编解码框架

1.5 相关知识点

码率（比特率）：单位时间播放连续媒体的比特数量。比特率越高，带宽消耗越多，音质/画质越好。

帧率（FPS）：每秒显示的帧数，常见24fps（电影）、30fps（视频）、60fps（高帧率）。

分辨率：视频画面的像素尺寸，如1920×1080（1080P）、3840×2160（4K）。

封装格式：将音视频编码数据打包成文件的格式，如MP4、FLV、TS、AVI、MKV等。封装格式不等于编码格式。

第2章 常用的系统播放器MediaPlayer

2.1 状态图及生命周期

MediaPlayer有严格的状态机，不同状态下可调用的方法不同：

状态流转：

  1. Idle：new MediaPlayer()或reset()后的状态
  2. Initialized：setDataSource()后
  3. Prepared：prepare()同步完成后
  4. Preparing：prepareAsync()调用后，异步准备中
  5. Started：start()后，播放中
  6. Paused：pause()后，暂停
  7. Stopped：stop()后，停止
  8. PlaybackCompleted：播放完成
  9. Error：发生错误
  10. End：release()后，资源释放

关键注意：在Idle状态下调用getCurrentPosition等方法会触发OnErrorListener；在Prepared之前调用start()会抛出IllegalStateException。

2.2 从创建到setDataSource过程

  1. 创建MediaPlayer：new MediaPlayer()，进入Idle状态
  2. 设置数据源：setDataSource(path)，支持本地文件路径、FileDescriptor、Uri
  3. setDataSource的底层实现：
    • Java层调用native方法
    • JNI层调用C++层MediaPlayer的setDataSource
    • 通过Binder IPC调用MediaPlayerService的setDataSource
    • 根据数据源类型创建对应的播放器（StageFrightPlayer/NuPlayer）

2.3 开始prepare后的流程

同步prepare：

  1. Java层prepare() → native_prepare
  2. C++层MediaPlayer.prepare() → Binder调用MediaPlayerService
  3. 实际播放器（AwesomePlayer/NuPlayer）执行prepare
  4. 完成后返回，进入Prepared状态

异步prepareAsync：

  1. Java层prepareAsync()立即返回
  2. 底层异步执行准备工作
  3. 准备完成后通过回调notify → JNI → Java层onPrepared
  4. 进入Prepared状态，此时可调用start()

2.4 C++中MediaPlayer的C/S架构

MediaPlayer采用客户端-服务端架构：

  • 客户端（Client）：应用进程中的MediaPlayer对象，通过Binder与服务端通信
  • 服务端（Server）：MediaPlayerService，运行在mediaserver进程中
  • 通信方式：Binder IPC，通过IMediaPlayer接口

关键类：

  • MediaPlayer：Java层接口
  • android::MediaPlayer：C++层客户端
  • IMediaPlayerService：服务端Binder接口
  • IMediaPlayer：播放器实例Binder接口
  • MediaPlayerService::Client：服务端客户端代理

3.1 Client/Server通过IPC的通信流程图

核心类关系：

3.3 产生过程

MediaPlayerService在系统启动时由mediaserver进程创建：

  1. mediaserver进程启动
  2. 调用MediaPlayerService::instantiate()
  3. 将服务注册到ServiceManager，名称为”media.player”
  4. 进入消息循环等待客户端请求

3.4 添加服务的过程

  1. 客户端通过ServiceManager.getService("media.player")获取服务Binder代理
  2. 调用IMediaPlayerService::create()创建播放器实例
  3. 服务端创建MediaPlayerService::Client对象
  4. 将Client的Binder代理返回给客户端
  5. 后续通过Client代理控制播放器

3.5 通过BinderDriver和MediaPlayer通信的过程

  1. 客户端调用IMediaPlayer接口方法（如start、pause、stop）
  2. Binder驱动将调用数据传递到mediaserver进程
  3. MediaPlayerService::Client的对应方法被调用
  4. Client转发给实际播放器（AwesomePlayer/NuPlayer）
  5. 播放器执行操作，状态变化通过回调通知客户端

3.6 创建播放器

MediaPlayerService根据数据源类型选择播放器：

  • StageFrightPlayer：基于AwesomePlayer，Android 4.x默认
  • NuPlayer：Android 5.0+默认，专为流媒体优化
  • TestPlayerStub：测试用

创建过程在MediaPlayerService::Client::setDataSource中，根据URL的scheme或文件类型决定使用哪个播放器。

3.7 建立StageFright层交互

创建AwesomePlayer后：

  1. 初始化AwesomePlayer
  2. 设置DataSource（从URI或文件描述符创建）
  3. 准备阶段：解析媒体格式、创建解码器、初始化渲染器
  4. 播放阶段：解码→渲染→音视频同步

第4章 StagefrightPlayer（AwesomePlayer）

4.1 AwesomePlayer构造过程

AwesomePlayer是StageFright框架的核心播放器类，构造过程：

  1. 创建AwesomePlayer实例
  2. 初始化成员变量（mQueue、mExtractor、mVideoSource、mAudioSource等）
  3. 创建AwesomeRenderer（视频渲染器）
  4. 创建AudioPlayer（音频播放器，负责音频解码和同步）

4.2 AwesomePlayer使用MediaExtractor进行数据解析的过程

数据解析流程：

  1. 根据DataSource创建MediaExtractor
  2. MediaExtractor解析封装格式（MP4/FLV/TS等）
  3. 获取轨道数量和各轨道的编码格式
  4. 对MP4文件：分离音视频轨道，返回MPEG4Source类型的视频轨道
  5. 根据编码类型选择解码器（如AVC类型选择AVCDecoder）
  6. 设置解码器的source为对应轨道

4.3 AwesomePlayer解码过程

视频解码：

  1. AwesomePlayer::onVideoEvent被触发
  2. 从mVideoSource读取一帧编码数据
  3. 调用OMXCodec解码
  4. 解码后的YUV数据交给AwesomeRenderer渲染
  5. 渲染完成后，post下一个onVideoEvent到队列

音频解码：

  1. AudioPlayer在独立线程中运行
  2. 从mAudioSource读取编码数据
  3. 调用OMXCodec解码为PCM
  4. PCM数据写入AudioTrack播放
  5. AudioPlayer维护时间戳，作为音视频同步的主时钟

4.4 AwesomePlayer的渲染输出过程

视频渲染：

  • AwesomeRenderer通过SoftwareRenderer或OMX渲染
  • SoftwareRenderer：将YUV转换为RGB，通过软件渲染到Surface
  • OMX渲染：通过硬件解码器直接渲染到Surface（零拷贝）

音频渲染：

  • AudioTrack将PCM数据写入音频设备
  • 通过setVolume控制音量
  • 支持立体声和多声道

4.5 概要总结

AwesomePlayer的核心组件：

  • MediaExtractor：数据解析，分离音视频轨道
  • OMXCodec：音视频解码，基于OpenMAX接口
  • AudioPlayer：音频解码和播放，作为同步主时钟
  • AwesomeRenderer：视频渲染
  • TimedEventQueue：事件队列，驱动视频播放循环

第5章 流媒体播放的新生力量NuPlayer

5.1 NuPlayer整体结构

NuPlayer是Android 5.0（Lollipop）引入的新一代播放器架构，专为流媒体播放优化，逐渐取代AwesomePlayer成为默认播放器。

NuPlayer的核心优势：

  • 更好的流媒体支持（HLS、DASH等自适应码率）
  • 更清晰的模块化架构
  • 更好的音视频同步
  • 支持更多的DRM方案

NuPlayer的核心组件：

  • NuPlayer::Source：数据源，负责数据读取和解析
  • NuPlayer::Decoder：解码器，基于MediaCodec
  • NuPlayer::Renderer：渲染器，负责音视频同步和输出
  • ALooper/AMessage：异步消息机制，驱动播放器状态机

5.2 NuPlayer的构建过程

  1. MediaPlayerService创建NuPlayerDriver（NuPlayer的包装类）
  2. NuPlayerDriver创建NuPlayer实例
  3. NuPlayer创建ALooper（消息循环）
  4. 注册NuPlayer到ALooper，处理AMessage
  5. 播放器通过AMessage异步驱动状态转换

5.3 NuPlayer的数据解析模块

Source模块负责：

  • 从URI或文件描述符创建DataSource
  • 解析媒体封装格式
  • 分离音视频轨道
  • 提供编码数据给Decoder

支持的数据源类型：

  • GenericSource：通用数据源，处理本地文件和普通HTTP流
  • HTTPLiveSource：HLS流媒体数据源
  • RTSPSource：RTSP流媒体数据源

5.4 NuPlayer的解码模块

Decoder模块：

  • 基于MediaCodec API实现硬解码
  • 支持视频和音频解码
  • 通过AMessage与Source和Renderer通信
  • 支持异步解码，提高效率

解码流程：

  1. Decoder向Source请求编码数据
  2. Source返回一帧编码数据（AccessUnit）
  3. Decoder将数据送入MediaCodec
  4. MediaCodec异步解码，通过回调返回解码后的数据
  5. Decoder将解码后的数据发送给Renderer

5.5 NuPlayer的渲染模块

Renderer模块负责：

  • 音视频同步（以音频时钟为主）
  • 视频帧渲染到Surface
  • 音频PCM数据写入AudioTrack
  • 管理播放速率（支持变速播放）

音视频同步策略：

  • 音频作为主时钟（master clock）
  • 视频根据音频时间戳调整播放速度
  • 视频帧延迟则丢帧，提前则等待
  • 保证音频连续不卡顿

6.2 Codec部分中的OMXCodec与OMX事件回调流程

OMXCodec的工作模式：

  • 输入端口：接收编码数据
  • 输出端口：输出解码数据
  • 事件回调：OMX组件通过回调通知状态变化

回调流程：

  1. OMX组件完成一帧解码
  2. 通过OnEvent回调通知OMXCodec
  3. OMXCodec处理事件，读取输出缓冲区
  4. 将解码后的数据返回给调用者（AwesomePlayer）
  5. 释放输出缓冲区，供OMX组件继续使用

6.3 MediaCodec相关知识

MediaCodec是Android 4.1（API 16）引入的硬编解码API，是应用层访问硬件解码器的标准接口。

MediaCodec的工作流程：

  1. 创建：MediaCodec.createDecoderByType(mime)或createByCodecName(name)
  2. 配置：configure(format, surface, crypto, flags)
  3. 启动：start()，进入Running状态
  4. 循环处理：
    • dequeueInputBuffer()获取输入缓冲区索引
    • 填充编码数据到输入缓冲区
    • queueInputBuffer()提交输入缓冲区
    • dequeueOutputBuffer()获取输出缓冲区索引
    • 处理输出数据（渲染或读取）
    • releaseOutputBuffer()释放输出缓冲区
  5. 结束：stop() → release()

MediaCodec的两种模式：

  • 同步模式：在循环中调用dequeueInputBuffer/dequeueOutputBuffer
  • 异步模式（API 21+）：设置Callback，通过回调处理输入输出

关键注意：MediaCodec的输入输出缓冲区管理非常重要，必须正确释放缓冲区，否则会导致死锁或内存泄漏。

第7章 FFmpeg项目

7.1 FFmpeg简介

FFmpeg是一套开源的跨平台音视频处理工具库，名称中的FF代表Fast Forward（快进）。

FFmpeg的核心库：

  • libavcodec：编解码库，包含几乎所有音视频编解码器
  • libavformat：封装格式库，支持读写各种音视频封装格式
  • libavutil：工具库，包含通用工具函数
  • libswscale：图像缩放和颜色空间转换库
  • libswresample：音频重采样库
  • libavfilter：滤镜库，支持音视频滤镜处理
  • libavdevice：设备库，支持输入输出设备

FFmpeg的命令行工具：

  • ffmpeg：音视频转码工具
  • ffplay：简单的播放器
  • ffprobe：音视频信息分析工具

7.2 在Windows下编译FFmpeg

Windows下编译FFmpeg需要MSYS2环境：

  1. 安装MSYS2
  2. 安装编译工具链（gcc、make、yasm/nasm）
  3. 安装依赖库（x264、x265、fdk-aac等）
  4. 配置：./configure --enable-gpl --enable-libx264 --enable-shared
  5. 编译：make -j4
  6. 安装：make install

7.3 在Linux下编译FFmpeg

Linux下编译相对简单：

  1. 安装依赖：sudo apt-get install build-essential yasm nasm
  2. 安装可选编解码库
  3. 配置、编译、安装（同Windows步骤）

7.4 在Mac OS下编译FFmpeg

Mac OS下使用Homebrew安装依赖，编译步骤与Linux类似。也可直接brew install ffmpeg安装预编译版本。

第8章 FFmpeg源码分析及实战

8.1 FFmpeg常用结构体分析

核心结构体：

结构体 作用
AVFormatContext 格式上下文，代表一个媒体文件或流，包含所有轨道信息
AVCodecContext 编解码器上下文，包含编解码参数和状态
AVStream 媒体轨道（视频流/音频流）
AVPacket 编码后的数据包（一帧视频或一段音频）
AVFrame 解码后的原始数据帧（YUV视频或PCM音频）
AVCodec 编解码器信息（名称、类型、支持的格式等）
AVIOContext I/O上下文，管理输入输出
AVDictionary 键值对字典，用于配置参数

关键关系：

  • AVFormatContext包含多个AVStream
  • 每个AVStream关联一个AVCodecContext
  • AVCodecContext关联一个AVCodec
  • 解码过程：AVPacket → 解码器 → AVFrame

8.2 FFmpeg关键函数介绍

初始化和打开：

  • av_register_all()：注册所有编解码器和格式（FFmpeg 4.0+已废弃，自动注册）
  • avformat_network_init()：初始化网络模块
  • avformat_open_input()：打开媒体文件，创建AVFormatContext
  • avformat_find_stream_info()：读取媒体信息，获取轨道详情

解码相关：

  • avcodec_find_decoder()：根据ID或名称查找解码器
  • avcodec_alloc_context3()：分配解码器上下文
  • avcodec_parameters_to_context()：将轨道参数复制到解码器上下文
  • avcodec_open2()：打开解码器
  • av_read_frame()：读取一帧数据包（AVPacket）
  • avcodec_send_packet()：发送编码数据到解码器
  • avcodec_receive_frame()：从解码器获取解码后的帧

资源释放：

  • av_packet_unref()：释放Packet引用
  • av_frame_free()：释放Frame
  • avcodec_free_context()：释放解码器上下文
  • avformat_close_input()：关闭媒体文件

8.4 FFPlay原理

FFPlay是FFmpeg自带的简单播放器，其架构体现了音视频播放器的经典设计：

核心模块：

  • 读线程（read_thread）：读取数据包，放入视频/音频Packet队列
  • 视频解码线程（video_thread）：从视频Packet队列取数据解码，放入Frame队列
  • 音频解码线程（audio_thread）：从音频Packet队列取数据解码，播放音频
  • 视频渲染线程（video_refresh_thread）：从Frame队列取帧，根据音视频同步策略渲染

音视频同步策略：

  • 以音频时钟为主时钟
  • 视频帧根据音频时钟调整显示时间
  • 延迟则丢帧，提前则等待

队列机制：

  • Packet队列：存储解码前的数据包
  • Frame队列：存储解码后的帧
  • 队列有最大长度限制，防止内存溢出
  • 通过条件变量实现生产者-消费者模式

第9章 直播技术

9.1 直播原理

直播的完整流程：

各环节说明：

  1. 采集：摄像头采集视频，麦克风采集音频
  2. 预处理：美颜、滤镜、水印、混音等
  3. 编码：H.264/H.265视频编码，AAC/Opus音频编码
  4. 封装：封装为FLV或TS格式（适合流式传输）
  5. 推流：通过RTMP协议推送到流媒体服务器
  6. 服务器分发：流媒体服务器接收并分发给观众
  7. 拉流：观众端通过RTMP/HTTP-FLV/HLS拉取流
  8. 解封装/解码/渲染：播放器处理并显示

9.2 直播架构

常见直播架构：

  1. CDN直播架构：

    • 推流端 → 接入层 → 源站 → CDN边缘节点 → 播放端
    • 适合大规模观众，延迟较高（3-10秒）

  2. 低延迟直播架构：

    • 使用WebRTC技术，端到端延迟可低于1秒
    • 适合互动直播、在线教育

  3. P2P直播架构：

    • 观众之间共享数据，减轻服务器压力
    • 适合超大规模直播

9.3 直播过程

推流端核心流程：

  1. 初始化采集设备（Camera、AudioRecord）
  2. 设置编码参数（分辨率、码率、帧率）
  3. 创建MediaCodec编码器
  4. 采集数据 → 预处理 → 送入编码器
  5. 编码数据封装为FLV Tag
  6. 通过RTMP协议发送到服务器

播放端核心流程：

  1. 连接流媒体服务器
  2. 接收FLV/TS数据流
  3. 解封装，分离音视频
  4. 送入MediaCodec解码器
  5. 解码后渲染视频、播放音频
  6. 音视频同步

9.4 流媒体服务器搭建

常见流媒体服务器：

  • Nginx-RTMP：Nginx的RTMP模块，轻量易用
  • SRS：Simple Realtime Server，国产高性能流媒体服务器
  • Wowza：商业流媒体服务器，功能强大
  • Red5：Java开源流媒体服务器

9.5 FFmpeg推流到流媒体服务器的过程

推流参数说明：

  • -re：按文件原始帧率读取（模拟实时流）
  • -c copy：直接复制编码数据，不重新编码
  • -f flv：输出格式为FLV
  • -preset ultrafast：编码速度最快（适合实时推流）
  • -tune zerolatency：零延迟优化

9.6 直播优化那些事

延迟优化：

  • 编码器设置低延迟模式（zerolatency）
  • 减少GOP长度（关键帧间隔）
  • 使用HTTP-FLV替代HLS
  • CDN边缘节点优化
  • 播放器缓冲区调小

卡顿优化：

  • 自适应码率（ABR）：根据网络状况切换码率
  • 前向纠错（FEC）：发送冗余数据修复丢包
  • 丢包重传（ARQ）：请求重传丢失的数据包
  • 网络抖动缓冲（Jitter Buffer）：平滑网络波动

画质优化：

  • 合理设置码率（1080P建议4-6Mbps）
  • 使用H.265替代H.264（同等画质码率减半）
  • 动态关键帧（场景切换时插入关键帧）
  • 码率控制模式选择（CBR/VBR/CRF）

第10章 H.264编码及H.265编码

10.1 H.264编码框架

H.264/AVC是目前应用最广泛的视频编码标准，由ITU-T和ISO/IEC联合制定。

H.264的编码层次：

  • 序列（Sequence）：一组连续的编码帧
  • 图像（Picture）：一帧视频
  • 片（Slice）：一帧可分为多个片，每个片独立编码
  • 宏块（Macroblock）：16×16像素块，H.264的基本编码单元
  • 子块（Sub-block）：4×4、8×8等更小的块

H.264的帧类型：

  • I帧（Intra-coded）：帧内编码，不依赖其他帧，可独立解码，作为随机访问点
  • P帧（Predictive-coded）：前向预测编码，参考前面的I/P帧
  • B帧（Bi-predictive-coded）：双向预测编码，参考前后的帧，压缩率最高

10.2 H.264编码原理

H.264编码的核心步骤：

  1. 帧内预测（Intra Prediction）：

    • 利用当前帧已编码的相邻像素预测当前块
    • 支持多种预测模式（4×4有9种，16×16有4种）
    • 消除空间冗余

  2. 帧间预测（Inter Prediction）：

    • 运动估计（Motion Estimation）：在参考帧中寻找最佳匹配块
    • 运动补偿（Motion Compensation）：根据运动向量生成预测块
    • 消除时间冗余

  3. 变换（Transform）：

    • 对预测残差进行4×4整数DCT变换
    • 将空间域信号变换到频率域
    • 直流系数（DC）单独进行Hadamard变换

  4. 量化（Quantization）：

    • 对变换系数进行量化，降低精度
    • 量化参数（QP）范围0-51，QP越大压缩率越高、画质越差
    • 是有损压缩的主要来源

  5. 熵编码（Entropy Coding）：

    • CAVLC（基于上下文的自适应变长编码）：Baseline Profile使用
    • CABAC（基于上下文的自适应二进制算术编码）：Main/High Profile使用，压缩率更高
    • 无损压缩

  6. 去块效应滤波（Deblocking Filter）：

    • 对重建图像进行滤波，消除块效应
    • 提高主观画质和后续帧的预测效率

10.3 H.264码流分析

H.264的码流结构：

网络抽象层（NAL）：

  • H.264码流由一系列NAL单元组成
  • 每个NAL单元以起始码0x000001或0x00000001开头
  • NAL单元类型由第一个字节的低5位决定

常见NAL单元类型：

类型 名称 说明
1 非IDR图像的Slice P/B帧数据
5 IDR图像的Slice I帧数据（关键帧）
6 SEI 补充增强信息
7 SPS 序列参数集
8 PPS 图像参数集
9 AUD 访问单元分隔符

关键参数集：

  • SPS（Sequence Parameter Set）：包含序列级参数（Profile、Level、图像尺寸、参考帧数量等），解码整个序列都需要
  • PPS（Picture Parameter Set）：包含图像级参数（量化参数、片组等），解码一帧需要
  • SPS和PPS通常在I帧之前发送，播放器必须先解析SPS/PPS才能解码

10.4 H.265编码框架

H.265/HEVC是H.264的继任者，2013年正式发布，目标是在同等画质下将码率降低约50%。

H.265相比H.264的主要改进：

  1. 编码单元（CU）更大：

    • H.264最大宏块16×16
    • H.265最大编码单元（LCU）64×64
    • 支持四叉树递归划分，更灵活

  2. 更多的预测模式：

    • 帧内预测模式从9种增加到35种
    • 帧间预测支持更精确的运动向量（1/4像素精度）
    • 支持运动向量合并（Merge）和高级运动向量预测（AMVP）

  3. 更高效的变换：

    • 支持4×4到32×32的可变大小DCT变换
    • 大尺寸变换更适合平坦区域

  4. 并行处理能力：

    • Tile（瓦片）：将图像分为多个独立编码的区域
    • Wavefront（波前）：行级并行编码
    • 适合多核CPU和GPU硬件加速

  5. 更高效的熵编码：

    • 全部使用CABAC（H.264的Baseline不支持CABAC）
    • 更高的压缩效率

H.265的NAL单元类型扩展：

  • VPS（Video Parameter Set）：视频参数集，H.265新增，管理多个子层的参数
  • SPS、PPS继续保留，结构有所扩展

H.265的编码复杂度约为H.264的2-3倍，但解码复杂度增加不多。随着硬件支持的普及，H.265正在逐步取代H.264成为主流。

第11章 视频格式分析

11.1 MP4格式分析

MP4（MPEG-4 Part 14）是目前最主流的视频封装格式，基于QuickTime的MOV格式发展而来。

MP4的核心特点：

  • 基于Box（原子）结构，每个Box有类型和大小
  • 支持流式播放（需要moov atom在文件头部）
  • 支持多种编码格式（H.264/H.265视频，AAC/MP3音频）
  • 支持字幕、章节、元数据

MP4的关键Box：

Box 作用
ftyp 文件类型，标识MP4版本和兼容性
moov Movie Box，包含所有媒体元数据（索引信息）
mvhd Movie Header，媒体整体信息（时长、时间戳等）
trak Track Box，一个轨道（视频/音频/字幕）
tkhd Track Header，轨道信息（ID、尺寸、音量等）
mdia Media Box，轨道媒体信息
mdhd Media Header，媒体时间信息
hdlr Handler Reference，轨道类型（vide/soun）
stbl Sample Table Box，采样表（索引数据）
stsd Sample Description，编码格式详情
stts Time-to-Sample，时间戳到采样的映射
stss Sync Sample，关键帧索引（随机访问点）
stsc Sample-to-Chunk，采样到块的映射
stsz Sample Size，每个采样的大小
stco Chunk Offset，每个块在文件中的偏移
mdat Media Data Box，实际的音视频数据

MP4播放需要先解析moov box获取索引信息，再根据索引从mdat中读取数据。因此moov在文件头部时支持流式播放，在尾部时需要下载完整个文件才能播放。

11.2 FLV格式分析

FLV（Flash Video）是Adobe推出的流媒体格式，曾是网页直播的主流格式。

FLV的核心特点：

  • 结构简单，适合流式传输
  • 支持H.264视频和AAC音频
  • 文件头 + 一系列Tag
  • 是RTMP协议传输的封装格式

FLV文件结构：

FLV Tag结构：

视频Tag数据：

  • 第1字节高4位：编码类型（7=H.264）
  • 第1字节低4位：帧类型（1=关键帧，2=非关键帧）
  • 第2字节：AVC包类型（0=序列头，1=NALU，2=序列结束）
  • 第3-5字节：合成时间（CTS）
  • 后续：H.264数据

音频Tag数据：

  • 第1字节高4位：编码格式（10=AAC）
  • 第1字节第2-3位：采样率（3=44kHz）
  • 第1字节第1位：采样精度（1=16bit）
  • 第1字节第0位：声道类型（1=立体声）
  • 第2字节：AAC包类型（0=序列头，1=原始数据）
  • 后续：AAC数据

11.3 F4V格式分析

F4V是Adobe基于MP4推出的Flash视频格式，本质上是MP4的子集，支持H.264和AAC。相比FLV，F4V支持更高效的编码和更好的 seeking 能力。

11.4 TS格式分析

TS（MPEG-2 Transport Stream）是为广播和流媒体设计的封装格式，是HLS（HTTP Live Streaming）的标准封装格式。

TS的核心特点：

  • 固定长度包（188字节），适合流式传输和纠错
  • 支持多路节目复用
  • 容错能力强，丢失部分包不影响整体播放
  • 是数字电视（DVB）和HLS的标准格式

TS包结构：

关键PID：

  • 0x0000：PAT（Program Association Table，节目关联表）
  • 0x0001：CAT（Conditional Access Table，条件访问表）
  • 0x1000-0x1FFE：PMT（Program Map Table，节目映射表）
  • 其他PID：音视频数据流

TS的关键表：

  • PAT：列出所有节目及其PMT的PID
  • PMT：列出一个节目包含的所有音视频流及其PID
  • 通过PAT→PMT→音视频PID的层级关系找到需要的流

PES（Packetized Elementary Stream）：

  • 原始音视频数据（ES）被打包成PES包
  • PES包再被切分成TS包的有效载荷
  • PES包头包含时间戳（PTS/DTS）

11.5 AVI格式分析

AVI（Audio Video Interleave）是微软1992年推出的封装格式，是Windows平台的经典视频格式。

AVI的特点：

  • 基于RIFF（Resource Interchange File Format）结构
  • 结构简单，但功能有限
  • 不支持流式播放
  • 不支持B帧（早期版本）
  • 文件大小限制（旧版2GB，新版支持更大）
  • 逐渐被MP4取代

11.6 ASF格式分析

ASF（Advanced Systems Format）是微软推出的流媒体格式，是WMA（音频）和WMV（视频）的封装格式。

ASF的特点：

  • 基于对象结构，每个对象有GUID标识
  • 支持数字版权管理（DRM）
  • 支持流式播放
  • 支持脚本命令和元数据
  • 文件扩展名通常为.asf、.wma、.wmv

ASF的核心对象：

  • Header Object：文件头，包含所有元数据
    • File Properties Object：文件属性（文件大小、创建时间、数据包数量）
    • Stream Properties Object：流属性（流类型、编码信息）
    • Header Extension Object：头扩展（内容描述、脚本命令）
  • Data Object：数据区，包含所有媒体数据包
  • Index Object：索引区，用于快速定位

读书笔记总结

《Android音视频开发》是一本系统讲解Android音视频系统架构的技术书籍，从应用层MediaPlayer到底层StageFright/NuPlayer播放器框架，从OMX硬解码到FFmpeg开源库，从直播技术到H.264/H.265编码原理和视频封装格式，形成了完整的知识体系。

  1. 系统播放架构（第2-5章）：MediaPlayer → MediaPlayerService → AwesomePlayer/NuPlayer，理解Android系统播放器的C/S架构和状态机
  2. 编解码框架（第6章）：OpenMAX/OMX框架和MediaCodec API，掌握硬件编解码的使用
  3. FFmpeg实战（第7-8章）：FFmpeg编译、命令行使用、源码结构和播放器原理
  4. 直播技术（第9章）：直播全流程、流媒体服务器搭建、推流和优化
  5. 编码原理（第10章）：H.264/H.265编码框架、原理和码流结构
  6. 封装格式（第11章）：MP4、FLV、TS、AVI等常见视频格式的底层结构

学习建议：

  • 系统播放架构部分需要结合Android源码理解，建议下载AOSP源码对照阅读
