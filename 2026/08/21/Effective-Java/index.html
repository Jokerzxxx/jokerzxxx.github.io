Effective Java

Effective Java（原书第3版）

作者：Joshua Bloch
全书共12章90条，316页，Java领域最经典的最佳实践书籍，涵盖对象创建、方法、类、泛型、枚举、Lambda、并发、序列化等核心主题。

第1章 引言

本书的目标是帮助读者更有效地使用Java编程语言及其基本类库。每条规则都以”第N条：”的形式呈现，包含具体的建议、代码示例和反例。

核心原则：

  • 清晰性和正确性优先于性能
  • 代码应被阅读的次数远多于被编写的次数
  • 优先使用库而非自己实现
  • 避免使用语言中容易出问题的特性

第2章 创建和销毁对象

第1条：用静态工厂方法代替构造器

静态工厂方法是一个返回类实例的静态方法，相比构造器有以下优势：

  • 有名称：方法名能清楚描述返回的对象（如BigInteger.probablePrime）
  • 不必每次调用都创建新对象：可返回预构建的实例或缓存的实例（如Boolean.valueOf）
  • 可返回原返回类型的任何子类型：隐藏实现类（如Collections.unmodifiableList返回不可修改列表）
  • 返回对象的类可以随参数变化：如EnumSet根据元素数量返回RegularEnumSet或JumboEnumSet
  • 方法返回的对象在编写时可以不存在：服务提供者框架（如JDBC）

缺点：

  • 只提供静态工厂方法而不提供public/protected构造器，类不能被子类化
  • 程序员难以发现静态工厂方法（需查阅文档）

常用命名：from、of、valueOf、instance、getInstance、create、getType、newType、type。

第2条：遇到多个构造器参数时要考虑使用构建器

当类有多个可选参数时，传统方式有：

  • 重叠构造器模式：参数多时代码难写难读
  • JavaBeans模式：调用无参构造器+setter，构造过程中对象可能不一致，无法做成不可变类

Builder模式：

  • 不直接生成对象，先调用构造器（或静态工厂）得到builder对象
  • 调用builder的setter-like方法设置参数
  • 调用build方法生成不可变对象
  • 可模拟具名可选参数，代码易读易写
  • 适用于参数多且多数可选的情况

Builder也适用于类层次结构，抽象类有抽象Builder，具体类有具体Builder。

第3条：用私有构造器或者枚举类型强化Singleton属性

Singleton是只被实例化一次的类。实现方式：

  1. 公有静态final成员：
  • 简单，但可通过反射调用私有构造器（需在构造器中防御）
  1. 公有静态工厂方法：
  • 灵活，可改为非Singleton而不修改API
  1. 单元素枚举类型（最佳方法）：
  • 无偿提供序列化机制，防止多次实例化
  • 防反射攻击
  • 简洁，是实现Singleton的最佳方法

第4条：通过私有构造器强化不可实例化的能力

工具类（只包含静态方法和静态域的类）不应被实例化。

  • 声明为抽象类不能阻止实例化（可被子类化后实例化）
  • 正确做法：提供私有构造器，在构造器中抛AssertionError（防止内部意外调用）
  • 副作用：类不能被子类化

第5条：优先考虑依赖注入来引用资源

不要用Singleton或静态工具类来引用底层资源，而应将资源传入构造器（依赖注入）。

  • 不当做法：SpellChecker内部new Dictionary()，无法替换字典
  • 正确做法：构造器接收Dictionary参数，可传入不同字典实现
  • 依赖注入使类更灵活、可测试、可复用
  • 资源工厂也可传入（如Supplier<Dictionary>）
  • 大型项目可使用依赖注入框架（Dagger、Guice、Spring），但不要过度使用

第6条：避免创建不必要的对象

重用对象比创建新对象更高效，尤其是不可变对象。

  • String s = new String("bikini") 会创建不必要的对象，应直接用String s = "bikini"
  • 静态初始化重用昂贵对象（如Pattern实例，不要在方法内每次编译）
  • 优先使用基本类型而非装箱基本类型（避免无意识的自动装箱）
  • 注意：不要过度使用对象池，除非对象创建确实昂贵（如数据库连接）

第7条：消除过期的对象引用

Java虽然有垃圾回收，但仍可能发生内存泄漏。

  • 常见来源：自己管理内存的类（如Stack），弹出元素后未清空引用
  • 解决：对象引用过期后手动置空（elements[size--] = null）
  • 其他内存泄漏来源：
    • 缓存：对象放入缓存后被遗忘（用WeakHashMap或定期清理）
    • 监听器和回调：注册后未取消注册（用弱引用）
  • 清空对象引用是例外，不是规范，让作用域结束自然回收即可

第8条：避免使用终结方法和清除方法

终结方法（finalizer）和Java 9的清除方法（cleaner）不可预测、危险、通常不必要。

  • 不保证及时执行，甚至不保证执行（JVM退出时可能不运行）
  • 性能开销大
  • 安全问题：finalizer攻击（子类finalizer中复活对象）
  • 正确做法：类实现AutoCloseable，用try-with-resources确保资源释放
  • 清除方法仅作为安全网（防止客户端忘记关闭资源），且应在独立线程中运行

第9条：try-with-resources优先于try-finally

传统try-finally关闭资源有问题：

  • 多个资源时代码冗长嵌套
  • try和finally中都可能抛异常，第二个异常会覆盖第一个（丢失原始异常信息）

try-with-resources（Java 7+）：

  • 资源实现AutoCloseable接口
  • 自动关闭资源，代码简洁
  • 被抑制的异常不会丢失，可通过getSuppressed()获取
  • 可同时管理多个资源，用分号分隔
  • 可配合catch子句使用

第3章 对于所有对象都通用的方法

第10条：覆盖equals时请遵守通用约定

不需要覆盖equals的情况：

  • 类的每个实例本质上都是唯一的（如Thread）
  • 不关心类是否提供”逻辑相等”测试
  • 超类已覆盖equals且行为适合子类
  • 类是私有的或包级私有的，确定不会调用equals

必须覆盖equals的情况：类有逻辑相等概念，且超类未覆盖equals（如值类、Integer、Date）。

equals约定：

  1. 自反性：x.equals(x)必须为true
  2. 对称性：x.equals(y)当且仅当y.equals(x)
  3. 传递性：若x.equals(y)且y.equals(z)，则x.equals(z)
  4. 一致性：多次调用结果一致
  5. 非空性：x.equals(null)必须为false

关键陷阱：无法在扩展可实例化类并增加新值组件的同时保留equals约定（如Point加color的ColorPoint）。解决：用组合代替继承，或用getClass()而非instanceof（但违反里氏替换原则）。

实现equals的诀窍：

  1. 用==检查是否为同一对象引用
  2. 用instanceof检查类型
  3. 转换为正确类型
  4. 比较每个关键字段（基本类型用==，float/double用compare，对象引用用equals，数组用Arrays.equals）
  5. 写完后问自己：是否对称、传递、一致？

第11条：覆盖equals时总要覆盖hashCode

每个覆盖equals的类都必须覆盖hashCode，否则违反hashCode约定：

  • 相等的对象必须有相等的哈希码
  • 不覆盖hashCode会导致类在HashMap、HashSet等基于散列的集合中行为异常

实现hashCode：

  • 用31作为乘数（奇素数，乘法可优化为移位减法）
  • Java 7+可用Objects.hash(field1, field2, ...)（但有性能开销）
  • 不可变类且hashCode频繁使用时，可缓存hashCode
  • 不要试图从hashCode中排除重要字段来提高性能

第12条：始终要覆盖toString

toString的约定：建议所有子类覆盖此方法，返回简洁但信息丰富的表示。

  • 好的toString使类更易于使用和调试
  • 应返回对象中包含的所有值得关注的信息
  • 是否指定格式取决于需求：
    • 值类（如PhoneNumber）应指定格式（文档化）
    • 不应指定格式的类，应保留灵活性
  • 无论是否指定格式，都应为toString返回的值中包含的信息提供访问方法（getter），否则程序员只能解析字符串

第13条：谨慎地覆盖clone

Cloneable接口的目的是作为对象的mixin接口，表明对象允许克隆，但它有缺陷：

  • 没有声明clone方法，Object的clone是protected的
  • 实现Cloneable后，需覆盖clone并改为public
  • clone方法的约定脆弱：创建并返回对象副本，x.clone() != x，x.clone().getClass() == x.getClass()，x.clone().equals(x)

实现clone的正确方式：

  • 调用super.clone()获取副本
  • 若域是基本类型或不可变对象引用，已完成
  • 若域引用可变对象，需递归克隆这些域（如数组、列表）
  • 不可变类永远不需要clone
  • 对于线程安全类，clone方法需同步

更好的替代方案：拷贝构造器或拷贝工厂（如new ArrayList<>(list)），比clone更安全、更简单，不依赖语言之外的机制，不要求遵守文档化的约定，不与final域冲突。

第14条：考虑实现Comparable接口

实现Comparable接口的类可以与集合框架和泛型算法协作（排序、搜索、最大值等）。

compareTo约定：

  • 自反性、对称性、传递性（与equals类似）
  • 强烈建议(x.compareTo(y)==0) == x.equals(y)（但非必需，如BigDecimal）

实现compareTo：

  • 从最关键的字段开始比较，若为0则比较下一个字段
  • 基本类型用compare方法（避免用<和>，有溢出风险）
  • 对象引用域递归调用compareTo
  • Java 8+可用Comparator.comparingInt等构造比较器
  • 不要在compareTo中依赖脆弱的关系（如hashCode）

第4章 类和接口

第15条：使类和成员的可访问性最小化

信息隐藏（封装）是软件设计的基本原则。

  • 尽可能降低每个类和成员的可访问性
  • 顶层类和接口：包级私有（package-private）优于公有（public）
  • 成员（域、方法、嵌套类）：
    • private：仅本类可访问
    • package-private：同包可访问
    • protected：同包+子类可访问
    • public：所有可访问
  • 公有类的实例域应尽量非public（见第16条）
  • 公有静态final域应是不可变的（基本类型或不可变对象引用）
  • 长度非零的数组永远是可变的，公有静态final数组域是安全漏洞（应返回不可变列表或数组克隆）

第16条：要在公有类而非公有域中使用访问方法

公有类不应暴露可变域。

  • 公有可变域使类无法强制执行约束（如范围检查）
  • 无法在域被修改时采取行动（如通知监听器）
  • 正确做法：私有域+公有访问方法（getter/setter）
  • 不可变域可以是公有的（公有final域），但仍建议用访问方法保持灵活性
  • 包级私有或私有顶层类暴露域危害较小

第17条：使可变性最小化

不可变类是实例不能被修改的类，所有信息在对象创建时固定。

  • Java平台库中的不可变类：String、基本类型包装类、BigInteger、BigDecimal

不可变类的规则：

  1. 不要提供修改对象状态的方法（mutator）
  2. 确保类不会被扩展（final类或私有构造器+静态工厂）
  3. 使所有域都是final
  4. 使所有域都是private
  5. 确保对任何可变组件的互斥访问（构造器、访问方法、readObject中防御性拷贝）

不可变类的优点：

  • 简单，状态不变
  • 线程安全，无需同步
  • 可自由共享（包括内部域）
  • 可作为缓存的键
  • 失败原子性（不会处于不一致状态）

缺点：

  • 每个不同的值都需要一个单独的对象，创建大对象开销大
  • 解决：提供配套的可变伙伴类（如StringBuilder）

第18条：复合优先于继承

继承是实现代码重用的强大方式，但不总是最佳工具。

  • 继承打破封装：子类依赖超类的实现细节，超类变化可能破坏子类
  • 方法调用在子类和超类间可能产生意外交互（如HashSet的addAll内部调用add，子类重写add后计数错误）
  • 即使超类API设计良好，继承也会带来不必要的脆弱性

复合（Composition）：

  • 在新类中包含私有域，引用现有类的实例
  • 现有类成为新类的组件
  • 新类的方法调用现有类实例的对应方法（转发，forwarding）
  • 新类不依赖现有类的实现细节
  • 适用于包装类（Wrapper Class），如Collections的checkedList、synchronizedList

继承仅适用于真正的子类型关系（is-a），且超类是为继承而设计的。否则用复合。

第19条：要么设计继承并提供文档说明，要么禁止继承

为继承而设计的类需要：

  • 文档化自用（self-use）的可覆盖方法：哪些方法调用了哪些可覆盖方法
  • 类必须通过其构造器调用可覆盖方法吗？（不应，因为超类构造器先于子类构造器运行，子类重写的方法会看到未初始化的域）
  • Cloneable和Serializable接口在为继承设计时更加困难（clone和readObject类似构造器，不能调用可覆盖方法）
  • 为继承设计的类应尽可能少的实现，尽可能多的文档化

禁止继承：

  • 类声明为final
  • 或构造器私有/包级私有，通过静态工厂创建实例
  • 对于不是为继承而安全设计的类，应禁止继承

第20条：接口优于抽象类

接口和抽象类都允许定义带实现的方法（Java 8+接口有默认方法），但接口更灵活。

接口的优势：

  • 现有类可以轻松实现新接口（只需添加方法，类层次不变）
  • 接口是定义mixin的理想选择（如Comparable、Iterable）
  • 接口允许构建非层次化的类型框架（类可实现多个接口）
  • 接口通过包装类模式提供安全的增强功能

接口与抽象类结合的骨架实现（Skeletal Implementation）：

  • 接口定义类型
  • 抽象类提供骨架实现（如AbstractCollection、AbstractSet、AbstractList）
  • 程序员可继承骨架实现，也可直接实现接口
  • 模拟多重继承

第21条：为后代设计接口

Java 8的默认方法使接口可以演化，但添加默认方法到现有接口有风险：

  • 默认方法可能注入到现有实现类中，与类的现有方法冲突或破坏不变式
  • 默认方法不能假设实现类的内部状态
  • 集合框架的removeIf默认方法在某些实现中导致问题（如同步集合）

设计接口时：

  • 尽可能在发布前测试接口（多个实现）
  • 默认方法应是通用的，不依赖特定实现
  • 即使有默认方法，也不是所有接口都能安全演化

第22条：接口只用于定义类型

接口应只用于定义类型，不应被滥用为常量接口。

  • 常量接口（Constant Interface）：只包含静态final常量，无方法
  • 类实现常量接口只是为了不用类名限定常量名
  • 问题：
    • 实现细节泄漏到API中
    • 误导用户（类实现接口暗示类是该类型）
    • 二进制兼容性问题（常量值编译进实现类）
  • 正确做法：常量放在不可实例化的工具类中，或用枚举类型

第23条：类层次优于标签类

标签类（Tagged Class）：用一个域（标签）表示对象的多种风格。

标签类的缺点：

  • 冗长、易错、效率低
  • 域不能是final（不同风格用不同域）
  • 无法在编译时检查类型安全
  • 添加新风格需修改所有方法，容易遗漏

类层次：

  • 抽象超类定义公共类型和方法
  • 每个具体子类表示一种风格
  • 每个子类只有需要的域，可为final
  • 编译时类型安全
  • 添加新风格只需添加新子类，不修改现有代码

第24条：静态成员类优于非静态成员类

嵌套类（Nested Class）有四种：

  1. 静态成员类：不持有外部类引用，可独立存在
  2. 非静态成员类（内部类）：持有外部类引用，可访问外部类实例成员
  3. 匿名类：无名称，在使用点声明和实例化
  4. 局部类：在方法中声明

非静态成员类的每个实例都持有外部类引用，增加内存和时间开销，可能导致外部类无法被GC。

  • 若嵌套类不需要访问外部类实例，应声明为static
  • 常见错误：声明非静态成员类但实际不需要外部类引用
  • 私有静态成员类常用于表示外部类的组件（如Map.Entry）
  • 匿名类常用于创建函数对象（Java 8前），现在优先用Lambda
  • 局部类用得最少，在需要命名类型且只在方法内使用时

第25条：限制源文件为单个顶级类

不要在一个源文件中放多个顶级类。

  • 可能导致编译顺序依赖，产生难以诊断的问题
  • 若多个顶级类必须在一起，考虑用静态成员类放入一个类中
  • 或将类放入不同源文件

第5章 泛型

第26条：请不要使用原生态类型

泛型（Generic）在编译时提供类型安全检查。

  • 原生态类型（Raw Type）：如List而非List<String>
  • 使用原生态类型会失去泛型的所有安全性和表达性优势
  • 错误会延迟到运行时（ClassCastException）而非编译时
  • List<Object>与原生态List不同：前者是参数化类型，编译器会检查；后者逃避检查
  • List<?>（无限制通配符）是安全的，可放入任何元素但不能添加（除null）

例外：

  • 必须在类字面量中使用原生态类型（List.class合法，List<String>.class不合法）
  • instanceof操作中必须用原生态类型（o instanceof Set），之后转换为通配符类型Set<?>

第27条：消除非受检的警告

非受检警告（Unchecked Warning）表示编译器无法保证类型安全。

  • 应尽可能消除所有非受检警告
  • 若无法消除，但能证明代码类型安全，用@SuppressWarnings("unchecked")注解抑制警告
  • 注解应放在尽可能小的作用域（局部变量声明优于方法）
  • 每次使用SuppressWarnings都应加注释说明为什么安全

第28条：列表优于数组

数组和泛型有重要区别：

  1. 数组是协变的（covariant）：Sub是Super的子类型，则Sub[]是Super[]的子类型。这会导致运行时异常（ArrayStoreException）。
  2. 泛型是不变的（invariant）：List<Sub>不是List<Super>的子类型，编译时就能发现错误。
  3. 数组是具体化的（reified）：运行时知道并检查元素类型。
  4. 泛型是通过擦除（erasure）实现的：运行时元素类型被擦除，只在编译时强化。

由于这些区别，数组和泛型不能很好地混合。

  • 不能创建泛型数组（new List<String>[]不合法）
  • 优先使用List<E>而非E[]
  • 泛型在编译时提供类型安全，数组在运行时才检查
  • 唯一需要数组的场景是性能（列表有包装开销），但通常不值得

第29条：优先考虑泛型

泛型类比需要客户端转换的类更安全、更易用。

  • 将类泛型化通常是值得的
  • 常见障碍：泛型数组创建不合法
    • 解决1：用Object[]存储，读取时强转（有警告但安全）
    • 解决2：用List<E>代替数组（类型安全但可能有性能差异）
  • 泛型类的类型参数通常用单个大写字母（E表示元素类型，K/V表示键/值，T表示类型）

第30条：优先考虑泛型方法

方法也可以泛型化，尤其是静态工具方法。

  • 泛型方法不需要像泛型类那样在创建实例时指定类型参数
  • 类型参数从方法参数推断
  • 泛型单例工厂：为不可变但适用于多种类型的对象创建泛型工厂（如Collections.reverseOrder）
  • 递归类型限制（Recursive Type Bound）：<T extends Comparable<T>>表示T可与自身比较

第31条：利用有限制通配符来提升API的灵活性

泛型是不变的，有时需要更灵活的类型。

  • PECS原则：Producer-Extends, Consumer-Super
    • 生产者（从集合读取）用? extends T
    • 消费者（向集合写入）用? super T
  • 示例：Stack<E>.pushAll(Iterable<? extends E> src)，popAll(Collection<? super E> dst)
  • 通配符使方法能接受更广泛的类型
  • 返回类型不要用通配符（会强制客户端处理通配符）
  • 比较器（Comparator）通常用? super T（消费者）
  • 若类型参数在方法声明中只出现一次，考虑用通配符替代

第32条：谨慎并用泛型和可变参数

泛型和可变参数（varargs）混合有问题：

  • 可变参数数组是泛型数组，编译器会创建Object[]
  • 向泛型可变参数数组存储值会导致堆污染（Heap Pollution）
  • @SafeVarargs注解可抑制警告，但必须确保方法安全

安全规则：

  • 不要让泛型可变参数数组对客户端可见（不要返回它）
  • 不要在泛型可变参数数组中存储值
  • 安全的用法：只从数组读取，或将数组传给另一个安全方法
  • 优先用List<E>代替可变参数（类型安全）
  • @SafeVarargs只能用于不能被重写的方法（static、final、private构造器）

第33条：优先考虑类型安全的异构容器

泛型的常见用法是集合（如List<E>），类型参数被限制为固定数量。

  • 异构容器（Heterogeneous Container）：键是泛型的，每个键可有不同的类型参数
  • 示例：类型安全的异构容器Favorites，用Class<T>作为键，存储任意类型的对象
  • Class.cast方法是动态的instanceof和转换
  • 限制：不能用不可具体化的类型（如List<String>.class不存在）
  • 用@SuppressWarnings处理必要的非受检警告

第6章 枚举和注解

第34条：用enum代替int常量

枚举类型是定义一组固定常量的最佳方式。

  • int枚举模式（public static final int APPLE_FUJI = 0）有缺陷：
    • 无类型安全，可传入任意int
    • 无命名空间，需前缀
    • 打印时只显示数字，无意义
    • 脆弱，int值编译进客户端，值变化需重新编译
  • Java枚举是完整的类，功能强大：
    • 编译时类型安全
    • 有命名空间
    • 可添加方法和域
    • 可实现接口
    • 可遍历（values()）
    • 每个枚举常量是单例
  • 枚举常量关联数据：构造器传入数据，用域存储
  • 枚举常量关联行为：用抽象方法，每个常量实现不同行为（策略枚举）

第35条：用实例域代替序数

所有枚举都有ordinal()方法返回常量在枚举中的位置。

  • 不要依赖ordinal()的值（如用它作为数组索引或计算值）
  • 问题：常量顺序变化会导致ordinal变化，破坏代码
  • 正确做法：用实例域存储值
  • ordinal()仅用于像EnumSet和EnumMap这样的通用数据结构，大多数程序员不需要使用它

第36条：用EnumSet代替位域

位域（Bit Field）用int的每一位表示一个选项：

缺点：

  • 类型不安全，int枚举模式的所有问题
  • 打印时是位模式，难以理解
  • 需手动遍历所有位

EnumSet：

  • 基于位域实现，性能相当
  • 类型安全，是Set的实现
  • 丰富的Set操作（removeAll、retainAll等）
  • 不可变？不，EnumSet是可变的（但可用Collections.unmodifiableSet包装）

第37条：用EnumMap代替序数索引

不要用ordinal()作为数组索引。

  • 问题：数组与枚举的对应关系脆弱，枚举变化需同步修改数组
  • 正确做法：用EnumMap
  • EnumMap内部用数组实现，性能与序数索引相当
  • 类型安全，键是枚举类型
  • 可嵌套使用（EnumMap的EnumMap）

第38条：用接口模拟可扩展的枚举

枚举类型不可扩展（不能继承另一个枚举），但有时需要可扩展的操作集合。

  • 用接口定义操作类型，枚举实现接口
  • 客户端可定义新枚举实现同一接口，扩展操作
  • 示例：Operation接口，BasicOperation枚举实现它，ExtendedOperation枚举扩展它
  • 限制：枚举实现不能互相继承（但可通过接口共享行为）
  • 用Class<? extends Operation>传递枚举类型，用getEnumConstants()获取所有常量

第39条：注解优先于命名模式

命名模式（Naming Pattern）用方法名约定表示特殊含义（如JUnit 3的testXxx方法）。
缺点：

  • 拼写错误不会报错（tsetXxx不会被识别）
  • 无法保证只用于正确的程序元素
  • 没有参数化能力

注解（Annotation）：

  • 编译时检查，拼写错误立即报错
  • 可限定适用的程序元素（@Target）
  • 可带参数
  • 示例：JUnit 4的@Test注解
  • 自定义注解：声明注解类型，用元注解（@Retention、@Target），编写注解处理器

第40条：坚持使用Override注解

在想要覆盖超类方法的方法声明上始终使用@Override注解。

  • 编译器会检查是否真的覆盖了方法
  • 防止因签名错误导致的”覆盖”变成”重载”（如参数类型错误）
  • 覆盖接口方法也应使用@Override（虽然不是必须，但保持一致）
  • 唯一例外：抽象方法覆盖（抽象方法覆盖抽象方法不需要，但用了也无害）

第41条：用标记接口定义类型

标记接口（Marker Interface）是不含方法声明的接口，仅用于标记类具有某种属性（如Serializable、Cloneable、RandomAccess）。

标记接口 vs 标记注解：

  • 标记接口的优势：
    • 定义类型，可在编译时检查（if (o instanceof Marker)）
    • 可被更精确地限定（接口只能被类实现，注解可用于任何元素）
  • 标记注解的优势：
    • 可带参数（更灵活）
    • 可在框架中统一处理（如JUnit的@Test）
  • 选择：
    • 若标记定义类型且需要编译时检查 → 标记接口
    • 若标记需要参数或只用于类/方法以外的元素 → 标记注解
    • 若标记用于框架且可能演化 → 标记注解

第7章 Lambda和Stream

第42条：Lambda优先于匿名类

Lambda表达式是创建函数对象的简洁方式，Java 8引入。

  • 匿名类冗长，Lambda简洁
  • Lambda的类型从上下文推断（目标类型）
  • Lambda参数类型通常可省略
  • 方法引用进一步简化（见第43条）
  • Lambda不能引用自身（this指向外部类），需要递归时用方法引用或匿名类
  • Lambda不应序列化（用匿名类或方法引用替代）

第43条：方法引用优先于Lambda

方法引用（Method Reference）是Lambda的更简洁形式。

  • 四种方法引用：
    • 静态方法：Integer::parseInt → x -> Integer.parseInt(x)
    • 实例方法（绑定接收者）：Instant.now()::isAfter → t -> Instant.now().isAfter(t)
    • 实例方法（未绑定接收者）：String::toLowerCase → s -> s.toLowerCase()
    • 构造器：TreeMap<K,V>::new → () -> new TreeMap<>()
  • 方法引用通常比Lambda更简洁、更清晰
  • 若Lambda比方法引用更短或更清晰，用Lambda（罕见）

第44条：坚持使用标准的函数接口

Java 8在java.util.function包中提供了43个标准函数接口。

  • 优先使用这些标准接口，而非自己定义
  • 六大基础接口：
    • UnaryOperator<T>：T→T
    • BinaryOperator<T>：(T,T)→T
    • Predicate<T>：T→boolean
    • Function<T,R>：T→R
    • Supplier<T>：→T
    • Consumer<T>：T→void
  • 基本类型变体：IntPredicate、LongFunction等（避免装箱）
  • 何时自定义函数接口：
    • 需要特殊命名（如Comparator<T>虽可被BiFunction替代，但命名有价值）
    • 有严格契约（如Comparator的契约）
    • 从自定义接口受益
  • 用@FunctionalInterface注解标记函数接口（防止意外添加抽象方法）

第45条：谨慎使用Stream

Stream API（Java 8）提供声明式数据处理，但不应过度使用。

  • Stream由源（集合、数组等）、中间操作（filter、map等）、终端操作（collect、forEach等）组成
  • 中间操作是惰性的，直到终端操作才执行
  • Stream的优势：简洁、声明式、可并行
  • 过度使用Stream的问题：
    • 代码难以阅读和维护
    • 某些操作在Stream中不自然（如需要跟踪多个中间值）
  • 经验法则：
    • 任务适合用Stream时用Stream（数据转换、过滤、聚合）
    • 不适合时用迭代（需要修改局部变量、复杂控制流）
    • 可以混合使用（Stream处理一部分，迭代处理另一部分）
  • 不要用Stream并行处理，除非有充分理由（见第48条）

第46条：优先选择Stream中无副作用的函数

Stream管道中的函数应是无副作用的（pure function）。

  • 不要在forEach中做有副作用的操作（如修改外部集合）
  • forEach应仅用于报告Stream计算结果，而非计算本身
  • 正确做法：用collect终端操作将结果收集到集合中
  • Collectors类提供丰富的收集器：
    • toList()、toSet()、toMap()
    • groupingBy()：分组
    • joining()：字符串连接
    • counting()、summingInt()、averagingDouble()
    • maxBy()、minBy()
    • partitioningBy()：分区
  • 收集器（Collector）是Stream的强大工具，应熟悉并使用

第47条：Stream要优先用Collection作为返回类型

编写返回多个元素的方法时，优先返回Collection（或其子类型），而非Stream。

  • Collection是Iterable，可用于for-each循环
  • Collection可转换为Stream（stream()）
  • Stream不能直接用于for-each（需先转换）
  • 返回Stream迫使调用者在需要迭代时做额外工作
  • 若返回的集合可能很大且内存是问题，可考虑返回Stream（但需文档化）
  • 标准库中Files.lines()返回Stream是因为文件可能很大
  • 对于大多数方法，返回合适的Collection（List、Set）是最佳选择

第48条：谨慎使用Stream并行

Stream的parallel()方法可使管道并行执行，但不总是提高性能。

  • 并行Stream在ForkJoinPool中执行
  • 并行的前提：
    • 数据源可高效拆分（ArrayList、数组、IntStream.range效果好；LinkedList、Stream.iterate效果差）
    • 终端操作可高效合并（reduce、collect效果好；forEach效果差）
    • 操作是无状态的、CPU密集的
  • 并行可能降低性能（线程管理开销、拆分开销）
  • 并行可能导致错误（有状态的lambda）
  • 并行仅在数据量大、操作耗时、CPU有空闲核心时才值得
  • 不要在生产代码中随意使用parallel，应先测量性能
  • 并行Stream使用公共ForkJoinPool，一个慢任务可能影响其他并行Stream

第8章 方法

第49条：检查参数的有效性

大多数方法和构造器对参数有约束。

  • 应在方法开头检查参数有效性，违反约束时抛出适当异常
  • 公有方法用Javadoc的@throws文档化异常
  • 常见异常：
    • NullPointerException：参数为null
    • IllegalArgumentException：参数值非法
    • IndexOutOfBoundsException：索引越界
    • IllegalStateException：对象状态不允许调用
  • Objects.requireNonNull检查非空（灵活简洁）
  • 非公有方法可用断言（assert）检查参数（断言可在运行时禁用）
  • 检查参数有效性不仅是为了错误检测，也是为了文档化方法约束
  • 有时参数有效性检查代价大，可在计算过程中自然检测（如排序时的比较）

第50条：必要时进行保护性拷贝

Java是安全的语言，但仍需主动防御以保护类的不变式。

  • 若方法接收可变对象参数，且方法需要存储该对象或其引用，应进行保护性拷贝
  • 否则客户端可在方法返回后修改对象，破坏类的不变式
  • 示例：Period类的构造器接收Date参数，应拷贝后存储
  • 访问方法也应返回可变域的拷贝（而非原始引用）
  • 保护性拷贝在参数检查之前进行（防止TOCTOU攻击：检查后、使用前被修改）
  • 对于不可变参数（如String、Integer），无需拷贝
  • 保护性拷贝有性能代价，仅在必要时使用

第51条：谨慎设计方法签名

好的方法签名应易于记忆和使用。

  • 方法名应符合命名惯例，可理解、自解释
  • 避免过长的参数列表（目标≤4个）
    • 若参数多，可拆分方法（每个方法处理部分参数）
    • 用辅助类（如Builder模式）封装参数
    • 用对象适配器（将参数组合为对象）
  • 参数类型优先用接口而非类（如Map而非HashMap）
  • 优先用基本类型而非装箱基本类型（避免NPE和性能开销）
  • 避免使用相同类型的多个连续参数（容易传反，编译时不报错）

第52条：慎用重载

重载（Overloading）方法的选择在编译时决定（静态分派），与重写（Override，运行时决定）不同。

  • 重载方法的选择基于参数的编译时类型，而非运行时类型
  • 这可能导致意外行为：
  • 安全的重载策略：
    • 避免多个重载方法有相同数量的参数
    • 若参数数量相同，确保参数类型有根本差异（不能互相转换）
    • 可使用不同方法名而非重载（如ObjectOutputStream的writeInt、writeLong等）
  • 构造器重载特别危险（无法用不同方法名），可用静态工厂替代

第53条：慎用可变参数

可变参数（varargs）方法接受0个或多个指定类型的参数。

  • 每次调用可变参数方法都会创建并初始化一个数组
  • 若性能关键且方法频繁调用，可重载固定参数数量的版本（如EnumSet.of有1到5个参数的重载，超过5个才用varargs）
  • 可变参数方法可接受0个参数，若至少需要1个参数，应声明1个固定参数+可变参数
  • 不要在可变参数方法中返回数组（可能暴露内部数组）
  • 泛型与可变参数混合有问题（见第32条）

第54条：返回零长度的数组或者集合，而不是null

返回null的方法迫使调用者在每次使用前检查null。

  • 零长度数组或集合是合法的返回值，表示”没有元素”
  • 返回null容易导致NPE（调用者忘记检查）
  • 零长度数组可重用（不可变的零长度数组是单例）
  • 集合返回Collections.emptyList()、emptySet()、emptyMap()
  • 不要为了”性能”返回null（零长度集合/数组开销极小）

第55条：谨慎返回Optional

Optional<T>表示可能缺失的返回值，是不可变的容器，可包含0或1个非null元素。

  • 无法返回结果时，返回Optional比返回null更安全（强迫调用者处理缺失情况）
  • 但Optional不应被滥用：
    • 容器类型（集合、映射、Stream、数组）不应包装在Optional中（返回空集合即可）
    • 基本类型不应使用Optional（用OptionalInt等，或直接返回默认值）
  • Optional的方法：
    • isPresent()：检查是否有值
    • get()：获取值（无值抛异常，应避免直接用）
    • orElse(default)：有值返回值，无值返回默认
    • orElseGet(supplier)：有值返回值，无值从supplier获取
    • orElseThrow(exceptionSupplier)：有值返回值，无值抛异常
    • ifPresent(consumer)：有值则执行consumer
    • map()、flatMap()、filter()：Stream-like操作
  • 永远不要返回null的Optional（应返回Optional.empty()）
  • Optional是为返回值设计的，不应作为域、参数或集合元素

第56条：为所有导出的API元素编写文档注释

API文档是API最重要的部分之一。

  • Javadoc工具从文档注释生成HTML文档
  • 应为每个导出的类、接口、方法、构造器、字段编写文档注释
  • 方法文档应描述：
    • 方法做什么（而非怎么做）
    • 前置条件（@param约束）
    • 后置条件
    • 副作用（如修改全局状态）
    • 参数说明（@param）
    • 返回值说明（@return）
    • 异常说明（@throws，包括未检查异常）
    • 线程安全性
    • 序列化形式
  • Javadoc标签：@param、@return、@throws、@see、@since、@serial、@deprecated
  • 文档注释应在代码之前，用/** ... */
  • 生成文档时用-Xdoclint:all检查问题
  • 文档注释应简洁、准确、可读

第9章 通用编程

第57条：将局部变量的作用域最小化

局部变量的作用域应尽可能小。

  • 在第一次使用变量的地方声明它
  • 几乎每个局部变量声明都应包含初始化器（若初始化依赖条件，用最小的if块）
  • 优先使用for循环而非while循环（for循环的循环变量作用域限制在循环内）
  • for-each循环优先于传统for循环（见第58条）
  • 方法小而聚焦（大方法中变量作用域自然更大）

第58条：for-each循环优先于传统的for循环

for-each循环（增强for循环）在Java 5引入，遍历集合和数组。

  • 优点：
    • 简洁，无索引变量和边界检查
    • 避免索引越界
    • 避免循环变量错误（如嵌套循环中用错索引）
    • 对任何Iterable都有效
  • 三种不能用for-each的情况：
    1. 需要删除元素（需用显式迭代器的remove方法，Java 8+可用removeIf）
    2. 需要替换元素（数组或列表，需索引）
    3. 需要并行遍历多个集合
  • for-each循环有微小性能开销，但通常可忽略

第59条：了解和使用类库

标准类库提供了大量经过测试、优化的功能。

  • 优先使用标准库而非自己实现
  • 优点：
    • 经过充分测试，bug少
    • 性能优化（专家实现）
    • 维护成本低
    • 代码可读性高（其他程序员熟悉）
  • 常见被忽视的类库：
    • java.util：集合框架
    • java.util.concurrent：并发工具
    • java.math：BigInteger、BigDecimal
    • java.util.regex：正则表达式
    • java.security：安全相关
  • 每个主要版本都应了解新类库功能
  • 不要重复造轮子

第60条：如果需要精确的答案，请避免使用float和double

float和double是二进制浮点类型，不适合精确计算（如货币）。

  • 0.1不能精确表示为二进制浮点数
  • 1.00 - 9 * 0.10结果不是0.10，而是0.09999999999999998
  • 解决方案：
    • BigDecimal：完全精确，但性能差、代码冗长
    • int或long：用最小单位计算（如货币用分而非元），性能好
  • float和double适用于科学计算、工程计算（近似值可接受）
  • 不要用==比较浮点数（用误差范围比较）

第61条：基本类型优先于装箱基本类型

基本类型（int、double等）和装箱基本类型（Integer、Double等）有重要区别：

  1. 基本类型只有值，装箱类型有身份（引用）
  2. 基本类型有功能完备的值，装箱类型有非功能值null
  3. 基本类型时间和空间效率更高

问题：

  • Integer的==比较身份而非值（两个值相同的Integer可能不相等）
  • 装箱类型为null时自动拆箱抛NPE
  • 自动装箱/拆箱有性能开销
  • 混合比较时，装箱类型被拆箱（可能NPE）

选择：

  • 优先用基本类型
  • 装箱类型用于：泛型类型参数（不能用基本类型）、需要null表示、反射
  • 不要用==比较装箱类型（用equals或先拆箱）

第62条：如果其他类型更适合，则尽量避免使用字符串

字符串被滥用的情况：

  • 用字符串表示枚举值（应用枚举类型，见第34条）
  • 用字符串表示聚合类型（应用类，如姓名+年龄+地址）
  • 用字符串表示能力（用接口或标记接口）
  • 用字符串编码数据（如用"key=value"字符串，应用Map或类）

字符串的问题：

  • 不灵活，难以操作
  • 性能差（字符串解析开销）
  • 容易出错（拼写错误、格式错误）
  • 无法编译时检查

只有当数据确实是文本时才用字符串。

第63条：了解字符串连接的性能

字符串连接操作符+是构建字符串的便捷方式，但不适合大规模使用。

  • 每次+操作创建新字符串，复制所有字符
  • n个字符串连接用+的时间复杂度是O(n²)
  • 大量连接时用StringBuilder（或StringBuffer，线程安全但慢）
  • 少量连接（如固定几个字符串）用+没问题（编译器会优化）
  • 不要在循环中用+=连接字符串
  • StringBuilder应指定初始容量（避免多次扩容）

第64条：通过接口引用对象

应使用接口类型而非实现类引用对象。

  • 优点：
    • 程序更灵活（可轻松替换实现，如ArrayList→LinkedList）
    • API更稳定（接口比实现更稳定）
  • 若需要实现类特有的方法（如ArrayList的ensureCapacity），可用实现类引用
  • 若没有合适的接口（如String、value class），用类引用
  • 框架基类（如AbstractList）比实现类好，但接口更好

第65条：接口优先于反射机制

反射（Reflection）允许程序在运行时访问类信息、调用方法、访问域。

  • 反射的代价：
    • 失去编译时类型检查（错误延迟到运行时）
    • 代码冗长笨拙
    • 性能开销（反射调用比直接调用慢）
  • 反射适用于：
    • 工具（如调试器、分析器、代码生成器）
    • 依赖注入框架（如Spring）
    • 序列化框架
  • 普通应用程序应避免反射
  • 若必须使用反射，用接口限制反射的使用范围：
    • 反射创建实例，用接口类型引用
    • 只在创建对象时用反射，调用方法用接口
  • 反射可能抛出运行时异常（ClassNotFoundException、NoSuchMethodException等），需处理

第66条：谨慎地使用本地方法

JNI（Java Native Interface）允许Java调用C/C++等本地方法。

  • 本地方法的用途：
    • 访问平台特定功能（如注册表）
    • 访问遗留C代码库
    • 性能关键部分（但现代JVM的JIT编译器通常足够快）
  • 本地方法的缺点：
    • 不安全（内存错误、缓冲区溢出）
    • 不可移植（需为每个平台编译）
    • 调试困难
    • 性能不一定更好（JNI调用有开销，JIT无法优化跨边界代码）
    • 增加构建复杂度
  • 除非必要，不要使用本地方法
  • 若使用，尽量减少本地代码量， thorough测试

第67条：谨慎地进行优化

优化有三条规则：

  1. 不要优化
  2. （仅对专家）不要优化，先确保正确
  3. 优化前先测量（profile）
  • 不成熟的优化是万恶之源
  • 优化可能引入bug、降低可读性、增加维护成本
  • 大多数性能问题来自算法和数据结构选择，而非代码微调
  • 优化前用profiler测量，找到瓶颈
  • 优化后再次测量，确认改进
  • 好的API设计比微优化更重要（好的API自然高效）
  • 考虑性能时关注大O复杂度，而非常数因子

第68条：遵守普遍接受的命名惯例

Java有完善的命名惯例，应遵守。

  • 类和接口：PascalCase（如Timer、FutureTask），缩写全大写（如HTTPURLConnection，现代风格HttpURLConnection）
  • 方法：camelCase（如remove、ensureCapacity），动词或动词短语
  • 域（字段）：
    • 非final实例域：camelCase（如width）
    • final静态常量：UPPER_SNAKE_CASE（如MAX_VALUE）
    • 其他静态域：camelCase
  • 局部变量：camelCase，可缩写（如i、j、buf）
  • 包：全小写，点分隔（如com.google.common.collect），不用下划线
  • 类型参数：单个大写字母（如T、E、K、V、R、X、T1、T2）
  • 命名应传达含义，避免无意义名称（如a、b，除非循环变量）
  • 遵守惯例使代码更易读、更易维护

第10章 异常

第69条：只针对异常的情况才使用异常

异常不应用于正常控制流。

  • 异常的设计目的是处理异常情况
  • 用异常控制流的问题：
    • 代码意图不清晰
    • 性能差（JVM不会优化异常路径）
    • 可能掩盖真正的bug（异常被catch后忽略）
  • 示例：不要用try { while(true) iterator.next(); } catch(NoSuchElementException e) {}遍历迭代器，应用hasNext()检查
  • 正确做法：用状态检查方法（hasNext()、isClosed()）或返回Optional/特殊值表示可预期的结果

第70条：对可恢复的情况使用受检异常，对编程错误使用运行时异常

Java有三种可抛出结构：受检异常、运行时异常、错误。

  • 受检异常（Checked Exception）：编译器要求处理（catch或声明throws）
    • 用于可恢复的情况（如文件不存在、网络中断）
    • 调用者可合理地恢复
    • 每个受检异常都应提供恢复所需的信息（如getter方法）
  • 运行时异常（RuntimeException）：未受检，不要求处理
    • 用于编程错误（如数组越界、空指针、非法参数）
    • 通常是不可恢复的（修复代码bug）
    • 所有未受检异常应继承RuntimeException
  • 错误（Error）：未受检，用于JVM资源不足、不变式失败等
    • 程序通常无法恢复，不应catch
    • 所有Error应继承Error
  • 不要定义不是受检异常、运行时异常、错误的Throwable子类

第71条：避免不必要地使用受检异常

受检异常迫使调用者处理异常，增加代码复杂度。

  • 若调用者无法合理恢复，用运行时异常
  • 若方法可通过状态检查避免异常，提供状态检查方法（如Iterator.hasNext()）
  • 若无法避免且可恢复，用受检异常
  • 受检异常使API更难使用（尤其是Lambda和Stream中）
  • 可用Optional返回值替代”无结果”的受检异常

第72条：优先使用标准的异常

重用标准异常使API更易学习和使用。

  • 常用标准异常：
    • IllegalArgumentException：参数值非法
    • IllegalStateException：对象状态不允许操作
    • NullPointerException：参数为null（用Objects.requireNonNull）
    • IndexOutOfBoundsException：索引越界
    • ConcurrentModificationException：并发修改检测
    • UnsupportedOperationException：不支持的操作
    • ArithmeticException：算术错误
    • NumberFormatException：数字格式错误
  • 不要重复发明异常类型
  • 选择最贴切的异常（如参数非法用IllegalArgumentException而非通用Exception）
  • 可继承标准异常添加域（但通常不需要）

第73条：抛出与抽象相对应的异常

方法抛出的异常应与方法的抽象层次一致。

  • 低层异常不应直接泄漏到高层（如SQLException从业务方法抛出）
  • 异常转译（Exception Translation）：捕获低层异常，抛出对应高层抽象的异常
  • 异常链（Exception Chaining）：将原始异常作为cause传入新异常（new HigherLevelException(cause)），保留原始信息
  • 并非所有异常都需转译（若低层异常恰好适合高层抽象，可直接传播）
  • 转译不应过度（不要每层都转译）

第74条：每个方法抛出的所有异常都要有文档

文档化异常是API文档的重要部分。

  • 用Javadoc的@throws标签文档化每个受检异常
  • 未受检异常也应文档化（虽然编译器不要求）
  • 文档应说明：
    • 什么情况下抛出异常
    • 异常的含义
    • 如何恢复（若可恢复）
  • 接口方法的异常文档应适用于所有实现
  • 不要在文档中列出”可能抛出”的异常（应精确）
  • 用@throws而非@exception（后者已过时）

第75条：在细节消息中包含能捕获失败的信息

异常的详细消息（detail message）应包含足够信息诊断失败。

  • 应包含：
    • 失败相关的参数值
    • 失败相关的对象状态
    • 失败的原因
  • 示例：IndexOutOfBoundsException应包含下界、上界、索引值
  • 不要在详细消息中包含敏感信息（密码、密钥等）
  • 详细消息是给程序员看的（诊断用），不是给用户看的
  • 为异常提供getter方法获取失败信息（而非仅依赖字符串消息）

第76条：努力使失败保持原子性

失败的方法调用应使对象保持在调用前的状态（失败原子性）。

  • 实现方式：
    1. 不可变对象（天然失败原子性）
    2. 在修改对象前检查参数有效性（先验证后修改）
    3. 调整操作顺序，使可能失败的部分在修改对象之前
    4. 在对象的临时拷贝上操作，成功后替换原对象
    5. 编写恢复代码，回滚到之前状态（复杂，少用）
  • 并非所有方法都能保证失败原子性（如并发修改、I/O操作）
  • 若无法保证，应文档化失败后对象的状态

第77条：不要忽略异常

空catch块（忽略异常）是危险的。

  • 忽略异常可能导致：
    • 程序在错误状态下继续运行
    • 难以诊断的bug
    • 数据损坏
  • 至少应：
    • 记录异常（用日志框架）
    • 重新抛出（让上层处理）
    • 转换为更合适的异常
  • 若确实可以忽略异常（如关闭资源时的异常），应加注释说明原因，并将异常变量命名为ignored
  • 空catch块是代码审查的重点

第11章 并发

第78条：同步访问共享的可变数据

synchronized关键字确保同一时刻只有一个线程执行方法或代码块。

  • 同步不仅是互斥，也是内存可见性（Java内存模型）
  • 若没有同步，一个线程的修改可能对其他线程不可见（由于寄存器、缓存、指令重排序）
  • 共享可变数据必须同步访问
  • 不可变数据不需要同步
  • 尽量避免共享可变数据（线程限制、不可变对象、并发数据结构）
  • volatile关键字保证可见性但不保证原子性（适合状态标志位，不适合计数器）
  • 长整型long和double的读写不是原子的（除非volatile）
  • 优先使用java.util.concurrent中的并发工具（原子类、并发集合、同步器）

第79条：避免过度同步

过度同步会导致性能问题、死锁、活性失败。

  • 同步方法或块中不要调用外来方法（可被重写的方法、客户端传入的方法）
    • 外来方法可能获取其他锁（死锁）
    • 外来方法可能耗时过长（性能问题）
    • 外来方法可能修改对象状态（破坏不变式）
  • 应将外来方法移到同步块之外（先在同步块中获取数据，再在同步块外调用方法）
  • 同步块应尽可能短（只保护需要保护的操作）
  • 不要在同步块中做耗时操作（I/O、等待）
  • 对于活跃的并发数据结构，用内部细粒度同步而非外部粗粒度同步

第80条：executor、task和stream优先于线程

java.util.concurrent.Executor框架是管理线程的标准方式。

  • 不要直接创建和管理线程（new Thread(r).start()）
  • 用ExecutorService：
  • 线程池的优势：
    • 复用线程（避免创建销毁开销）
    • 控制并发数
    • 任务队列
    • 统计和监控
  • 选择线程池：
    • newFixedThreadPool：固定线程数
    • newCachedThreadPool：弹性线程数（适合短任务）
    • newSingleThreadExecutor：单线程（保证顺序）
    • newScheduledThreadPool：定时任务
  • 对于大程序，用自定义ThreadPoolExecutor（控制核心线程数、最大线程数、队列、拒绝策略）
  • ForkJoinPool用于并行Stream和分治任务
  • 不要用Timer（用ScheduledThreadPoolExecutor替代，Timer有线程泄漏和异常处理问题）

第81条：并发工具优先于wait和notify

java.util.concurrent提供高级并发工具，优于底层的wait/notify。

  • 并发工具分类：
    1. 执行器框架（Executor）：见第80条
    2. 并发集合：ConcurrentHashMap、ConcurrentLinkedQueue、BlockingQueue等
    3. 同步器：CountDownLatch、Semaphore、CyclicBarrier、Exchanger、Phaser
  • 并发集合内部已同步，性能优于外部同步的集合
    • ConcurrentHashMap：高并发哈希表
    • CopyOnWriteArrayList：读多写少场景
    • BlockingQueue：生产者-消费者模式
  • 同步器用于线程间协调：
    • CountDownLatch：一个或多个线程等待其他线程完成
    • Semaphore：限制并发数
    • CyclicBarrier：多个线程互相等待到达屏障
  • wait/notify是底层机制，难以正确使用（易丢失信号、虚假唤醒）
  • 若必须用wait/notify，用while循环检查条件（而非if），在同步块中调用

第82条：线程安全性的文档化

线程安全性是API承诺的一部分，应文档化。

  • 线程安全性级别：
    1. 不可变：类实例不可变，无需外部同步（如String、Long）
    2. 无条件线程安全：类实例可变，但内部有足够同步，可自由使用（如AtomicLong、ConcurrentHashMap）
    3. 有条件线程安全：某些方法组合需要外部同步（如Collections.synchronized集合的迭代）
    4. 非线程安全：类实例可变，使用时需外部同步（如ArrayList、HashMap）
    5. 线程对立：即使外部同步也不安全（罕见，如Thread.stop）
  • 应在类的Javadoc中说明线程安全性级别
  • 有条件线程安全应说明哪些方法组合需要同步、用什么锁
  • 不要在文档中说”线程安全”而不说明含义
  • 私有锁对象（private final Object lock = new Object()）可防止客户端代码干扰同步

第83条：慎用延迟初始化

延迟初始化（Lazy Initialization）是在第一次需要时才初始化域。

  • 目的：
    • 避免不必要的初始化开销（若域从不使用）
    • 打破初始化循环
  • 代价：
    • 代码复杂
    • 可能引入线程安全问题
    • 访问延迟初始化域有性能开销
  • 大多数情况下，正常初始化（声明时初始化）优于延迟初始化
  • 若需要延迟初始化：
    • 单线程环境：简单检查即可
    • 多线程环境：
      • 静态域：用holder class模式（初始化器类）
      • 实例域：用双重检查锁定模式（double-check locking）
  • 不要用延迟初始化作为性能优化的借口（先测量确认需要）

第84条：不要依赖于线程调度器

线程调度器决定哪些线程运行、运行多久。

  • 程序正确性不应依赖线程调度器的具体行为
  • Thread.yield()和线程优先级是高度不可移植的
  • 不要用Thread.yield()或线程优先级”修复”并发问题
  • 若程序某些线程无法获得CPU时间，应减少线程数或用Executor控制并发
  • 线程优先级可用于改善服务质量（如后台线程低优先级），但不应依赖它保证正确性
  • 忙等待（busy-waiting）是糟糕的实践（浪费CPU，依赖调度器），用wait/notify或并发工具替代

第12章 序列化

第85条：Java序列化优先考虑其他方式

Java序列化（Serialization）是危险的，应优先考虑其他方式。

  • Java序列化的问题：
    • 攻击面大（反序列化漏洞可导致远程代码执行）
    • 复杂且难以正确实现
    • 性能差
    • 不跨语言
  • 替代方案：
    • JSON（Jackson、Gson）：文本格式，跨语言，人类可读
    • Protocol Buffers（protobuf）：二进制格式，跨语言，高效，有schema
    • Apache Avro：二进制格式，schema演化
    • XML：冗长但成熟
  • 这些格式不支持引用共享和循环引用，但通常不需要
  • 若必须使用Java序列化（如遗留系统），严格遵循后续条目

第86条：谨慎地实现Serializable

实现Serializable接口有代价，应谨慎。

  • 实现Serializable的代价：
    • 降低类改变的灵活性（序列化形式成为API的一部分）
    • 增加bug和安全漏洞的可能性
    • 增加测试负担
    • 内部表示泄漏（私有域也被序列化）
  • 为继承而设计的类应尽量不实现Serializable（除非必要）
  • 内部类不应实现Serializable（编译器生成的字段不稳定）
  • 若类可序列化，需认真设计序列化形式
  • 考虑自定义序列化形式（writeObject/readObject）而非默认形式

第87条：考虑使用自定义的序列化形式

默认序列化形式编码对象的物理表示（所有非transient域），可能不适合。

  • 选择序列化形式的原则：
    • 应编码对象的逻辑内容，而非物理表示
    • 应尽量独立于类的实现
  • 若默认形式合理（域表示逻辑状态，无循环引用），可用默认形式
  • 若默认形式不合理（如表示链表、树、稀疏数组），应自定义形式
  • 自定义序列化：
    • 声明非逻辑域为transient
    • 实现writeObject和readObject
    • writeObject先调用defaultWriteObject（若有非transient域），再写自定义数据
    • readObject先调用defaultReadObject，再读自定义数据
  • 序列化形式应文档化（用@serial、@serialField、@serialData标签）

第88条：保护性地编写readObject方法

readObject方法相当于一个”隐式构造器”，必须像构造器一样检查参数有效性。

  • 反序列化时，readObject接收字节流，可能是恶意构造的
  • readObject必须：
    1. 检查参数有效性（对象不变式）
    2. 进行保护性拷贝（可变域）
    3. 不要调用可被重写的方法
  • 反序列化的对象可能处于非法状态，必须验证
  • 对于引用其他对象的域，反序列化后可能被篡改（攻击者可修改字节流中的引用）
  • 解决方案：反序列化后检查引用是否指向预期类型，或用保护性拷贝重建对象
  • 若类有安全敏感的不变式，用readResolve或序列化代理模式

第89条：对于实例控制，枚举类型优先于readResolve

readResolve方法允许替换反序列化的对象，用于实例控制（如Singleton）。

  • 若Singleton实现Serializable，反序列化会创建新实例（破坏Singleton）
  • readResolve返回替换对象（如INSTANCE），反序列化的对象被丢弃
  • 但readResolve有问题：
    • 若域是对象引用类型，攻击者可在readResolve之前窃取引用
    • 需将所有域声明为transient（否则攻击面大）
  • 更好的方式：用单元素枚举实现Singleton（见第3条）
    • 枚举无偿提供序列化保护
    • 防反射攻击
    • 简洁
  • 若不能用枚举（如必须继承其他类），用readResolve并确保所有域为transient或基本类型

第90条：考虑用序列化代理代替序列化实例

序列化代理模式（Serialization Proxy Pattern）是实现安全序列化的最佳方式。

  • 思路：
    1. 定义私有静态嵌套类作为序列化代理（包含外部类的逻辑状态）
    2. 外部类的writeObject抛出异常（防止直接序列化），或用writeReplace返回代理
    3. 代理的writeObject序列化代理状态
    4. 代理的readResolve重建外部类实例
  • 优点：
    • 外部类的不变式在readResolve中通过构造器检查（自动验证）
    • 不受字节流篡改影响（代理只包含逻辑状态）
    • 不需要readObject的复杂检查
    • 可反序列化为不同实现类
  • 缺点：
    • 代码略多
    • 有微小性能开销
  • 序列化代理模式是实现Serializable的最安全方式，应优先考虑

《Effective Java》是Java领域最经典的最佳实践书籍，由Joshua Bloch（Java集合框架、java.math包的设计者）撰写。第3版覆盖Java 7、8、9的新特性。

章节 主题 核心内容

  • 本书不是通读型书籍，而是参考型书籍，可按主题查阅
  • 每条规则都有代码示例和反例，建议动手实践
  • 第2-4章是基础，所有Java开发者都应掌握

  • 代码审查时可将本书规则作为检查清单

这本书适合所有Java开发者，从初学者到资深工程师都能从中受益，是Java领域必读的经典之作。
