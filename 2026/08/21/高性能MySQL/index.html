高性能MySQL

高性能MySQL（第4版）

作者：Jeremy Tinley, Silvia Botros
全书共约14章，281页，MySQL性能优化的经典著作，涵盖MySQL架构、监控、Performance Schema、硬件优化、服务器配置、Schema设计、查询优化、索引优化、复制、高可用等核心主题。

第1章 MySQL架构

MySQL的逻辑架构

MySQL采用分层架构：

  1. 连接管理与安全性：

    • 每个客户端连接在服务器进程中拥有一个线程
    • 连接的查询只在一个线程中运行
    • 线程由线程池缓存，无需为每个连接创建销毁线程
    • 连接时进行身份认证（用户名、密码、主机IP）
    • 认证成功后，服务器验证该客户端是否有执行特定查询的权限

  2. 优化与执行：

    • 解析器：解析SQL，生成解析树
    • 预处理器：检查解析树合法性（表、列是否存在，名称解析）
    • 查询优化器：将解析树转化为执行计划
    • 查询执行引擎：根据执行计划执行查询
    • 存储引擎接口：执行引擎通过存储引擎API与存储引擎交互

并发控制

读写锁：

  • 读锁（共享锁）：多个读操作可同时持有，不阻塞其他读
  • 写锁（排他锁）：写锁排他，阻塞其他读和写
  • 锁粒度：表锁、页锁、行锁

锁的粒度：

  • 表锁：锁定整个表，开销小，并发度低
  • 行锁：锁定单行，开销大，并发度高
  • MySQL服务器层实现表锁，存储引擎实现行锁（如InnoDB）

事务

ACID特性：

  • 原子性（Atomicity）：事务中操作要么全部成功，要么全部回滚
  • 一致性（Consistency）：数据库从一个一致性状态转换到另一个一致性状态
  • 隔离性（Isolation）：一个事务的修改在提交前对其他事务不可见
  • 持久性（Durability）：事务提交后修改永久保存

隔离级别：

  1. READ UNCOMMITTED（读未提交）：可读取未提交数据，脏读
  2. READ COMMITTED（读已提交）：只能读取已提交数据，不可重复读
  3. REPEATABLE READ（可重复读）：同一事务内多次读取结果一致，MySQL默认级别，InnoDB通过MVCC解决幻读
  4. SERIALIZABLE（串行化）：最高隔离级别，强制事务串行执行

死锁：

  • 两个或多个事务互相等待对方释放锁
  • InnoDB自动检测死锁，回滚代价最小的事务
  • 死锁原因：事务以不同顺序访问资源
  • 避免：以固定顺序访问资源、缩短事务、使用更低隔离级别

事务日志：

  • 预写式日志（WAL）：修改先写日志，再写数据页
  • redo log：记录数据页修改，崩溃恢复
  • undo log：记录修改前版本，用于回滚和MVCC
  • 事务日志顺序写，比随机写数据页快

MySQL中的事务：

  • InnoDB支持事务，MyISAM不支持
  • 自动提交（AUTOCOMMIT）：默认开启，每条SQL自动提交
  • 隐式锁：InnoDB在事务执行时自动加锁
  • 显式锁：SELECT … FOR UPDATE / LOCK IN SHARE MODE

多版本并发控制（MVCC）

  • InnoDB通过MVCC实现非锁定一致性读
  • 每行数据有两个隐藏列：创建版本号、删除版本号
  • 事务开始时获取系统版本号
  • SELECT：只查找创建版本号≤当前事务版本号，且删除版本号>当前事务版本号（或未删除）的行
  • INSERT：创建版本号设为当前事务版本号
  • UPDATE：标记旧行删除（删除版本号=当前版本号），插入新行（创建版本号=当前版本号）
  • DELETE：删除版本号设为当前事务版本号
  • MVCC只在REPEATABLE READ和READ COMMITTED级别工作

复制

  • MySQL复制基于binlog（二进制日志）
  • 主库将修改写入binlog，从库读取并重放
  • 复制模式：
    • 语句级复制（SBR）：复制SQL语句
    • 行级复制（RBR）：复制行变更
    • 混合模式（MBR）：自动选择
  • 复制用途：备份、读扩展、高可用、数据分析

数据文件结构

  • InnoDB使用表空间（tablespace）管理数据
  • 系统表空间（ibdata1）：数据字典、undo log、insert buffer等
  • 独立表空间（file-per-table）：每个表一个.ibd文件
  • redo log：ib_logfile0、ib_logfile1，循环写
  • binlog：二进制日志文件，记录修改

InnoDB引擎

InnoDB是MySQL默认存储引擎，特点：

  • 支持事务、行锁、MVCC
  • 聚簇索引（主键索引即数据）
  • 自适应哈希索引
  • 插入缓冲（Insert Buffer）
  • 两次写（Double Write）
  • 崩溃恢复

JSON文档支持：

  • MySQL 5.7+支持JSON类型
  • 原生JSON存储，支持索引和函数操作
  • JSON_EXTRACT、JSON_SET、JSON_ARRAY等函数

数据字典的变化：

  • MySQL 8.0引入全局数据字典（Data Dictionary）
  • 取代之前的.frm文件
  • 数据字典存储在InnoDB表中，支持事务
  • 原子DDL：DDL操作要么全部成功要么全部回滚

原子DDL：

  • MySQL 8.0支持原子DDL
  • DDL操作（CREATE、ALTER、DROP）具有原子性
  • 数据字典更新、存储引擎操作、binlog写入在一个事务中
  • 崩溃后不会出现部分完成的DDL

第2章 可靠性工程世界中的监控

可靠性工程对DBA团队的影响

  • SRE（站点可靠性工程）理念影响数据库运维
  • 关注服务水平目标（SLO）而非单纯性能指标
  • 监控从”收集指标”转向”度量用户体验”
  • 自动化运维减少人工干预

定义服务水平目标

怎样才能让客户满意：

  • 从用户视角定义可靠性
  • 可用性：服务可正常访问的时间比例
  • 延迟：请求响应时间
  • 错误率：请求失败比例

用什么来度量

定义SLI和SLO：

  • SLI（服务水平指标）：可量化的服务质量度量（如请求延迟、错误率）
  • SLO（服务水平目标）：SLI的目标值（如99.9%请求延迟<200ms）
  • SLA（服务水平协议）：与客户的合同约定，违反有惩罚

监控解决方案：

  • Prometheus + Grafana：主流监控栈
  • 采集指标、存储、可视化、告警
  • MySQL Exporter采集MySQL指标

监控可用性：

  • 服务是否可访问
  • 连接数、线程数
  • 主从复制状态

监控查询延迟：

  • 查询响应时间分布（P50/P95/P99）
  • 慢查询日志
  • Performance Schema的语句统计

监控报错：

  • 错误率、错误类型
  • 连接错误、查询错误
  • 死锁、锁等待

主动监控：

  • 定期执行探测查询
  • 模拟用户请求
  • 提前发现问题

度量长期性能

了解业务节奏：

  • 业务有周期性（日/周/月）
  • 基线对比：与同时期历史数据对比
  • 容量规划：基于增长趋势预测

有效地跟踪指标：

  • 指标降采样：长期存储用降采样数据
  • 异常检测：自动识别异常指标
  • 关联分析：多指标关联定位问题

使用监控工具检查性能：

  • 仪表盘：关键指标可视化
  • 告警：阈值告警、异常告警
  • 根因分析：从告警到根因

使用SLO来指导整体架构：

  • SLO驱动架构决策
  • 错误预算：SLO未用完时可发布/变更，用完时冻结变更
  • 容量规划基于SLO需求

第3章 Performance Schema

Performance Schema介绍

Performance Schema是MySQL内置的性能监控工具，用于监控MySQL服务器执行时的资源消耗和等待事件。

插桩元件：

  • 等待事件（wait）：互斥锁、读写锁、条件变量、文件I/O、表I/O、socket I/O
  • 阶段事件（stage）：SQL执行阶段（如排序、发送数据）
  • 语句事件（statement）：SQL语句执行统计
  • 事务事件（transaction）：事务统计
  • 内存事件（memory）：内存分配统计

消费者表的组织：

  • current表：当前事件
  • history表：最近事件（每个线程10条）
  • history_long表：更多历史事件（每个线程10000条）
  • 汇总表：按维度汇总（按线程、按用户、按主机、按账号、按语句等）

资源消耗：

  • Performance Schema有性能开销
  • 可通过配置启用/禁用特定插桩和消费者
  • 按需启用，减少开销

局限性：

  • 不监控所有MySQL操作
  • 部分事件粒度有限
  • 历史表数据可能丢失（环形缓冲区）

sys Schema：

  • 基于Performance Schema的视图和存储过程集合
  • 提供更友好的查询接口
  • 常用视图：
    • sys.session：当前会话
    • sys.statement_analysis：语句分析
    • sys.innodb_buffer_stats_by_table：InnoDB缓冲池统计
    • sys.schema_unused_indexes：未使用索引
    • sys.schema_redundant_indexes：冗余索引

理解线程：

  • MySQL内部线程类型：连接线程、后台线程
  • Performance Schema按线程统计事件
  • threads表：所有线程信息

配置

启用或禁用Performance Schema：

  • performance_schema=ON/OFF（启动参数）
  • 运行时不可更改

启用或禁用插桩：

  • setup_instruments表：配置插桩启用状态
  • UPDATE setup_instruments SET ENABLED='YES', TIMED='YES' WHERE NAME LIKE '%';
  • 可按名称模式启用（如wait/io/file/%）

启用或禁用消费者表：

  • setup_consumers表：配置消费者启用状态
  • 消费者层次：global_instrumentation → thread_instrumentation → events_waits_current → events_waits_history → events_waits_history_long
  • 上层禁用则下层不工作

优化特定对象的监控：

  • setup_objects表：配置监控哪些对象（表、存储过程等）
  • 可排除系统表或不关心的表

优化线程的监控：

  • setup_threads表：配置监控哪些线程
  • 可只监控前台线程（连接线程），忽略后台线程

调整Performance Schema的内存大小：

  • 各种缓冲区大小可配置
  • performance_schema_events_waits_history_size
  • performance_schema_events_waits_history_long_size
  • 内存预分配，运行时不可更改

默认值：

  • MySQL 8.0默认启用大部分插桩和消费者
  • 开销可控，生产环境可使用

使用Performance Schema

检查SQL语句：

  • events_statements_summary_by_digest：按语句摘要统计
  • 字段：SCHEMA_NAME、DIGEST、DIGEST_TEXT、COUNT_STAR、SUM_TIMER_WAIT、SUM_ROWS_EXAMINED等
  • 找出执行次数多、耗时长、扫描行多的语句

检查读写性能：

  • table_io_waits_summary_by_table：表I/O统计
  • file_summary_by_instance：文件I/O统计
  • 找出I/O热点表和文件

检查元数据锁：

  • metadata_locks表：当前元数据锁
  • 找出DDL阻塞、锁等待

检查内存使用情况：

  • memory_summary_global_by_event_name：按事件统计内存
  • memory_summary_by_thread_by_event_name：按线程统计
  • 找出内存泄漏或大内存消耗

检查变量：

  • global_variables、session_variables：系统变量
  • user_variables_by_thread：用户变量
  • status_by_thread：状态变量

检查最常见的错误：

  • events_errors_summary_global_by_error：按错误统计
  • 找出高频错误

检查Performance Schema自身：

  • performance_timers：可用计时器
  • setup_timers：当前计时器配置
  • host_cache：主机缓存

第4章 操作系统和硬件优化

什么限制了MySQL的性能

  • CPU：计算密集型查询、排序、聚合
  • 内存：缓冲池大小、缓存命中率
  • 磁盘I/O：随机读写、吞吐量、延迟
  • 网络：带宽、延迟、连接数
  • 找出瓶颈：CPU高？I/O等待高？内存不足？

如何为MySQL选择CPU

  • CPU主频影响单查询性能（MySQL单查询单线程）
  • CPU核心数影响并发能力
  • 选择高主频+多核平衡
  • CPU缓存大小影响性能
  • 避免过度超线程（MySQL对超线程利用有限）

平衡内存和磁盘资源

缓存、读取和写入：

  • 内存越大，缓冲池越大，缓存命中率越高，磁盘I/O越少
  • InnoDB缓冲池应占可用内存的50%-70%
  • 读多写少场景：大内存减少读I/O
  • 写密集场景：内存缓存写，合并写减少I/O

你的工作集是什么：

  • 工作集：频繁访问的数据量
  • 若工作集可放入内存，性能最佳
  • 若工作集远大于内存，需依赖磁盘，性能受限
  • 估算工作集：热点数据量、访问频率

固态存储

闪存概述：

  • SSD（固态硬盘）：基于NAND闪存
  • 相比机械硬盘：随机读写快、延迟低、抗震、功耗低
  • 类型：SLC（单层，寿命长成本高）、MLC（多层）、TLC（三层，成本低寿命短）、QLC（四层）
  • NVMe：PCIe接口SSD，比SATA SSD更快

垃圾收集：

  • SSD写入前需擦除块（block），擦除粒度大
  • 垃圾收集（GC）：整理有效页，擦除空闲块
  • GC在后台运行，可能影响性能（写放大）
  • 预留空间（OP）：SSD保留部分空间用于GC，提高性能和寿命
  • TRIM：操作系统通知SSD哪些页可擦除，提高GC效率

RAID性能优化

RAID故障、恢复和监控：

  • RAID提供冗余和性能
  • RAID级别选择：
    • RAID 0：条带化，性能高，无冗余
    • RAID 1：镜像，冗余好，写性能一般
    • RAID 5：分布式奇偶校验，读好，写有奇偶计算开销
    • RAID 6：双奇偶，可容忍两块故障
    • RAID 10：镜像+条带，性能好，冗余好，成本高
  • MySQL推荐RAID 10（性能和冗余平衡）
  • 监控RAID状态、磁盘健康、重建进度

RAID配置和缓存：

  • RAID控制器缓存：读缓存、写缓存
  • 写回缓存（Write-back）：先写缓存再写磁盘，性能好，但断电可能丢数据（需电池保护BBU/闪存）
  • 写透缓存（Write-through）：直接写磁盘，安全但慢
  • 启用电池保护的写回缓存可显著提升写性能

网络配置

  • 网络带宽：大结果集、复制、备份需要高带宽
  • 网络延迟：分布式查询、远程连接受延迟影响
  • TCP参数调整：缓冲区大小、连接队列
  • 网络中断聚合：减少中断开销
  • 绑定（Bonding）：多网卡聚合，提高带宽和冗余

选择文件系统

  • Linux推荐XFS或ext4
  • XFS：高性能，支持大文件，适合MySQL
  • ext4：成熟稳定，日志文件系统
  • 避免使用Btrfs（稳定性和性能问题）
  • 文件系统挂载选项：
    • noatime：不更新访问时间，减少写
    • nodiratime：不更新目录访问时间
    • data=writeback（ext4）：元数据日志，数据不日志，性能好但崩溃可能数据不一致
    • XFS默认日志模式适合MySQL

选择磁盘队列调度器：

  • I/O调度器：Noop、Deadline、CFQ、Kyber
  • SSD推荐Noop或Deadline（SSD无寻道，不需要复杂调度）
  • 机械硬盘推荐Deadline（兼顾延迟和吞吐量）
  • MySQL数据库推荐Deadline

内存和交换：

  • 尽量避免使用swap（swap会严重降低MySQL性能）
  • 配置vm.swappiness=1（尽量不使用swap）
  • 确保内存足够，MySQL缓冲池不超过物理内存
  • 禁用swap或限制swap使用

操作系统状态：

  • 监控CPU使用率、I/O等待、内存使用、网络
  • vmstat、iostat、mpstat、sar、top
  • 找出系统瓶颈

其他有用的工具：

  • perf：Linux性能分析工具
  • bcc/BPF：动态跟踪工具
  • pt-stalk：Percona Toolkit，问题发生时收集诊断信息
  • pt-diskstats：磁盘I/O统计

第5章 优化服务器设置

MySQL配置原则

  • 不要盲目调优，先找出瓶颈
  • 大部分默认配置已合理，只需调整少数关键参数
  • 配置变更后测量效果
  • 配置文件：my.cnf / my.ini
  • 动态变量可运行时修改（SET GLOBAL），静态变量需重启

重要配置变量

InnoDB缓冲池：

  • innodb_buffer_pool_size：缓冲池大小，最重要的参数
    • 专用数据库服务器：物理内存的50%-70%
    • 需为操作系统、其他进程、连接内存留空间
  • innodb_buffer_pool_instances：缓冲池实例数，减少锁竞争（大缓冲池时设为多个）
  • innodb_buffer_pool_dump_at_shutdown / innodb_buffer_pool_load_at_startup：缓冲池预热

InnoDB日志：

  • innodb_log_file_size：redo log文件大小
    • 影响写性能和崩溃恢复时间
    • 越大写性能越好，但崩溃恢复越慢
    • 推荐512MB-2GB（写密集场景）
  • innodb_log_files_in_group：日志文件数，默认2
  • innodb_flush_log_at_trx_commit：日志刷盘策略
    • 0：每秒刷盘，事务提交不刷盘（性能最好，崩溃丢1秒数据）
    • 1：每次提交刷盘（最安全，默认，性能差）
    • 2：每次提交写操作系统缓存，每秒刷盘（折中）

InnoDB I/O：

  • innodb_flush_method：刷盘方法
    • O_DIRECT：绕过操作系统缓存，直接写磁盘（推荐，避免双缓冲）
    • fsync：默认，使用操作系统缓存
  • innodb_io_capacity：InnoDB后台I/O能力（每秒IOPS）
    • 根据磁盘性能设置：SAS 200-400，SSD 2000+，NVMe 10000+
  • innodb_io_capacity_max：最大I/O能力
  • innodb_read_io_threads / innodb_write_io_threads：I/O线程数

InnoDB其他：

  • innodb_file_per_table=ON：独立表空间（推荐）
  • innodb_open_files：可打开文件数
  • table_open_cache：表缓存
  • innodb_lock_wait_timeout：锁等待超时（默认50秒）
  • innodb_print_all_deadlocks：记录所有死锁到错误日志

连接和线程：

  • max_connections：最大连接数
    • 不要设置过大（每个连接消耗内存）
    • 根据实际需求设置，配合连接池
  • thread_cache_size：线程缓存大小
  • wait_timeout / interactive_timeout：连接超时
  • max_allowed_packet：最大包大小（大查询/大插入需调大）

查询缓存：

  • MySQL 8.0已移除查询缓存
  • 之前版本：query_cache_type、query_cache_size
  • 查询缓存有锁竞争，高并发下性能差，不推荐使用

排序和临时表：

  • sort_buffer_size：排序缓冲区（每个会话）
  • join_buffer_size：连接缓冲区（每个会话）
  • tmp_table_size / max_heap_table_size：内存临时表大小
    • 超过大小则转为磁盘临时表（性能差）
    • 两个变量需同时设置

安全和二进制日志：

  • server_id：服务器ID（复制必需）
  • log_bin：启用binlog
  • binlog_format=ROW：行级复制（推荐）
  • expire_logs_days / binlog_expire_logs_seconds：binlog过期时间
  • sync_binlog：binlog刷盘频率（1=每次提交刷盘，最安全）
  • gtid_mode=ON / enforce_gtid_consistency=ON：GTID复制

配置检查清单

  • 缓冲池大小是否合理
  • redo log大小是否合理
  • 刷盘策略是否符合数据安全要求
  • 字符集是否统一（utf8mb4）
  • 时区设置
  • 复制配置
  • 连接数限制
  • 慢查询日志是否开启

第6章 Schema与数据类型优化

选择优化的数据类型

更小的通常更好：

  • 尽量使用最小的数据类型（能存下数据即可）
  • 小数据类型占用更少磁盘、内存、CPU缓存
  • 如：年龄用TINYINT而非INT

简单就好：

  • 简单数据类型操作开销小
  • 整数比字符串比较快
  • 用日期时间类型而非字符串存储日期
  • 用IP地址的整数表示（INET_ATON）而非字符串

尽量避免NULL：

  • NULL列使索引、索引统计、值比较更复杂
  • NULL列需额外存储空间（1位/列）
  • 可使用0、空字符串、特殊值替代NULL
  • 但InnoDB中NULL列的性能影响已减小，不必过度优化

整数类型

  • TINYINT：8位，-128127（或0255无符号）
  • SMALLINT：16位
  • MEDIUMINT：24位
  • INT：32位
  • BIGINT：64位
  • UNSIGNED：无符号，最大值翻倍（如INT UNSIGNED 0~4294967295）
  • 选择能存下数据的最小类型
  • 整数类型指定宽度（如INT(11)）不限制存储，只影响显示宽度

实数类型

  • FLOAT：4字节，近似值
  • DOUBLE：8字节，近似值
  • DECIMAL：精确存储，用于货币等需精确计算的场景
    • DECIMAL(M,D)：M总位数，D小数位数
    • 每9位数字占4字节
    • 计算开销比FLOAT/DOUBLE大
  • 金额计算用DECIMAL或整数（分为单位）

字符串类型

VARCHAR：

  • 可变长度字符串，比定长节省空间
  • 需1-2字节存储长度
  • 适合长度变化大的字符串
  • 更新时可能导致行移动（长度增加）

CHAR：

  • 定长字符串，不足补空格
  • 适合长度固定或很短的字符串
  • 如：MD5值CHAR(32)、性别CHAR(1)、状态码

TEXT/BLOB：

  • 大对象类型，存储大量数据
  • TEXT：文本（TINYTEXT、TEXT、MEDIUMTEXT、LONGTEXT）
  • BLOB：二进制（TINYBLOB、BLOB、MEDIUMBLOB、LONGBLOB）
  • 不能有默认值
  • 排序只取前max_sort_length字节
  • 可能导致磁盘临时表
  • 大字段建议单独存储或使用外部存储

枚举（ENUM）：

  • 字符串对象，值从允许列表中选择
  • 内部用整数存储，紧凑
  • 列表修改需ALTER TABLE（昂贵）
  • 适合固定的状态值、类型值
  • 排序按内部整数而非字符串

日期和时间类型

  • DATETIME：8字节，范围1000-9999年，与时区无关
  • TIMESTAMP：4字节，范围1970-2038年，与时区相关，自动更新
  • DATE：3字节，仅日期
  • TIME：3字节，仅时间
  • YEAR：1字节，年份
  • 选择：需大范围用DATETIME，需时区自动转换用TIMESTAMP
  • 避免用字符串存储日期

位数据类型

  • BIT：位字段，可存储多个布尔值（BIT(8)存8个布尔）
  • 节省空间，但操作不便
  • 整数的位运算也可实现类似效果

选择标识符（主键）

  • 主键应尽可能小（整数最佳）
  • 自增整数（AUTO_INCREMENT）是常用主键
  • UUID不适合作为InnoDB主键（随机插入导致页分裂、聚簇索引性能差）
  • 若需全局唯一ID，考虑雪花算法（Snowflake）等有序ID
  • 避免使用过长字符串作为主键

索引和外键

  • 索引加速查询，但增加写开销和存储空间
  • 外键保证引用完整性，但有性能开销
  • InnoDB外键自动创建索引
  • 高并发写场景可考虑应用层维护引用完整性，不用外键

Schema设计中的陷阱

  • 太多列（宽表）
  • 太多联合查询
  • 过度使用ENUM
  • 过度使用NULL
  • 用不同数据类型存储相同值（关联列类型不一致导致索引失效）

第7章 索引优化

索引类型

B-Tree索引：

  • InnoDB默认索引类型，B+树实现
  • 适合全值匹配、最左前缀匹配、范围查询、排序
  • 聚簇索引：主键索引，叶子节点存储数据行
  • 二级索引：非主键索引，叶子节点存储主键值

哈希索引：

  • 哈希表实现，O(1)查找
  • 只支持等值查询，不支持范围、排序
  • InnoDB自适应哈希索引（自动创建）
  • Memory引擎支持哈希索引

全文索引：

  • 全文搜索，MATCH AGAINST
  • 适合文本搜索
  • InnoDB支持全文索引（5.6+）

空间索引：

  • GIS数据，R-Tree
  • MySQL支持空间索引

B-Tree索引工作原理

  • B+树：非叶子节点存储键值和指针，叶子节点存储数据（或主键），叶子节点链表连接
  • 聚簇索引：数据按主键顺序存储，主键查询快，范围查询快
  • 二级索引：叶子节点存储主键值，查询需回表（再查聚簇索引）
  • 覆盖索引：索引包含查询所需所有列，无需回表

索引的优点

  • 减少服务器扫描的数据量
  • 避免排序和临时表
  • 将随机I/O变为顺序I/O
  • 加速查询

高性能索引策略

最左前缀原则：

  • 联合索引按列顺序匹配
  • 查询必须从索引最左列开始
  • 不能跳过中间列
  • 范围查询后的列不能使用索引

索引列不能是表达式的一部分：

  • WHERE TO_DAYS(CURDATE()) - TO_DAYS(date_col) <= 10 不能用索引
  • 改写为 WHERE date_col >= DATE_SUB(CURDATE(), INTERVAL 10 DAY)

前缀索引：

  • 对长字符串列索引前N个字符
  • 节省空间，但不能用于ORDER BY和GROUP BY
  • 选择合适前缀长度（区分度高）

选择合适的索引列顺序：

  • 等值查询列在前，范围查询列在后
  • 区分度高的列在前
  • 考虑排序和分组需求

聚簇索引最佳实践：

  • 主键用自增整数（顺序插入，减少页分裂）
  • 避免随机主键（UUID）
  • 主键尽量小（二级索引存储主键值）

覆盖索引：

  • 索引包含查询所有列
  • 避免回表，性能提升
  • EXPLAIN中Extra显示”Using index”

使用索引扫描排序：

  • 索引顺序与ORDER BY一致时，可用索引排序
  • 避免filesort
  • 条件：最左前缀匹配、所有列升序或降序一致

索引维护

  • 索引碎片化：删除/更新导致页分裂和碎片
  • 分析索引：ANALYZE TABLE更新统计信息
  • 优化表：OPTIMIZE TABLE重建表和索引
  • 监控索引使用：sys.schema_unused_indexes、sys.schema_redundant_indexes
  • 删除未使用和冗余索引

索引设计误区

  • 索引越多越好（索引增加写开销）
  • 为每个列创建索引（联合索引更高效）
  • 忽略查询模式设计索引
  • 不考虑索引维护成本

第8章 查询性能优化

慢查询基础：优化数据访问

  • 查询性能差的根本原因：访问数据太多
  • 分析步骤：
    1. 应用是否请求了太多数据（不需要的行/列）
    2. MySQL是否扫描了太多额外行

是否请求了不需要的数据：

  • SELECT * 获取不需要的列
  • 查询过多行（LIMIT限制）
  • 多表关联获取重复数据

MySQL是否扫描额外的行：

  • 衡量指标：响应时间、扫描行数、返回行数
  • 扫描行数远大于返回行数 → 需要优化索引
  • EXPLAIN分析执行计划

重构查询方式

一个复杂查询还是多个简单查询：

  • MySQL内部连接/排序开销大
  • 拆分为多个简单查询，应用层合并可能更快
  • 减少锁持有时间

切分查询：

  • 大查询（如DELETE大量行）分批执行
  • 避免长时间锁表、大量undo log、主从延迟
  • 如：每次删除1000行，循环执行

分解关联查询：

  • 将多表JOIN拆为单表查询，应用层关联
  • 优点：缓存效率高、减少锁竞争、易于分布式扩展
  • 缺点：多次查询、应用层逻辑复杂

查询执行基础

MySQL查询执行流程：

  1. 客户端发送SQL
  2. 服务器解析、预处理、优化
  3. 生成执行计划
  4. 存储引擎执行
  5. 返回结果

MySQL客户端/服务器协议：

  • 半双工，查询结果流式返回
  • 客户端不能中途停止接收（必须接收完或断开）
  • 大结果集消耗客户端内存

查询状态：

  • Sleep：等待客户端发送请求
  • Query：执行查询
  • Locked：等待表锁
  • Analyzing statistics / Optimizing：优化
  • Preparing：预处理
  • Sorting result：排序
  • Sending data：发送数据
  • SHOW FULL PROCESSLIST查看

查询优化器

  • 基于成本的优化器（CBO）
  • 估算各种执行计划成本，选择最低成本
  • 成本基于统计信息（索引基数、表行数等）
  • 统计信息可能不准确，导致优化器选错
  • ANALYZE TABLE更新统计信息
  • EXPLAIN查看执行计划
  • 优化器提示（Optimizer Hints）可干预优化器选择

特定类型查询优化

优化COUNT()查询：

  • COUNT(*)：统计行数，InnoDB需扫描
  • COUNT(column)：统计非NULL行数
  • 近似值：SHOW TABLE STATUS的Rows列（估算，不精确）
  • 大表精确COUNT慢，可考虑缓存、汇总表、近似值

优化关联查询：

  • 确保ON或USING列有索引
  • 小表驱动大表
  • 避免不必要的排序（ORDER BY可利用索引）
  • 限制关联表数量（MySQL最多61张表，建议不超过5-7张）

优化LIMIT分页：

  • 深分页（LIMIT 1000000, 10）扫描大量行
  • 优化：
    • 延迟关联：先查主键，再回表查数据
    • 书签分页：记录上一页最后ID，WHERE id > last_id LIMIT 10
    • 避免深分页，限制最大页数

优化UNION查询：

  • UNION ALL不去重，比UNION快
  • 除非需要去重，否则用UNION ALL
  • 每个子查询可独立优化

优化GROUP BY和DISTINCT：

  • 利用索引分组/去重
  • 无法用索引时，MySQL用临时表或filesort
  • 大结果集分组性能差
  • 可考虑汇总表预计算

EXPLAIN解读

  • id：查询序号
  • select_type：查询类型（SIMPLE、PRIMARY、SUBQUERY、DERIVED、UNION等）
  • table：表名
  • type：访问类型（system > const > eq_ref > ref > range > index > ALL，越左越好）
  • possible_keys：可能使用的索引
  • key：实际使用的索引
  • key_len：索引使用长度
  • ref：索引比较的列
  • rows：预估扫描行数
  • Extra：额外信息（Using index、Using where、Using filesort、Using temporary等）

第9章 复制

复制概述

MySQL复制是将数据从一个服务器（主库）复制到另一个服务器（从库）的过程。

复制用途：

  • 数据备份
  • 读扩展（读写分离）
  • 高可用（主从切换）
  • 数据分析（从库跑报表）
  • 地理分布

复制原理：

  1. 主库将修改写入binlog
  2. 从库IO线程读取主库binlog，写入relay log
  3. 从库SQL线程读取relay log并重放
  4. 异步复制，从库可能延迟

复制模式

基于语句的复制（SBR）：

  • 复制SQL语句
  • 优点：binlog小、易审计
  • 缺点：非确定性函数（NOW()、UUID()）、触发器、存储过程可能导致主从不一致

基于行的复制（RBR）：

  • 复制行变更（before image + after image）
  • 优点：精确、安全、无确定性问题
  • 缺点：binlog大（大表UPDATE/DELETE）、无法直接看到SQL

混合模式（MBR）：

  • 自动选择SBR或RBR
  • 安全语句用SBR，非确定性语句用RBR
  • MySQL默认推荐ROW模式

GTID复制

  • GTID（全局事务ID）：每个事务唯一标识
  • 格式：source_id:transaction_id
  • 从库记录已执行的GTID集合
  • 自动定位复制位置，无需手动指定binlog文件名和位置
  • 故障切换更简单
  • 配置：gtid_mode=ON、enforce_gtid_consistency=ON

复制拓扑

  • 主从（一主一从）
  • 一主多从
  • 主主（双主，需注意冲突）
  • 级联复制（主→从→从，减少主库压力）
  • 环形复制（多主，复杂，不推荐）

复制监控和排错

  • SHOW SLAVE STATUS\G查看从库状态
  • 关键指标：
    • Slave_IO_Running：IO线程状态
    • Slave_SQL_Running：SQL线程状态
    • Seconds_Behind_Master：延迟秒数（估算，不精确）
    • Last_IO_Error / Last_SQL_Error：错误信息
  • 常见问题：
    • 连接错误：网络、权限、防火墙
    • 主键冲突：数据不一致
    • 表不存在：结构不一致
    • 延迟大：大事务、慢查询、网络、从库性能差

复制性能优化

  • 从库并行复制（MySQL 5.7+基于组提交，8.0+基于WRITESET）
  • slave_parallel_workers：并行复制线程数
  • slave_parallel_type=LOGICAL_CLOCK：基于组提交的并行
  • 大事务拆分为小事务
  • 从库使用更好的硬件
  • 网络优化

第10章 高可用与可扩展性

高可用

高可用目标：

  • 减少停机时间，提高服务可用性
  • 可用性 = 正常运行时间 / 总时间
  • 99.9% = 年停机8.76小时
  • 99.99% = 年停机52.6分钟
  • 99.999% = 年停机5.26分钟

高可用方案：

  • 主从复制 + 手动/自动切换
  • MHA（Master High Availability）：自动故障切换
  • Orchestrator：MySQL复制拓扑管理和故障切换
  • ProxySQL / HAProxy：读写分离和故障转移
  • 组复制（Group Replication）：MySQL原生多主高可用
  • InnoDB Cluster：组复制 + MySQL Router + MySQL Shell

故障切换：

  • 检测主库故障
  • 提升从库为主库
  • 切换应用连接
  • 恢复原主库为从库
  • 注意：数据一致性、切换时间、脑裂

可扩展性

扩展方式：

  • 垂直扩展（Scale Up）：升级硬件（更快CPU、更大内存、更快磁盘）
  • 水平扩展（Scale Out）：增加服务器数量

读扩展：

  • 读写分离：写主库，读从库
  • 多个从库分担读压力
  • 中间件（ProxySQL、MaxScale）路由
  • 注意：复制延迟导致读不一致

写扩展：

  • 写扩展比读扩展困难
  • 分库分表（Sharding）：
    • 垂直分库：按业务模块拆分
    • 水平分表：按规则（哈希、范围）将数据分散到多表/多库
  • 分库分表中间件：ShardingSphere、MyCAT、Vitess
  • 注意：跨库JOIN、分布式事务、全局ID、扩容迁移

缓存：

  • 减少数据库访问
  • Redis、Memcached
  • 缓存策略：Cache-Aside、Write-Through、Write-Behind
  • 缓存穿透、击穿、雪崩问题

学习建议：

  • 第3章Performance Schema是第4版重点，现代MySQL性能诊断必备
  • 第6-8章（Schema、索引、查询）是日常优化最常用的内容
  • 第4-5章（硬件、配置）在部署和调优时参考
  • 第9-10章（复制、高可用）在生产环境架构设计时参考
  • 优化原则：先测量再优化，不要盲目调参
  • 配合工具：EXPLAIN、Performance Schema、慢查询日志、pt-query-digest
  • 推荐配合《MySQL技术内幕：InnoDB存储引擎》深入理解InnoDB

这本书适合DBA、后端开发工程师、架构师阅读，是MySQL性能优化领域的权威参考。
