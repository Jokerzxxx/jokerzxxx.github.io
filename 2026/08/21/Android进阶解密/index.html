第1章 Android系统架构

1.1 Android系统架构

Android系统采用分层架构，从上到下分为：

  1. 应用层（Applications）：系统应用和第三方应用，运行在ART虚拟机中
  2. 应用框架层（Application Framework）：Java API框架，包括ActivityManager、WindowManager、ContentProvider、View System、Package Manager、Telephony Manager等
  3. 系统运行库层（Libraries & Android Runtime）：
    • C/C++库：SurfaceFlinger、Media Framework、SQLite、OpenGL ES、WebKit、SGL、FreeType
    • Android运行时：ART虚拟机（Android 5.0+）+ 核心Java库
  4. 硬件抽象层（HAL）：封装硬件驱动，向上提供标准接口
  5. Linux内核层（Linux Kernel）：进程管理、内存管理、网络协议栈、驱动程序、安全机制

1.2 Android系统源码目录

目录 说明
frameworks/base/ 核心框架（Java API、系统服务、资源）
frameworks/native/ Native框架（SurfaceFlinger、Binder、SensorService）
system/core/ 系统核心（init、adbd、logcat、libcutils）
system/media/ 多媒体系统（AudioFlinger、CameraService）
hardware/ 硬件抽象层（HAL）
art/ ART虚拟机
dalvik/ Dalvik虚拟机
external/ 第三方开源库
packages/ 系统应用
kernel/ Linux内核
build/ 编译系统（Soong/Ninja/Make）
prebuilts/ 预编译工具链

1.3 源码阅读

阅读方法：

  • 从宏观到微观，先理解整体架构再深入细节
  • 结合调用链追踪，从入口方法一路跟到底层
  • 善用工具：SourceInsight、Android Studio（AOSP导入）、grep/ripgrep
  • 关注关键类和关键方法，不必逐行阅读
  • 结合时序图和类图理解复杂流程

第2章 Android系统启动

2.1 init进程启动过程

init是Linux系统中用户空间的第一个进程（PID=1），是所有进程的父进程。

启动流程：

  1. 内核加载完成后，启动init进程
  2. init解析/init.rc和/init.<硬件>.rc脚本
  3. 创建文件系统挂载点（/dev、/proc、/sys等）
  4. 启动属性服务（property service）
  5. 启动关键守护进程（ueventd、logd、healthd等）
  6. 启动zygote进程（通过app_process）
  7. 启动servicemanager（Binder服务管理者）
  8. 启动mediaserver、installd等系统服务

2.2 Zygote进程启动过程

Zygote（孵化器）是Android系统的核心进程，所有应用进程和SystemServer都由Zygote fork而来。

启动流程：

  1. init启动app_process，传入参数启动Zygote
  2. app_process调用AndroidRuntime.start，启动虚拟机
  3. 注册JNI方法
  4. 预加载类和资源（preloadClasses、preloadResources）
  5. 启动SystemServer进程（forkSystemServer）
  6. 进入Zygote循环（runSelectLoop），通过LocalSocket等待创建应用进程的请求

Zygote的作用：

  • 预加载类和资源，子进程fork后共享，减少应用启动时间和内存占用
  • 统一管理应用进程的创建

2.3 SystemServer处理过程

SystemServer是Android系统的核心服务进程，所有重要的系统服务（AMS、WMS、PMS等）都运行在这个进程中。

启动流程：

  1. Zygote fork出SystemServer进程
  2. 启动Binder线程池
  3. 创建SystemServer对象
  4. 引导服务（Bootstrap Services）：ActivityManagerService、PowerManagerService、PackageManagerService等
  5. 核心服务（Core Services）：BatteryService、UsageStatsService、WebViewUpdateService等
  6. 其他服务（Other Services）：WindowManagerService、InputManagerService、AccessibilityManagerService等
  7. 进入Looper循环

2.4 Launcher启动过程

Launcher是Android的桌面应用，是用户看到的第一个界面。

启动流程：

  1. SystemServer启动完成后，AMS发送开机广播
  2. AMS调用startHomeActivityLocked启动Launcher
  3. Launcher的onCreate中加载已安装应用列表
  4. 通过PackageManager获取所有应用信息
  5. 显示应用图标和名称到桌面

第3章 应用程序进程启动过程

3.1 应用程序进程简介

每个Android应用运行在独立的进程中，由Zygote fork创建。进程名默认为应用包名，可通过android:process指定。

3.2 应用程序进程启动过程介绍

启动流程：

  1. 调用startActivity启动一个新应用的Activity
  2. AMS检查应用进程是否存在，不存在则调用startProcessLocked
  3. AMS通过Process.start向Zygote发送创建进程请求
  4. Zygote通过LocalSocket接收请求，fork出子进程
  5. 子进程中调用ActivityThread.main
  6. 创建ApplicationThread（Binder对象，用于与AMS通信）
  7. 调用attach方法，向AMS注册ApplicationThread
  8. AMS调用bindApplication，通过ApplicationThread回调handleBindApplication
  9. handleBindApplication中创建Application，调用onCreate
  10. 启动目标Activity

3.3 Binder线程池启动过程

每个应用进程启动时会创建Binder线程池，用于处理来自系统服务的IPC请求。

启动流程：

  1. ActivityThread.main中调用Looper.prepareMainLooper
  2. 调用attach(false)，内部调用IActivityManager.attachApplication
  3. AMS处理attachApplication，调用bindApplication
  4. 应用进程的ApplicationThread.bindApplication中发送消息
  5. handleBindApplication中初始化各种系统服务客户端
  6. Binder线程池在进程启动时由AndroidRuntime自动创建（openBinderDriver、startThreadPool）

3.4 消息循环创建过程

应用进程的主线程消息循环在ActivityThread.main中创建：

  1. Looper.prepareMainLooper()：创建主线程Looper和MessageQueue
  2. 创建ActivityThread对象
  3. Looper.loop()：进入消息循环，不断从MessageQueue取消息并处理

第4章 四大组件的工作过程

4.1 根Activity的启动过程

根Activity是应用启动的第一个Activity。

启动流程：

  1. Launcher点击应用图标，调用startActivity
  2. Instrumentation.execStartActivity → ActivityManagerService.startActivity
  3. AMS通过ActivityStarter处理启动请求，检查权限、创建ActivityRecord
  4. AMS检查应用进程是否存在，不存在则先创建进程（见第3章）
  5. 进程创建后，AMS通过ApplicationThread调用scheduleLaunchActivity
  6. ActivityThread的H Handler收到LAUNCH_ACTIVITY消息
  7. handleLaunchActivity → performLaunchActivity
  8. performLaunchActivity中：
    • 通过ClassLoader加载Activity类
    • 创建Activity实例
    • 调用attach（创建PhoneWindow、设置WindowManager）
    • 调用onCreate
    • 调用onStart
  9. handleResumeActivity → 调用onResume → wm.addView显示DecorView

4.2 Service的启动过程

  1. startService → ContextImpl.startService → AMS.startService
  2. AMS通过ActiveServices处理，创建ServiceRecord
  3. 若进程不存在则先创建进程
  4. AMS通过ApplicationThread调用scheduleCreateService
  5. ActivityThread.handleCreateService：加载Service类、创建实例、attach、onCreate
  6. AMS调用scheduleServiceArgs → handleServiceArgs → onStartCommand

4.3 Service的绑定过程

  1. bindService → ContextImpl.bindService → AMS.bindService
  2. AMS通过ActiveServices处理，若Service未启动则先启动
  3. Service创建后，调用publishService（通过onBind返回IBinder）
  4. AMS通过ApplicationThread调用scheduleBindService
  5. handleBindService → onBind（首次绑定）→ onServiceConnected（ServiceConnection回调）

4.4 广播的注册、发送和接收过程

静态注册：在AndroidManifest中声明，应用安装时由PMS解析，无需应用启动即可接收。

动态注册：Context.registerReceiver → AMS.registerReceiver，将ReceiverDispatcher存入AMS。

发送和接收：

  1. sendBroadcast → ContextImpl.sendBroadcast → AMS.broadcastIntent
  2. AMS通过BroadcastQueue处理，区分有序/普通广播
  3. 遍历匹配的Receiver，通过ApplicationThread回调scheduleRegisteredReceiver
  4. ReceiverDispatcher调用onReceive（动态注册）；静态注册则先启动进程再调用

4.5 ContentProvider的启动过程

  1. 应用启动时，ActivityThread.handleBindApplication中：
    • installContentProviders（启动ContentProvider）
    • Application.onCreate
  2. installContentProviders遍历providers列表，通过AMS.publishContentProviders发布
  3. ContentProvider创建时调用onCreate（先于Application.onCreate）
  4. 其他应用通过ContentResolver访问时，ContentResolver通过AMS获取ContentProvider的Binder代理（IContentProvider），再通过IPC调用

第5章 理解上下文Context

5.1 Context的关联类

Context是抽象类，具体实现有：

  • ContextImpl：真正的实现类，所有Context方法的具体实现
  • ContextWrapper：Context的包装类，持有mBase（ContextImpl），方法委托给mBase
  • Application：继承ContextWrapper，应用级Context
  • Activity：继承ContextWrapper（通过ContextThemeWrapper），Activity级Context
  • Service：继承ContextWrapper，Service级Context

5.2 Application Context的创建过程

  1. ActivityThread.handleBindApplication中创建LoadedApk
  2. LoadedApk.makeApplication创建Application
  3. 创建ContextImpl，通过attach设置为Application的mBase
  4. 调用Application.attach → attachBaseContext
  5. 调用Application.onCreate

5.3 Application Context的获取过程

  • **getApplicationContext()**：ContextWrapper中调用mBase.getApplicationContext，返回Application对象
  • **getApplication()**：仅Activity和Service有，返回Application对象
  • 两者返回的都是同一个Application对象

5.4 Activity的Context创建过程

  1. performLaunchActivity中创建Activity实例
  2. 创建ContextImpl，设置为Activity的mBase
  3. 调用Activity.attach → attachBaseContext
  4. attach中创建PhoneWindow，设置WindowManager

5.5 Service的Context创建过程

  1. handleCreateService中创建Service实例
  2. 创建ContextImpl，设置为Service的mBase
  3. 调用Service.attach → attachBaseContext

第6章 理解ActivityManagerService

6.1 AMS家族

AMS相关类：

  • ActivityManagerService（AMS）：核心服务，管理四大组件和进程
  • ActivityManager：客户端API，通过Binder调用AMS
  • IActivityManager：AMS的Binder接口
  • ActivityStack：管理一个Activity栈
  • ActivityStackSupervisor：管理所有ActivityStack
  • ActivityRecord：一个Activity的记录
  • TaskRecord：一个任务栈的记录
  • ProcessRecord：一个进程的记录

6.2 AMS的启动过程

  1. SystemServer启动时，在引导服务阶段创建AMS
  2. ActivityManagerService.Lifecycle.startService创建AMS实例
  3. AMS构造方法中初始化各种数据结构
  4. setSystemProcess设置系统进程信息
  5. installSystemProviders安装系统ContentProvider
  6. systemReady通知系统就绪，启动Launcher

6.3 AMS与应用程序进程

AMS通过ProcessRecord管理每个应用进程：

  • 记录进程名、pid、uid、ApplicationInfo
  • 管理进程中的Activity、Service、BroadcastReceiver、ContentProvider
  • 管理进程的优先级（adj值），用于LowMemoryKiller杀进程
  • 通过ApplicationThread（Binder）与应用进程通信

6.4 AMS重要的数据结构

  • mProcessNames：进程名到ProcessRecord的映射
  • mPidsSelfLocked：pid到ProcessRecord的映射
  • mHistoryStack：Activity栈管理
  • mServices：ActiveServices，管理所有Service
  • mBroadcastQueues：广播队列（前台/后台）

6.5 Activity栈管理

AMS通过ActivityStack和ActivityStackSupervisor管理Activity栈：

  • 每个ActivityRecord记录一个Activity的状态
  • 每个TaskRecord记录一个任务栈
  • ActivityStack管理任务栈的顺序和Activity的生命周期
  • 支持多种启动模式（standard/singleTop/singleTask/singleInstance）
  • 管理最近任务列表（RecentTasks）

第7章 理解WindowManager

7.1 Window、WindowManager和WMS

  • Window：抽象类，具体实现PhoneWindow，代表一个窗口
  • WindowManager：接口，继承ViewManager，提供addView/updateViewLayout/removeView
  • WindowManagerImpl：WindowManager的实现类，委托给WindowManagerGlobal
  • WindowManagerGlobal：单例，管理所有Window的添加/删除/更新
  • WindowManagerService（WMS）：系统服务，运行在SystemServer，管理所有窗口的状态、层级、动画

7.2 WindowManager的关联类

  • ViewRootImpl：每个Window对应一个ViewRootImpl，连接WindowManager和DecorView，负责View的三大流程（measure/layout/draw）和事件分发
  • WindowManager.LayoutParams：Window的布局参数，包括type（窗口类型）、flags（窗口标志）、gravity、x/y
  • IWindowSession：WindowManager与WMS通信的Binder接口
  • IWindow：WMS回调应用进程的Binder接口（ViewRootImpl.W）

7.3 Window的属性

Window类型（type）：

  • 应用Window（1-99）：Activity的Window
  • 子Window（1000-1999）：Dialog、PopupWindow，需依附于应用Window
  • 系统Window（2000-2999）：Toast、状态栏、锁屏、系统提示，需要权限

层级越高，显示越靠上。

Window标志（flags）：

  • FLAG_NOT_FOCUSABLE：不获取焦点
  • FLAG_NOT_TOUCH_MODAL：区域外事件传递给下层Window
  • FLAG_SHOW_WHEN_LOCKED：锁屏上显示
  • FLAG_KEEP_SCREEN_ON：保持屏幕常亮
  • FLAG_FULLSCREEN：全屏

7.4 Window的操作

添加Window：

  1. WindowManager.addView → WindowManagerGlobal.addView
  2. 创建ViewRootImpl
  3. 将View、LayoutParams、ViewRootImpl存入列表
  4. ViewRootImpl.setView → requestLayout → WindowSession.addWindow → WMS.addWindow

更新Window：

  1. WindowManager.updateViewLayout → WindowManagerGlobal.updateViewLayout
  2. 更新LayoutParams
  3. ViewRootImpl.setLayoutParams → scheduleTraversals → WindowSession.relayout → WMS.relayout

删除Window：

  1. WindowManager.removeView → WindowManagerGlobal.removeView
  2. ViewRootImpl.die → dispatchDetachedFromWindow → WindowSession.remove → WMS.removeWindow

第8章 理解WindowManagerService

8.1 WMS的职责

WMS是Android系统的窗口管理服务，核心职责：

  • 管理所有窗口的添加、删除、更新
  • 管理窗口的层级（Z-order）和显示顺序
  • 管理窗口的动画（窗口切换动画、转场动画）
  • 管理输入事件的分发（通过InputManagerService）
  • 管理系统界面（状态栏、导航栏、锁屏）
  • 管理窗口的焦点（哪个Window接收按键事件）

8.2 WMS的创建过程

  1. SystemServer启动时，在其他服务阶段创建WMS
  2. DisplayThread线程中创建WMS（与显示相关的服务运行在这个线程）
  3. WMS构造方法中初始化：
    • DisplayManager（显示管理）
    • InputManagerService（输入管理）
    • WindowAnimator（窗口动画）
    • WindowStateManager（窗口状态管理）
    • 各种窗口容器（DisplayContent）
  4. 调用systemReady通知系统就绪

8.3 WMS的重要成员

  • mRoot：RootWindowContainer，所有窗口容器的根
  • mDisplayContents：DisplayContent列表，每个屏幕对应一个
  • mWindowMap：IBinder到WindowState的映射，所有窗口记录
  • mAnimator：WindowAnimator，窗口动画管理
  • mInputManager：InputManagerService，输入事件管理
  • mPolicy：WindowManagerPolicy，窗口策略（PhoneWindowManager）
  • mH：Handler，处理WMS内部消息

8.4 Window的添加过程（WMS处理部分）

  1. 应用进程通过WindowSession.addWindow调用WMS.addWindow
  2. WMS检查调用者权限（系统Window需要SYSTEM_ALERT_WINDOW权限）
  3. 创建WindowState，代表一个窗口
  4. 根据Window类型分配层级（layer）
  5. 将WindowState加入对应DisplayContent的窗口列表
  6. 调用updateFocusedWindowLocked更新焦点窗口
  7. 调用performSurfacePlacement执行窗口布局
  8. 创建Surface（通过SurfaceControl），用于绘制

8.5 Window的删除过程

  1. 应用进程通过WindowSession.remove调用WMS.removeWindow
  2. WMS从mWindowMap中移除WindowState
  3. 从DisplayContent的窗口列表中移除
  4. 播放退出动画
  5. 动画结束后释放Surface
  6. 更新焦点窗口和窗口布局

第9章 JNI原理

9.1 系统源码中的JNI

JNI（Java Native Interface）是Java与C/C++交互的桥梁。Android系统中大量使用JNI：

  • Framework层调用Native层（如MediaPlayer、SurfaceFlinger）
  • 系统服务的Native实现
  • 图形、音频、数据库等底层库

9.2 MediaRecorder框架中的JNI

以MediaRecorder为例：

  1. Java层MediaRecorder调用native方法（如native_start）
  2. JNI层（android_media_MediaRecorder.cpp）注册native方法
  3. JNI层调用Native层MediaRecorder
  4. Native层通过Binder调用MediaPlayerService

9.3 数据类型的转换

基本类型映射：boolean→jboolean、byte→jbyte、char→jchar、short→jshort、int→jint、long→jlong、float→jfloat、double→jdouble。

引用类型映射：jobject（所有引用类型的基类）、jclass（Class）、jstring（String）、jarray（数组）、jobjectArray（对象数组）、jbooleanArray等（基本类型数组）。

9.4 方法签名

JNI方法签名格式：(参数类型签名)返回值类型签名

  • 基本类型：Z(boolean)、B(byte)、C(char)、S(short)、I(int)、J(long)、F(float)、D(double)、V(void)
  • 引用类型：L全限定名;（如Ljava/lang/String;）
  • 数组：[类型签名（如[I表示int[]）

示例：void setDataSource(String path) → (Ljava/lang/String;)V

9.5 解析JNIEnv

JNIEnv是JNI环境指针，是Native代码调用Java功能的入口：

  • 每个线程有独立的JNIEnv，不能跨线程使用
  • Native线程中通过JavaVM.AttachCurrentThread获取JNIEnv
  • 使用完后DetachCurrentThread
  • JNIEnv提供大量方法：FindClass、GetMethodID、CallObjectMethod、NewStringUTF、GetArrayElements等

9.6 引用类型

JNI中的引用分为三类：

  • 局部引用（Local Reference）：Native方法调用期间有效，方法返回后自动释放。通过NewLocalRef创建，DeleteLocalRef释放。
  • 全局引用（Global Reference）：跨方法、跨线程有效，需手动释放。通过NewGlobalRef创建，DeleteGlobalRef释放。
  • 弱全局引用（Weak Global Reference）：类似全局引用，但不阻止GC回收。通过NewWeakGlobalRef创建。

第10章 Java虚拟机

10.1 概述

Java虚拟机（JVM）是Java程序运行的环境，负责加载字节码、解释/编译执行、内存管理、垃圾回收。

10.2 Java虚拟机结构

运行时数据区：

  • 方法区（Method Area）：存储类信息、常量、静态变量、JIT编译后的代码。线程共享。
  • 堆（Heap）：存储对象实例和数组，是GC的主要区域。线程共享。
  • 虚拟机栈（VM Stack）：每个线程私有，存储局部变量表、操作数栈、动态链接、方法返回地址。
  • 本地方法栈（Native Method Stack）：为Native方法服务。
  • 程序计数器（PC Register）：记录当前线程执行的字节码行号。

执行引擎：解释器（逐条解释字节码）+ JIT编译器（热点代码编译为本地机器码）。

10.3 对象的创建

对象创建流程：

  1. 类加载检查：检查new指令的参数是否能在常量池中定位到类符号引用，检查类是否已加载、解析、初始化
  2. 分配内存：根据堆是否规整，使用”指针碰撞”（Bump the Pointer）或”空闲列表”（Free List）
  3. 初始化零值：将分配的内存空间初始化为零值（不包括对象头）
  4. 设置对象头：Mark Word（哈希码、GC分代年龄、锁状态）、类型指针（指向类元数据）
  5. 执行方法：调用构造函数，初始化对象

10.4 对象的堆内存布局

对象在堆内存中分为三部分：

  • 对象头（Header）：Mark Word（8字节）+ 类型指针（8字节，开启压缩指针后4字节）+ 数组长度（4字节，仅数组对象）
  • 实例数据（Instance Data）：对象的字段值，包括父类继承的字段
  • 对齐填充（Padding）：对象大小必须是8字节的整数倍，不足则填充

10.5 oop-klass模型

HotSpot虚拟机采用oop-klass模型描述对象：

  • oop（Ordinary Object Pointer）：对象指针，描述对象实例本身。包括instanceOop（普通对象）、arrayOop（数组对象）、methodOop（方法）等。
  • klass：描述对象的元数据（类信息），相当于Java.lang.Class的Native表示。包括instanceKlass（普通类）、arrayKlass（数组类）等。

oop存储在堆中，klass存储在方法区中。

10.6 垃圾标记算法

引用计数算法（Reference Counting）：每个对象维护一个引用计数器，被引用时+1，引用失效时-1，计数器为0时可回收。优点简单，缺点无法解决循环引用。

可达性分析算法（Reachability Analysis）：从GC Roots出发，遍历引用链，不可达的对象可回收。HotSpot使用此算法。

GC Roots包括：

  • 虚拟机栈中引用的对象（局部变量）
  • 方法区中类静态属性引用的对象
  • 方法区中常量引用的对象
  • 本地方法栈中JNI引用的对象
  • 活跃线程引用的对象

10.7 Java对象在虚拟机中的生命周期

对象的生命周期：

  1. 创建阶段：类加载 → 分配内存 → 初始化 → 构造函数
  2. 应用阶段：对象被至少一个强引用持有，处于使用中
  3. 不可见阶段：程序不再持有对象的强引用，但可能被软引用/弱引用持有
  4. 不可达阶段：从GC Roots不可达，可被GC回收
  5. 收集阶段：GC标记，若重写了finalize且未执行过，则放入F-Queue等待finalize执行
  6. 对象空间重分配阶段：GC回收对象占用的内存

10.8 垃圾收集算法

标记-清除（Mark-Sweep）：标记所有可达对象，清除未标记对象。缺点：产生内存碎片。

复制（Copying）：将内存分为两块，每次只用一块，回收时将存活对象复制到另一块。优点无碎片，缺点内存利用率低。新生代使用此算法（Eden+Survivor）。

标记-整理（Mark-Compact）：标记存活对象，将存活对象向一端移动，清除边界外的内存。优点无碎片，缺点需要移动对象。老年代使用此算法。

分代收集（Generational Collection）：根据对象存活周期分为新生代和老年代，新生代使用复制算法，老年代使用标记-清除或标记-整理。

第11章 Dalvik和ART

11.1 Dalvik虚拟机

Dalvik是Android早期使用的虚拟机（Android 2.2-4.4）：

  • 基于寄存器架构（JVM基于栈架构），指令更短、执行更快
  • 执行dex（Dalvik Executable）格式字节码
  • Android 2.2引入JIT（即时编译），热点代码编译为本地机器码
  • 内存管理：堆分为Zygote堆和Active堆，Zygote堆用于预加载，写时复制（COW）共享
  • 垃圾回收：CMS（Concurrent Mark Sweep）收集器

11.2 ART虚拟机

ART（Android Runtime）从Android 5.0开始取代Dalvik：

  • AOT（Ahead-Of-Time）编译：应用安装时将dex编译为本地机器码（oat文件），运行时直接执行，无需解释
  • Android 7.0引入JIT + AOT混合模式：安装时不编译，运行时JIT编译热点代码，空闲时AOT编译保存
  • 更好的垃圾回收：压缩GC（Compacting GC），减少内存碎片；并发GC，减少停顿
  • 更好的调试支持：支持更多调试特性
  • 64位支持：原生支持64位架构

11.3 DVM和ART的区别

特性 Dalvik ART
执行方式 解释 + JIT AOT + JIT（混合）
编译时机 运行时 安装时/运行时
应用安装速度 快 慢（AOT编译）
运行速度 较慢 较快
占用空间 小 大（oat文件）
GC CMS Compacting GC
64位 不支持 支持

第12章 理解ClassLoader

12.1 Java中的ClassLoader

Java类加载器负责将.class文件加载到JVM中。

类加载器分类：

  • 启动类加载器（Bootstrap ClassLoader）：加载JRE核心类库（rt.jar），C++实现，无父加载器
  • 扩展类加载器（Extension ClassLoader）：加载扩展类库（jre/lib/ext）
  • 应用程序类加载器（Application ClassLoader）：加载用户类路径（classpath）上的类

双亲委托模型：类加载时先委托父加载器加载，父加载器无法加载时才自己加载。保证核心类库的安全性和一致性。

12.2 Android中的ClassLoader

Android的ClassLoader加载dex文件（而非.class文件）。

Android中的类加载器：

  • BootClassLoader：加载Android Framework层的类（如android.app.Activity），是所有ClassLoader的父加载器
  • PathClassLoader：加载已安装应用的dex文件（/data/app/xxx.apk），应用默认的类加载器
  • DexClassLoader：加载任意路径的dex/jar/apk文件，需要指定optimizedDirectory（odex输出目录），用于插件化和热修复

类加载流程：

  1. ClassLoader.loadClass → findLoadedClass检查是否已加载
  2. 未加载则委托父加载器加载（双亲委托）
  3. 父加载器无法加载则自己加载（findClass）
  4. DexClassLoader/PathClassLoader的findClass通过BaseDexClassLoader实现，从dexElements数组中查找类
  5. dexElements是Element数组，每个Element对应一个dex文件

类加载器的应用：

  • 热修复：将修复后的dex插入dexElements数组头部，优先加载修复后的类
  • 插件化：通过DexClassLoader加载插件APK中的类

第13章 热修复原理

13.1 热修复的产生

热修复技术允许应用在不重新安装APK的情况下修复bug。产生背景：

  • 应用发布后发现bug，重新发版周期长、成本高
  • 用户升级率低，大量用户仍使用有bug的版本
  • 紧急bug需要快速修复

13.2 热修复框架的种类和对比

框架 原理 特点
阿里Sophix 综合方案（代码/资源/so） 商业产品，功能全面
腾讯Tinker 类加载方案（dex差量） 开源，需要重启生效，支持代码/资源/so
美团Robust 方法体替换（Instant Run原理） 开源，即时生效，无需重启
阿里AndFix Native层方法替换 开源，即时生效，兼容性问题
滴滴Aceso 类加载方案 开源

13.3 资源修复

资源修复的原理：

  • 将修复后的资源打包成补丁
  • 通过反射替换AssetManager，加载补丁中的资源
  • 替换Resources对象，使应用优先加载补丁中的资源
  • 类似插件化的资源加载方案

13.4 代码修复

代码修复主要有三种方案：

类加载方案（Tinker）：

  1. 将修复后的类打包成dex补丁
  2. 应用启动时，通过反射将补丁dex插入PathClassLoader的dexElements数组头部
  3. 类加载时优先从补丁dex中加载，实现修复
  4. 需要重启应用生效（已加载的类无法替换）

方法体替换方案（Robust）：

  1. 编译时在每个方法中插入代码：if (changeQuickRedirect != null) return changeQuickRedirect.accessDispatch(…)
  2. 修复时，将修复后的方法封装为Patch对象
  3. 通过反射将changeQuickRedirect设置为修复后的方法代理
  4. 方法执行时走修复后的逻辑，即时生效

Native层方法替换（AndFix）：

  1. 通过JNI修改ArtMethod结构体中的方法入口指针
  2. 将修复后的方法地址替换原方法地址
  3. 调用原方法时跳转到修复方法
  4. 即时生效，但兼容性差（不同Android版本ArtMethod结构不同）

13.5 动态链接库的修复

so库修复：

  • 将修复后的so库放入补丁
  • 通过System.load加载补丁中的so库
  • 或通过反射替换NativeLibrary的加载路径
  • Tinker等框架支持so库的差量修复

第14章 Hook技术

14.1 Hook技术概述

Hook技术是指在程序运行时，拦截并修改方法调用的技术。通过Hook可以：

  • 监控方法调用（日志、统计）
  • 修改方法行为（替换参数、返回值）
  • 绕过某些限制（权限检查、签名验证）
  • 实现插件化（Hook系统服务）

14.2 Hook技术分类

  • Java层Hook：通过反射和动态代理实现，Hook Java方法
  • Native层Hook：通过修改函数指针或指令实现，Hook Native方法
  • 框架层Hook：Hook Android Framework层的系统服务（如AMS、WMS、PMS）

14.3 代理模式

代理模式是Hook技术的基础：

  • 静态代理：编译时生成代理类，实现与目标类相同的接口，持有目标类引用，方法调用时委托给目标类
  • 动态代理：运行时通过Proxy.newProxyInstance生成代理类，通过InvocationHandler处理方法调用
  • Hook时通常使用动态代理，替换系统服务的Binder代理对象

14.4 Hook startActivity方法

以Hook startActivity为例：

  1. 找到Hook点：ActivityManager.getService()返回的IActivityManager单例
  2. 通过反射获取IActivityManager实例（Singleton中的instance字段）
  3. 创建动态代理，实现IActivityManager接口
  4. 在InvocationHandler中拦截startActivity方法，修改Intent（如将插件Activity替换为占坑Activity）
  5. 通过反射将代理对象设置回Singleton.instance
  6. 后续startActivity调用都会经过代理，实现Hook

其他常见Hook点：

  • Hook AMS：IActivityManager
  • Hook WMS：IWindowManager
  • Hook PMS：IPackageManager
  • Hook ClipboardManager
  • Hook Instrumentation（替换Activity启动逻辑）

第15章 插件化原理

15.1 动态加载技术

动态加载技术允许应用在运行时加载并执行外部的dex/jar/apk文件，是插件化的基础。核心技术：

  • 类加载：DexClassLoader加载插件中的类
  • 资源加载：反射AssetManager.addAssetPath加载插件资源
  • 四大组件管理：通过占坑和Hook实现插件四大组件的生命周期管理

15.2 插件化的产生

插件化产生背景：

  • 应用功能越来越多，APK体积增大
  • 模块化需求：不同业务模块独立开发、独立更新
  • 按需加载：减少主APK体积，用户按需下载功能模块
  • 热更新：不发版更新功能模块

15.3 插件化框架对比

框架 原理 特点
滴滴VirtualAPK Hook系统服务 + 占坑 轻量，四大组件支持完善
360 DroidPlugin 占坑 + Hook Binder 功能全面，独立进程
携程DynamicAPK 占坑 + 资源修改 修改aapt，资源隔离
阿里Atlas 容器化 + OSGi思想 淘宝使用，支持热更新
腾讯Shadow 委托代理（非Hook） 开源，避免Hook兼容性问题

15.4 Activity插件化

Activity插件化的核心是占坑式启动：

  1. 在宿主AndroidManifest中预先声明多个占坑Activity（不同启动模式、不同process）
  2. 启动插件Activity时，Hook IActivityManager.startActivity，将Intent中的插件Activity替换为占坑Activity
  3. AMS校验通过（占坑Activity已注册）
  4. 在ActivityThread的H Handler中，Hook handleLaunchActivity，将占坑Activity的Intent还原为插件Activity
  5. 使用插件的ClassLoader加载插件Activity类
  6. 正常执行Activity生命周期

15.5 Service插件化

Service插件化同样使用占坑：

  1. 宿主中声明占坑Service
  2. 启动插件Service时，Hook IActivityManager.startService，替换为占坑Service
  3. AMS校验通过
  4. 在ActivityThread中Hook handleCreateService，还原为插件Service
  5. 使用插件ClassLoader加载插件Service类
  6. 绑定服务类似处理

15.6 ContentProvider插件化

ContentProvider插件化：

  1. 宿主中声明占坑ContentProvider
  2. Hook IContentProvider，将对插件Provider的访问转发到占坑Provider
  3. 在占坑Provider中根据URI分发到实际的插件Provider
  4. 或通过IContentProvider的动态代理直接转发

15.7 BroadcastReceiver的插件化

BroadcastReceiver插件化：

  • 静态注册：解析插件APK中的AndroidManifest，提取静态注册的Receiver，在宿主中动态注册
  • 动态注册：插件代码中直接调用registerReceiver，使用插件Context

15.8 资源的插件化

资源插件化的核心：

  1. 反射调用AssetManager.addAssetPath(pluginPath)，将插件APK加入资源搜索路径
  2. 创建新的Resources对象，使用插件的AssetManager
  3. 插件中使用插件Resources加载资源
  4. 资源ID冲突问题：通过修改aapt（重命名资源ID前缀）或公共资源包解决

15.9 so的插件化

so库插件化：

  1. 将插件中的so库解压到指定目录
  2. 通过反射修改ApplicationInfo的nativeLibraryDir，加入插件so路径
  3. 或通过System.load直接加载插件so库的绝对路径

第16章 绘制优化

16.1 绘制性能分析

绘制性能分析工具：

  • Hierarchy Viewer：分析View树层级和绘制时间（已废弃，推荐Layout Inspector）
  • Layout Inspector：Android Studio提供的布局检查器
  • Systrace：系统级性能分析工具，查看绘制流程
  • GPU过度绘制调试：开发者选项中开启，查看过度绘制
  • GPU呈现模式分析：开发者选项中开启，查看每帧绘制时间

性能标准：

  • 60fps要求每帧绘制时间不超过16.67ms
  • 超过16.67ms会出现掉帧、卡顿
  • 过度绘制：蓝色1次（可接受）、绿色2次、淡红3次、深红4次+（需优化）

16.2 布局优化

减少布局层级：

  • 使用ConstraintLayout减少嵌套
  • 避免不必要的嵌套布局
  • 使用Hierarchy Viewer/Layout Inspector分析层级

使用include标签：复用布局，减少重复代码。

使用merge标签：当include的根布局与父布局相同时，使用merge减少一层布局。

使用ViewStub：延迟加载不常显示的布局（如错误页、加载更多）。ViewStub是轻量级View，不占用位置，inflate时才加载。

避免在onDraw中创建对象：onDraw会被频繁调用，创建对象会导致频繁GC。

避免过度绘制：

  • 移除不必要的背景
  • 使用clipRect减少绘制区域
  • 复杂布局使用自定义View减少层级

第17章 内存优化

17.1 避免可控的内存泄漏

常见内存泄漏场景：

  • 静态变量持有Activity/Context
  • 单例模式持有Activity Context
  • 非静态内部类/匿名内部类（Handler、AsyncTask、Thread）持有外部类引用
  • 未取消注册的广播/事件总线
  • 资源未关闭（Cursor、File、Socket、Stream）
  • 属性动画未停止
  • WebView内存泄漏
  • 监听器未移除

避免方法：

  • 使用Application Context替代Activity Context
  • 静态内部类+弱引用
  • 在组件销毁时取消注册、关闭资源、停止动画
  • WebView使用独立进程或正确销毁

17.2 Memory Monitor

Android Studio的Memory Monitor（已整合到Profiler）：

  • 实时显示应用内存使用情况
  • 查看内存分配和回收
  • 手动触发GC
  • 导出HPROF文件（堆转储）

17.3 Allocation Tracker

Allocation Tracker（已整合到Profiler）：

  • 记录内存分配情况
  • 查看每个对象的分配位置、大小、线程
  • 分析内存分配热点
  • 发现不必要的对象创建

17.4 Heap Dump

Heap Dump（堆转储）：

  • 导出当前堆内存快照（.hprof文件）
  • 包含所有对象的信息（类型、数量、引用关系）
  • 使用MAT工具分析
  • 发现内存泄漏的对象

17.5 内存分析工具MAT

MAT（Memory Analyzer Tool）：

  • Histogram：查看对象数量和占用内存
  • Dominator Tree：查看最大对象和引用链
  • Path to GC Roots：查看对象到GC Root的引用路径，定位泄漏原因
  • 对比两个HPROF：操作前后对比，找出增长的对象

关键概念：

  • Shallow Heap：对象自身大小
  • Retained Heap：对象被回收后能释放的总内存
  • GC Root：可达性分析的根节点

17.6 LeakCanary

LeakCanary是Square出品的内存泄漏检测库：

  • 自动检测Activity/Fragment的内存泄漏
  • 泄漏时显示通知和泄漏链
  • 开发阶段集成，自动发现内存泄漏
  • 原理：监听Activity生命周期，onDestroy后将对象放入WeakReference，GC后检查是否被回收，未回收则dump堆并分析泄漏链

读书笔记总结

《Android进阶解密》是一本深入Android Framework源码的进阶书籍，从系统启动到应用进程，从四大组件到系统服务，从虚拟机到热修复插件化，形成了完整的Android系统知识体系。

全书知识脉络：

  1. 系统启动篇（第1-3章）：系统架构、系统启动流程（init→Zygote→SystemServer→Launcher）、应用进程启动
  2. 组件与服务篇（第4-8章）：四大组件工作过程、Context、AMS、WindowManager、WMS
  3. 底层原理篇（第9-12章）：JNI、Java虚拟机、Dalvik/ART、ClassLoader
  4. 进阶技术篇（第13-15章）：热修复、Hook技术、插件化
  5. 性能优化篇（第16-17章）：绘制优化、内存优化

学习建议：

  • 第2-3章（系统启动/进程启动）是理解Android系统的基础，建议结合源码深入学习
  • 第4章（四大组件）和第6章（AMS）是面试高频考点
  • 第7-8章（WindowManager/WMS）是理解GUI系统的关键
  • 第10章（JVM）和第12章（ClassLoader）是理解热修复/插件化的基础
  • 第13-15章（热修复/Hook/插件化）是Android高级开发的进阶技能

这本书适合有一定Android开发基础、希望深入Framework源码和系统原理的开发者阅读。
