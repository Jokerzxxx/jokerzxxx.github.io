深入理解Android内核设计思想

深入理解Android内核设计思想（第二版）

作者：林学森
全书共4篇25章，2156页（上下册），从编译系统、系统原理、应用原理到系统工具，全方位深入Android内核设计。

第1篇 Android编译篇

第1章 Android系统简介

Android是基于Linux内核的开源移动操作系统，由Google主导开发。

系统架构分层：

  1. 应用层：系统应用和第三方应用
  2. 应用框架层：Java API框架（ActivityManager、WindowManager等）
  3. 系统运行库层：C/C++库（SurfaceFlinger、MediaFramework、SQLite、OpenGL）+ Android运行时（ART）
  4. 硬件抽象层（HAL）：封装硬件驱动，向上提供标准接口
  5. Linux内核层：进程管理、内存管理、网络协议栈、驱动程序

Android的设计思想：

  • 开放性：开源代码，允许厂商定制
  • 分层架构：各层职责清晰，通过标准接口通信
  • 组件化：四大组件（Activity、Service、BroadcastReceiver、ContentProvider）
  • 沙箱机制：每个应用运行在独立进程和虚拟机中，相互隔离

第2章 Android源码下载及编译

源码下载方式：

  • repo工具：Google提供的多仓库管理工具，通过repo init和repo sync下载
  • 镜像源：国内可使用中科大、清华等镜像源加速下载
  • 单仓库下载：通过git clone下载单个模块仓库

源码目录结构：

  • frameworks/：框架层
  • system/：系统组件
  • packages/：系统应用
  • hardware/：硬件抽象层
  • kernel/：Linux内核
  • art/：ART虚拟机
  • external/：第三方库
  • build/：编译系统
  • prebuilts/：预编译工具链
  • out/：编译输出目录

编译步骤：

  1. source build/envsetup.sh：初始化编译环境
  2. lunch：选择编译目标（如aosp_arm64-eng）
  3. make -j8：编译（-j指定并行任务数）
  4. 编译产物在out/target/product/<产品名>/目录

编译目标类型：

  • user：正式版，限制访问，无root，无调试
  • userdebug：调试版，有root，有调试，类似user但开启调试
  • eng：工程版，有root，有调试，默认安装所有模块，适合开发

第3章 Android编译系统

Android编译系统从早期的Make（Android.mk）演进到Soong（Android.bp + Ninja）。

Make编译系统（Android.mk）：

  • 基于GNU Make
  • Android.mk定义模块编译规则
  • Application.mk定义应用级编译配置
  • 支持BUILD_PACKAGE、BUILD_SHARED_LIBRARY、BUILD_STATIC_LIBRARY等模块类型
  • 缺点：Makefile语法复杂，并行编译效率低，增量编译不准确

Soong编译系统（Android.bp）：

  • Android 7.0引入，基于Blueprint和Ninja
  • Android.bp使用类似JSON的简洁语法定义模块
  • Blueprint解析Android.bp生成Ninja文件
  • Ninja专注于快速执行构建
  • 优点：语法简洁、并行高效、增量编译准确
  • androidmk工具可将Android.mk转换为Android.bp

关键编译概念：

  • 模块（Module）：编译的基本单位（APK、库、可执行文件等）
  • 变量（Variable）：编译配置（LOCAL_SRC_FILES、LOCAL_PACKAGE_NAME等）
  • 依赖（Dependency）：模块间的依赖关系
  • 产品配置（Product）：定义目标设备的编译配置（设备类型、包含的模块、属性等）
  • Board配置（BoardConfig）：定义硬件相关配置（CPU架构、分区大小、驱动等）

第2篇 Android原理篇

第4章 操作系统基础

进程与线程：

  • 进程是资源分配的最小单位，拥有独立的地址空间
  • 线程是CPU调度的最小单位，共享进程资源
  • Android中每个应用默认运行在独立进程中

进程间通信（IPC）：

  • 管道（Pipe）、消息队列（Message Queue）、共享内存（Shared Memory）、信号量（Semaphore）、套接字（Socket）
  • Android特有的Binder机制

内存管理：

  • 虚拟内存：每个进程拥有独立的虚拟地址空间
  • 分页机制：将内存分为固定大小的页（通常4KB）
  • 页面置换：LRU、Clock等算法
  • Android的LowMemoryKiller：根据进程优先级（adj值）杀进程回收内存

文件系统：

  • Linux虚拟文件系统（VFS）：统一接口，支持多种文件系统
  • Android常用文件系统：ext4、f2fs、yaffs2
  • 分区：boot、system、vendor、data、cache等

第5章 Android进程/线程和程序内存优化

Android进程模型：

  • 每个应用默认运行在独立进程，进程名为包名
  • 通过android:process指定组件运行在指定进程
  • 多进程的优缺点：内存隔离、崩溃不影响主进程；但数据不共享、增加内存开销

进程优先级（adj值）：

  • 前台进程（Foreground）：正在交互的Activity或前台Service，adj=0
  • 可见进程（Visible）：可见但不可交互的Activity，adj=100
  • 服务进程（Service）：运行中的Service，adj=300
  • 后台进程（Background）：不可见的Activity，adj=400
  • 空进程（Empty）：无组件运行的进程，adj=500
  • LowMemoryKiller根据adj值从低优先级杀起

Android线程模型：

  • 主线程（UI线程）：处理UI事件和绘制，不能执行耗时操作
  • 子线程：执行耗时任务（网络、数据库、计算）
  • 线程间通信：Handler、Looper、MessageQueue
  • 线程池：复用线程，控制并发数

程序内存优化：

  • 内存泄漏：静态变量持有Context、未取消注册、资源未关闭、非静态内部类
  • 内存溢出（OOM）：加载大图未压缩、集合未清理、内存泄漏累积
  • 优化方法：图片压缩（inSampleSize）、使用LruCache、避免静态变量持有Activity、及时释放资源、使用SparseArray替代HashMap
  • 内存分析工具：Memory Monitor、Allocation Tracker、Heap Dump、MAT、LeakCanary

第6章 进程间通信——Binder

Binder概述：

  • Binder是Android特有的IPC机制，基于OpenBinder
  • 采用C/S架构，由Client、Server、ServiceManager、Binder驱动组成
  • 性能优于传统IPC（一次数据拷贝），支持线程迁移和引用计数

Binder架构组件：

  • Client：客户端进程，通过Binder代理调用服务端方法
  • Server：服务端进程，提供具体实现
  • ServiceManager：管理所有Binder服务，负责注册和查询（类似DNS）
  • Binder驱动：内核层驱动，负责数据传输和线程管理，位于/dev/binder

Binder通信流程：

  1. Server向ServiceManager注册服务（addService）
  2. Client通过ServiceManager查询服务（getService），获得Binder代理
  3. Client通过代理调用方法，数据经Binder驱动传递到Server
  4. Server执行方法，返回结果经Binder驱动传回Client
  5. Binder驱动维护线程池，Server端从线程池取线程处理请求

AIDL（Android Interface Definition Language）：

  • 定义跨进程接口的语言
  • 编译后生成Java代码（Stub服务端、Proxy客户端）
  • 支持基本类型、String、CharSequence、Parcelable、List、Map

Binder连接池：

  • 多个AIDL接口共享一个Service，通过BinderPool统一管理
  • Client通过queryBinder(code)获取对应接口的Binder
  • 减少Service数量，节省资源

第7章 Android启动过程

完整启动链：

各阶段详解：

  1. BootROM：芯片固化的引导程序，上电后执行，加载BootLoader
  2. BootLoader：引导加载程序，初始化硬件，加载Linux内核到内存
  3. Linux Kernel：内核启动，初始化驱动、进程管理、内存管理，启动init进程（PID=1）
  4. init进程：
    • 解析init.rc脚本
    • 挂载文件系统（/dev、/proc、/sys）
    • 启动属性服务
    • 启动关键守护进程（ueventd、logd、healthd）
    • 启动servicemanager（Binder服务管理者）
    • 启动zygote（通过app_process）
    • 启动mediaserver、installd等
  5. Zygote进程：
    • 启动ART虚拟机
    • 注册JNI方法
    • 预加载类和资源
    • fork出SystemServer进程
    • 进入循环，等待创建应用进程请求（LocalSocket）
  6. SystemServer进程：
    • 启动Binder线程池
    • 启动引导服务（AMS、PMS、PowerManagerService等）
    • 启动核心服务（BatteryService、UsageStatsService等）
    • 启动其他服务（WMS、InputManagerService、AudioService等）
    • 进入Looper循环
  7. Launcher启动：
    • AMS系统就绪后启动桌面应用
    • Launcher加载已安装应用列表，显示桌面

第8章 AMS——管理Activity和组件运行状态的系统进程

AMS（ActivityManagerService）概述：

  • 运行在SystemServer进程中，是Android最核心的系统服务之一
  • 负责管理四大组件的生命周期、进程管理、任务栈管理、内存管理

AMS的核心职责：

  • Activity管理：启动、停止、销毁Activity，管理Activity栈和任务栈
  • Service管理：启动、停止、绑定Service
  • Broadcast管理：注册、发送、接收广播
  • ContentProvider管理：发布和查询ContentProvider
  • 进程管理：创建应用进程、管理进程优先级、LowMemoryKiller配合杀进程
  • 任务栈管理：管理最近任务列表（RecentTasks）
  • 内存管理：监控内存使用，触发进程回收

AMS的关键数据结构：

  • ActivityRecord：一个Activity的记录，包含所有状态信息
  • TaskRecord：一个任务栈的记录，包含多个ActivityRecord
  • ActivityStack：管理一个Activity栈，包含多个TaskRecord
  • ActivityStackSupervisor：管理所有ActivityStack
  • ProcessRecord：一个进程的记录
  • ActiveServices：管理所有Service

Activity启动流程（AMS部分）：

  1. Client调用startActivity → Instrumentation.execStartActivity → AMS.startActivity
  2. AMS通过ActivityStarter处理启动请求
  3. 检查调用者权限、创建ActivityRecord
  4. 检查目标进程是否存在，不存在则先创建进程
  5. 将Activity加入任务栈，调整栈顺序
  6. 通过ApplicationThread回调scheduleLaunchActivity
  7. 目标进程执行Activity生命周期

第9章 GUI系统——SurfaceFlinger

SurfaceFlinger概述：

  • 运行在独立进程（surfaceflinger）中，是Android的图形合成服务
  • 负责将所有应用的Surface（图形缓冲区）合成后输出到显示设备
  • 基于OpenGL ES和Hardware Composer（HWC）实现

SurfaceFlinger的核心职责：

  • 图形合成：将多个Layer（对应每个Window的Surface）合成为一帧
  • 显示输出：将合成后的帧提交到显示设备（屏幕）
  • VSYNC同步：接收硬件VSYNC信号，协调应用绘制和系统合成
  • Buffer管理：管理图形缓冲区的分配、释放和排队

关键概念：

  • Surface：图形缓冲区的抽象，应用通过Surface绘制内容
  • Layer：SurfaceFlinger中的一个图层，对应一个Window
  • BufferQueue：缓冲区队列，生产者-消费者模式，应用生产，SurfaceFlinger消费
  • GraphicBuffer：图形缓冲区，存储像素数据
  • VSYNC：垂直同步信号，屏幕刷新频率（通常60Hz=16.67ms/帧）
  • Choreographer：应用侧的VSYNC协调者，统一安排输入、动画、绘制的时机

图形合成流程：

  1. 应用通过Canvas/OpenGL绘制到Surface的Buffer
  2. BufferQueue将Buffer传递给SurfaceFlinger
  3. SurfaceFlinger接收VSYNC信号，触发合成
  4. SurfaceFlinger遍历所有Layer，通过OpenGL ES或HWC合成
  5. 合成后的帧提交到显示设备
  6. 显示设备刷新屏幕

Hardware Composer（HWC）：

  • 硬件合成器，由显示芯片厂商提供
  • 可将部分Layer的合成工作交给硬件，减轻GPU负担
  • 降低功耗，提升合成效率
  • SurfaceFlinger优先使用HWC合成，HWC不支持的Layer回退到OpenGL ES

第10章 GUI系统之”窗口管理员”——WMS

WMS（WindowManagerService）概述：

  • 运行在SystemServer进程中，是Android的窗口管理服务
  • 负责管理所有窗口的添加、删除、更新、层级、焦点、动画

WMS的核心职责：

  • 窗口管理：添加、删除、更新所有窗口（应用窗口、系统窗口、子窗口）
  • 层级管理：管理窗口的Z-order（显示顺序），根据窗口类型分配层级
  • 焦点管理：管理哪个窗口接收输入事件（按键、触摸）
  • 窗口动画：管理窗口的进入/退出/切换动画
  • 输入事件分发：与InputManagerService配合，将输入事件分发到正确的窗口
  • 系统界面管理：管理状态栏、导航栏、锁屏等系统窗口

窗口类型（Type）：

  • 应用窗口（Application Window）：type=1~99，Activity的Window
  • 子窗口（Sub Window）：type=1000~1999，Dialog、PopupWindow，需依附于应用窗口
  • 系统窗口（System Window）：type=2000~2999，Toast、状态栏、导航栏、锁屏、系统提示，需要权限

层级越高，显示越靠上。

WMS的关键类：

  • WindowManagerService：核心服务
  • WindowState：一个窗口的记录，包含所有窗口属性
  • WindowToken：窗口令牌，一组相关窗口的标识
  • DisplayContent：一个屏幕的窗口容器，管理该屏幕所有窗口
  • RootWindowContainer：所有DisplayContent的根容器
  • WindowAnimator：窗口动画管理
  • WindowManagerPolicy：窗口策略（PhoneWindowManager实现）

窗口添加流程（WMS部分）：

  1. 应用通过WindowManager.addView → WindowManagerGlobal.addView
  2. 创建ViewRootImpl，调用setView
  3. ViewRootImpl通过WindowSession（IWindowSession Binder）调用WMS.addWindow
  4. WMS检查权限（系统窗口需要SYSTEM_ALERT_WINDOW）
  5. 创建WindowState，分配层级
  6. 将WindowState加入DisplayContent的窗口列表
  7. 更新焦点窗口
  8. 执行窗口布局（performSurfacePlacement）
  9. 创建Surface（通过SurfaceControl）

第11章 让你的界面炫彩起来的GUI系统——View体系

View体系概述：

  • View是所有UI控件的基类，ViewGroup继承自View，是控件容器
  • View树的根是DecorView，本质是FrameLayout

View的位置参数：

  • left/top/right/bottom：相对于父容器的原始坐标
  • x/y：当前坐标 = left + translationX
  • translationX/translationY：偏移量
  • elevation：Z轴高度（Android 5.0+）

View的三大流程：

  1. measure（测量）：

    • 从ViewRootImpl的performTraversals开始
    • measureSpec：32位int，高2位SpecMode（UNSPECIFIED/EXACTLY/AT_MOST），低30位SpecSize
    • View通过onMeasure测量，setMeasuredDimension设置大小
    • ViewGroup遍历测量子元素，自身无onMeasure（子类实现）
    • 自定义View需重写onMeasure处理wrap_content

  2. layout（布局）：

    • layout方法确定View位置，setFrame设置四个顶点
    • onLayout确定子元素位置（View空实现，ViewGroup抽象方法）

  3. draw（绘制）：

    • 顺序：背景 → onDraw → dispatchDraw（子元素）→ 装饰（滚动条）
    • setWillNotDraw(true)优化纯容器ViewGroup

事件分发机制：

  • dispatchTouchEvent：分发事件
  • onInterceptTouchEvent：判断是否拦截（仅ViewGroup）
  • onTouchEvent：处理事件
  • 传递顺序：Activity → Window → DecorView → ViewGroup → View
  • 关键结论：DOWN不消费则后续事件不再交给该View；onTouchListener优先级高于onTouchEvent

滑动冲突处理：

  • 外部拦截法：父容器onInterceptTouchEvent中处理，DOWN不拦截，MOVE按需拦截，UP不拦截
  • 内部拦截法：子元素dispatchTouchEvent中配合requestDisallowInterceptTouchEvent

自定义View分类：

  1. 继承View重写onDraw：不规则效果
  2. 继承特定ViewGroup：组合布局
  3. 继承特定View：扩展已有控件
  4. 继承ViewGroup重写onMeasure/onLayout：自定义布局

第12章 InputManagerService与输入事件

IMS（InputManagerService）概述：

  • 运行在SystemServer进程中，与WMS紧密配合
  • 负责输入事件的读取、处理和分发

输入事件处理流程：

  1. 硬件中断：触摸/按键产生硬件中断
  2. 驱动层：Linux输入子系统（evdev）读取事件，写入/dev/input/eventX
  3. InputReader：IMS中的线程，从设备节点读取原始事件，转换为Android输入事件（MotionEvent/KeyEvent）
  4. InputDispatcher：IMS中的线程，将输入事件分发到合适的窗口
  5. WMS配合：InputDispatcher通过WMS获取焦点窗口和窗口状态
  6. 应用处理：事件通过InputChannel（一对匿名Socket，跨进程传递）发送到应用进程的ViewRootImpl
  7. View分发：ViewRootImpl将事件交给DecorView，沿View树分发

关键概念：

  • InputChannel：输入通道，一对匿名Socket（跨进程）或管道（同进程），用于IMS和应用间传递输入事件
  • InputReader：读取原始输入事件并转换
  • InputDispatcher：分发输入事件到目标窗口
  • 焦点窗口：当前接收按键事件的窗口，由WMS管理
  • 触摸窗口：接收触摸事件的窗口，根据触摸位置和窗口区域确定

ANR与输入事件：

  • 输入事件超时（5秒无响应）会触发ANR
  • InputDispatcher监控事件处理超时，超时后通知AMS弹出ANR对话框

第13章 应用不再同质化——音频系统

Android音频系统架构：

  • 应用框架层：MediaPlayer、AudioTrack、AudioRecord、SoundPool
  • JNI层：android_media_AudioTrack.cpp等
  • Native框架层：libmedia（AudioTrack、AudioRecord C++类）、libaudioclient
  • 音频服务层：AudioFlinger（音频混音服务，运行在mediaserver进程）、AudioPolicyService（音频策略服务）
  • HAL层：audio.primary.so、audio.a2dp.so等，封装硬件驱动
  • 内核驱动层：ALSA（Advanced Linux Sound Architecture）驱动

核心服务：

  • AudioFlinger：
    • 运行在mediaserver进程
    • 负责音频混音（Mixer）、重采样、音量调节
    • 管理音频输出线程（PlaybackThread）和输入线程（RecordThread）
    • PlaybackThread分类：DirectOutput（直接输出）、MixerThread（混音输出）、OffloadThread（硬件解码输出）
  • AudioPolicyService：
    • 运行在mediaserver进程
    • 负责音频路由策略（选择输出设备：扬声器/耳机/蓝牙）
    • 管理音频焦点（AudioFocus）
    • 管理音频设备连接状态

音频播放流程：

  1. 应用创建AudioTrack，指定采样率、声道、格式
  2. AudioTrack通过Binder与AudioFlinger通信，创建Track
  3. 应用将PCM数据写入AudioTrack
  4. 数据经Binder传递到AudioFlinger的Track
  5. AudioFlinger的PlaybackThread从所有Track读取数据，混音、重采样、音量调节
  6. 混音后的数据写入HAL层
  7. HAL层写入ALSA驱动，输出到音频硬件

音频焦点（AudioFocus）：

  • 多个应用同时播放时，通过音频焦点协调
  • 请求焦点：AudioManager.requestAudioFocus
  • 失去焦点：暂停或降低音量（ducking）
  • AudioPolicyService管理焦点分配

第14章 Intent的匹配规则

Intent概述：

  • Intent是组件间通信的消息对象，用于启动Activity、Service、发送广播
  • 分为显式Intent（指定组件名）和隐式Intent（通过IntentFilter匹配）

IntentFilter匹配规则：
隐式Intent需同时匹配action、category、data三个维度：

  1. action匹配：

    • Intent的action必须与filter中至少一个action完全匹配（区分大小写）
    • filter可声明多个action，Intent只需匹配其中一个
    • Intent不设置action时，只要filter有action就不匹配

  2. category匹配：

    • Intent中的每个category都必须在filter中存在
    • Intent不设置category时，系统默认添加android.intent.category.DEFAULT
    • 因此隐式调用的Activity必须在filter中声明DEFAULT category
    • filter可声明多个category，Intent只需全部包含在filter中

  3. data匹配：

    • data由mimeType和URI组成
    • URI包含scheme、host、port、path/pathPattern/pathPrefix
    • Intent的data必须与filter的data规则匹配
    • filter声明了mimeType时，Intent必须设置相同的mimeType
    • filter声明了URI时，Intent的URI各部分必须匹配
    • data匹配要求Intent的data各部分都能在filter中找到匹配

Intent解析流程：

  1. PackageManagerService（PMS）在应用安装时解析所有组件的IntentFilter
  2. 隐式Intent启动时，PMS遍历所有已注册的IntentFilter
  3. 同时匹配action、category、data的组件为匹配结果
  4. 多个匹配时弹出选择对话框（如”选择使用哪个应用打开”）

第15章 APK应用程序的资源适配

Android资源体系：

  • 资源包括布局（layout）、字符串（string）、图片（drawable）、颜色（color）、尺寸（dimen）、样式（style）等
  • 资源存储在res/目录下，通过R类引用
  • 系统根据设备配置自动选择最合适的资源

资源限定符（Qualifiers）：
资源目录名可添加限定符，系统按优先级匹配：

  • 语言和区域：values-zh、values-zh-rCN
  • 屏幕尺寸：layout-small、layout-normal、layout-large、layout-xlarge
  • 屏幕密度：drawable-ldpi、drawable-mdpi、drawable-hdpi、drawable-xhdpi、drawable-xxhdpi、drawable-xxxhdpi
  • 屏幕方向：layout-land（横屏）、layout-port（竖屏）
  • UI模式：values-night（夜间模式）、values-car（车载模式）
  • 最小宽度：values-sw600dp（最小宽度600dp，平板）
  • 可用宽度：values-w600dp
  • 平台版本：values-v21（API 21+）

资源匹配优先级：
系统按以下顺序选择资源（从高到低）：

  1. MCC/MNC（移动国家码/网络码）
  2. 语言和区域
  3. 布局方向（LTR/RTL）
  4. 最小宽度（smallestWidth）
  5. 可用宽度（availableWidth）
  6. 可用高度（availableHeight）
  7. 屏幕尺寸（screenSize）
  8. 屏幕纵横比（screenAspect）
  9. 屏幕方向（orientation）
  10. UI模式（uiMode）
  11. 夜间模式（night）
  12. 屏幕密度（density）
  13. 触摸屏类型（touchscreen）
  14. 键盘可用性（keyboardHidden）
  15. 输入法类型（keyboard）
  16. 导航键可用性（navigationHidden）
  17. 导航类型（navigation）
  18. 平台版本（SDK版本）

匹配时从最高优先级开始，一旦某个限定符有匹配资源，就不再考虑更低优先级的限定符（除非更高优先级没有匹配）。

资源加载机制：

  • Resources类管理所有资源的加载
  • AssetManager负责读取APK中的资源文件
  • 资源编译时aapt2工具处理，生成resources.arsc（资源索引表）
  • 运行时Resources根据设备配置和resources.arsc选择最合适的资源

第16章 Android字符编码格式

字符编码基础：

  • ASCII：7位编码，128个字符，仅支持英文字母和符号
  • ISO-8859-1（Latin-1）：8位编码，256个字符，支持西欧语言
  • GB2312：中国国家标准，6763个汉字
  • GBK：GB2312的扩展，21003个汉字，Windows中文版默认编码
  • GB18030：GBK的扩展，支持更多汉字和少数民族文字，中国国家标准
  • Unicode：统一字符集，为每个字符分配唯一码点（Code Point），范围U+0000~U+10FFFF
  • UTF-8：Unicode的变长编码，1~4字节，ASCII字符1字节，中文通常3字节，兼容ASCII
  • UTF-16：Unicode的变长编码，2或4字节，Java和Android的char使用UTF-16
  • UTF-32：Unicode的定长编码，4字节

Android中的字符编码：

  • Java/Android的char：使用UTF-16编码，每个char占2字节（BMP字符），辅助平面字符需要两个char（代理对）
  • String：内部使用char数组（UTF-16）存储
  • XML文件：默认UTF-8编码
  • Java源码：可指定编码，Android项目默认UTF-8
  • DEX文件：字符串使用MUTF-8（Modified UTF-8）编码
  • Native层：C/C++字符串默认使用系统编码（Android系统默认UTF-8）

MUTF-8（Modified UTF-8）：

  • JVM和DEX使用的UTF-8变体
  • 与标准UTF-8的区别：
    • null字符（U+0000）编码为2字节（0xC0 0x80），而非1字节（0x00），保证字符串中没有null字节
    • 辅助平面字符（U+10000+）编码为两个代理对的UTF-8编码（6字节），而非标准UTF-8的4字节

编码转换：

  • Java中通过String.getBytes(charset)和new String(bytes, charset)转换
  • Native层通过iconv库转换
  • Android推荐统一使用UTF-8，避免编码问题

第17章 Android和OpenGL ES

OpenGL ES概述：

  • OpenGL ES（OpenGL for Embedded Systems）是OpenGL的嵌入式版本，专为移动设备和嵌入式系统设计
  • 由Khronos Group维护，移除了OpenGL中不适合移动设备的功能（如立即模式、四边形、多边形等）
  • Android通过OpenGL ES提供硬件加速的2D/3D图形渲染

OpenGL ES版本：

  • OpenGL ES 1.0/1.1：固定功能管线（Fixed Function Pipeline），通过glEnable/glVertexPointer等状态机API
  • OpenGL ES 2.0：可编程管线（Programmable Pipeline），引入着色器（Shader），Android 2.2+支持
  • OpenGL ES 3.0：2.0的超集，增加新特性（变换反馈、实例化渲染、ETC2压缩纹理等），Android 4.3+支持
  • OpenGL ES 3.1/3.2：增加计算着色器（Compute Shader）、高级纹理等，Android 5.0+/7.0+支持

渲染管线（Rendering Pipeline）：

  1. 顶点着色器（Vertex Shader）：处理每个顶点的位置、颜色、纹理坐标
  2. 图元装配（Primitive Assembly）：将顶点组装为点、线、三角形
  3. 光栅化（Rasterization）：将图元转换为片元（Fragment，像素候选）
  4. 片元着色器（Fragment Shader）：处理每个片元的颜色
  5. 逐片元操作（Per-Fragment Operations）：深度测试、模板测试、混合、裁剪等
  6. 帧缓冲（Framebuffer）：最终像素写入帧缓冲，输出到屏幕

Android中使用OpenGL ES：

  • GLSurfaceView：封装了OpenGL ES渲染环境的View，管理EGL上下文和渲染线程
  • Renderer接口：实现onSurfaceCreated、onSurfaceChanged、onDrawFrame
  • EGL：OpenGL ES和原生窗口系统之间的桥梁，管理渲染上下文和Surface
  • SurfaceTexture：将图像流转换为GL纹理，可用于相机预览、视频播放等

着色器语言（GLSL ES）：

  • 类C语言，专为图形渲染设计
  • 顶点着色器：attribute（输入顶点属性）、uniform（全局变量）、varying（传递给片元着色器）、gl_Position（输出位置）
  • 片元着色器：varying（从顶点着色器接收）、uniform（全局变量）、gl_FragColor（输出颜色）
  • ES 3.0使用in/out替代attribute/varying

第18章 “系统的UI”——SystemUI

SystemUI概述：

  • SystemUI是Android的系统界面应用，运行在独立进程（com.android.systemui）
  • 负责显示系统级UI元素：状态栏、导航栏、锁屏、通知面板、快速设置、最近任务、截图、音量面板等

第19章 Android常用的工具”小插件”——Widget机制

App Widget概述：

  • App Widget（桌面小部件）是可以嵌入其他应用（如桌面Launcher）的微型应用视图
  • 通过RemoteViews跨进程更新UI
  • 常见Widget：时钟、天气、日历、音乐播放器、快捷开关

Widget的核心组件：

  1. AppWidgetProvider：

    • 继承自BroadcastReceiver
    • 接收Widget相关的广播（更新、删除、启用、禁用）
    • 核心回调：onUpdate、onDeleted、onEnabled、onDisabled、onReceive
    • onUpdate在定时更新或添加Widget时调用

  2. AppWidgetProviderInfo：

    • 描述Widget的元数据
    • 通过XML文件定义（res/xml/xxx_widget_info.xml）
    • 属性：minWidth/minHeight（最小尺寸）、updatePeriodMillis（更新周期）、initialLayout（初始布局）、previewImage（预览图）、resizeMode（调整大小模式）、widgetCategory（类别：home_screen/keyguard）

  3. RemoteViews：

    • 跨进程更新UI的机制
    • 支持有限的View和方法（TextView、ImageView、Button、ProgressBar等）
    • 通过set方法设置控件内容（setTextViewText、setImageViewResource等）
    • 通过setOnClickPendingIntent设置点击事件
    • 内部通过Action列表序列化，跨进程传递后在远程进程apply执行

  4. AppWidgetManager：

    • 管理所有Widget
    • updateAppWidget：更新Widget界面
    • getAppWidgetIds：获取所有Widget ID
    • getAppWidgetInfo：获取Widget信息

Widget的工作流程：

  1. 用户在桌面长按 → 选择Widget → 添加到桌面
  2. Launcher通过AppWidgetService创建Widget实例，分配appWidgetId
  3. 调用AppWidgetProvider的onUpdate
  4. onUpdate中构建RemoteViews，通过AppWidgetManager.updateAppWidget更新
  5. RemoteViews跨进程传递到Launcher进程，Launcher应用更新Widget界面
  6. 定时更新：updatePeriodMillis到期后，系统发送更新广播，触发onUpdate
  7. 点击事件：通过PendingIntent，点击时发送广播或启动Activity

Widget的更新机制：

  • 定时更新：updatePeriodMillis指定更新周期（最短30分钟，系统为省电会合并更新）
  • 手动更新：通过Service或BroadcastReceiver主动调用AppWidgetManager.updateAppWidget
  • 配置Activity：添加Widget时可启动配置Activity，配置完成后更新Widget

Widget的限制：

  • RemoteViews仅支持有限的View类型和方法
  • 不支持自定义View
  • 不支持findViewById直接操作控件
  • 更新频率受限（最短30分钟）
  • 内存和性能限制（Widget过多会影响Launcher性能）

第20章 Android应用程序的编译和打包

APK构建流程：

详细步骤：

  1. 资源编译（aapt2）：

    • aapt2 compile：编译res/目录下的资源文件
    • 生成编译后的资源文件（.flat）
    • aapt2 link：链接所有编译后的资源
    • 生成resources.arsc（资源索引表）、R.java（资源ID类）、合并AndroidManifest.xml

  2. Java/Kotlin编译：

    • javac/kotlinc编译Java/Kotlin源码
    • 生成.class字节码文件
    • 注解处理器（如ButterKnife、Dagger2）在此阶段生成代码

  3. DEX转换（D8）：

    • D8将.class字节码转换为DEX（Dalvik Executable）格式
    • 支持desugaring（脱糖）：将高版本Java API转换为低版本兼容代码
    • 方法数超过65536时生成多个DEX（multidex）

  4. 资源打包：

    • 将resources.arsc、res/下的编译资源、assets/下的原始资源打包

  5. APK打包（apkbuilder）：

    • 将DEX文件、资源文件、AndroidManifest.xml、libs/下的so库打包为APK
    • APK本质是ZIP格式压缩包

  6. 签名（apksigner/jarsigner）：

    • 使用开发者私钥对APK签名
    • 签名确保APK的完整性和来源可信
    • V1签名（JAR签名）：对ZIP条目签名
    • V2签名（APK签名方案v2）：对整个APK内容签名，验证更快
    • V3签名：支持密钥轮换
    • V4签名：支持APK的增量安装

  7. 对齐（zipalign）：

    • 对APK中的未压缩资源进行4字节对齐
    • 对齐后资源可通过mmap直接读取，减少内存占用
    • zipalign -v 4 input.apk output.apk

Gradle构建系统：

  • Android Gradle Plugin（AGP）封装了上述构建流程
  • 构建类型（Build Type）：debug、release
  • 产品风味（Product Flavor）：多渠道、多版本
  • 构建变体（Build Variant）= Build Type + Product Flavor
  • 常用任务：assembleDebug、assembleRelease、installDebug、bundleDebug（AAB）

AAB（Android App Bundle）：

  • Google推出的新发布格式
  • 包含所有代码和资源，由Google Play根据设备配置生成优化的APK
  • 减小下载体积（动态交付：按语言、屏幕密度、ABI拆分）
  • 支持动态功能模块（Dynamic Feature）

第21章 Android虚拟机

Dalvik虚拟机：

  • Android早期使用的虚拟机（Android 1.0-4.4）
  • 基于寄存器架构（JVM基于栈架构），指令更短、执行更快
  • 执行DEX（Dalvik Executable）格式字节码
  • DEX优化：dx工具将.class转换为.dex，dexopt优化为.odex
  • Android 2.2引入JIT（即时编译），热点代码编译为本地机器码
  • 内存管理：堆分为Zygote堆和Active堆，写时复制（COW）共享Zygote预加载的类
  • GC：CMS（Concurrent Mark Sweep）收集器，并发标记清除

ART虚拟机（Android Runtime）：

  • Android 5.0开始取代Dalvik
  • AOT编译：应用安装时dex2oat将DEX编译为本地机器码（OAT文件，ELF格式），运行时直接执行
  • Android 7.0引入JIT + AOT混合模式：
    • 安装时不编译，首次运行解释执行
    • 运行时JIT编译热点代码
    • 设备空闲/充电时，AOT将JIT编译的热点代码保存为profile，下次安装时根据profile AOT编译
    • 兼顾安装速度和运行速度
  • 垃圾回收优化：
    • Compacting GC（压缩GC）：回收后整理内存，减少碎片
    • 并发GC，减少停顿时间
    • 分代回收（年轻代/老年代）
  • 64位支持：原生支持64位架构
  • 更好的调试：支持更多调试特性、方法采样

DEX文件格式：

  • DEX是Dalvik/ART执行的字节码格式
  • 结构：header（文件头）、string_ids（字符串索引）、type_ids（类型索引）、proto_ids（方法原型索引）、field_ids（字段索引）、method_ids（方法索引）、class_defs（类定义）、data（数据区）
  • 相比.class更紧凑，共享常量池，减少内存占用

类加载机制：

  • BootClassLoader：加载Framework层类，所有ClassLoader的父加载器
  • PathClassLoader：加载已安装应用的DEX，应用默认类加载器
  • DexClassLoader：加载任意路径的DEX/JAR/APK，用于插件化和热修复
  • 双亲委托：加载时先委托父加载器，父加载器无法加载才自己加载
  • BaseDexClassLoader：PathClassLoader和DexClassLoader的父类，通过dexElements数组查找类
  • 热修复原理：将修复后的DEX插入dexElements数组头部，优先加载修复类

OAT文件格式：

  • ART AOT编译产物，ELF格式（可执行文件格式）
  • 包含编译后的本地机器码
  • 包含DEX文件的副本（用于解释执行和反射）
  • dex2oat工具生成，存储在/data/dalvik-cache/或应用目录下

第22章 Android安全机制透析

Android安全架构分层：

  1. Linux内核安全：用户/权限机制、SELinux、进程沙箱
  2. 应用沙箱：每个应用独立UID、独立进程、独立数据目录
  3. 权限机制：安装时/运行时权限控制
  4. 应用签名：APK签名验证，确保来源可信
  5. 代码安全：ProGuard/R8混淆、DEX加固
  6. 网络安全：HTTPS、证书锁定、网络安全配置
  7. 数据存储安全：内部存储私有、外部存储权限、加密

应用沙箱机制：

  • 每个应用安装时分配唯一的Linux UID（User ID）
  • 应用运行在独立进程中，只能访问自己的数据目录（/data/data/<包名>/）
  • 应用间默认无法互相访问数据，除非通过共享UID（sharedUserId）或IPC
  • 进程隔离基于Linux的用户/权限机制

权限机制：

  • 正常权限（Normal）：不涉及用户隐私，安装时自动授予（如网络访问、振动）
  • 危险权限（Dangerous）：涉及用户隐私，需运行时动态申请（如相机、位置、通讯录、存储）
    • Android 6.0（API 23）引入运行时权限
    • 危险权限分为9组：日历、相机、通讯录、位置、麦克风、电话、传感器、短信、存储
    • 同组权限授予一个后，同组其他权限自动授予
  • 特殊权限（Special）：需要用户在设置中手动开启（如悬浮窗、修改系统设置、忽略电池优化）
  • 签名权限（Signature）：仅相同签名的应用可获取

权限申请流程：

  1. 检查权限：ContextCompat.checkSelfPermission
  2. 未授权则请求：ActivityCompat.requestPermissions
  3. 系统弹出权限请求对话框
  4. 用户选择后回调onRequestPermissionsResult
  5. 处理授权结果

应用签名机制：

  • APK必须使用开发者私钥签名才能安装
  • 签名确保APK完整性（篡改后签名验证失败）和来源可信（相同签名的应用可共享数据、升级）
  • 签名证书由开发者生成（keystore）
  • V1签名：JAR签名，对ZIP条目签名，验证较慢
  • V2签名：对整个APK内容签名，验证更快，Android 7.0+支持
  • V3签名：支持密钥轮换，Android 9.0+支持
  • 应用升级必须使用相同签名，否则无法覆盖安装

SELinux（Security-Enhanced Linux）：

  • Linux内核安全模块，提供强制访问控制（MAC）
  • Android 4.3引入，5.0默认强制模式（enforcing）
  • 基于安全上下文（user:role:type:level）控制进程对资源的访问
  • 每个进程和文件都有安全上下文，策略定义哪些上下文可访问哪些资源
  • 即使root权限也受SELinux策略限制

代码安全：

  • 代码混淆（ProGuard/R8）：混淆类名、方法名、字段名，增加反编译难度，同时压缩代码
  • DEX加固：第三方加固服务（如360加固、腾讯乐固），对DEX加密、加壳，防止反编译和篡改
  • Native代码保护：核心逻辑用C/C++实现，增加逆向难度
  • 防调试：检测调试器、模拟器，防止动态调试

网络安全：

  • HTTPS：加密传输，防止中间人攻击
  • 证书锁定（Certificate Pinning）：应用内置服务器证书，只信任指定证书，防止伪造证书
  • 网络安全配置（Network Security Config）：XML配置，可设置允许/禁止明文流量、信任的CA、证书锁定
  • Android 9.0+默认禁止明文HTTP流量

数据存储安全：

  • 内部存储：/data/data/<包名>/，仅应用自己可访问（MODE_PRIVATE）
  • 外部存储：/sdcard/，所有应用可访问，需存储权限，Android 10+引入分区存储（Scoped Storage）
  • SharedPreferences：私有存储，MODE_PRIVATE确保安全
  • 数据库：SQLite数据库私有存储，可加密（SQLCipher）
  • 密钥存储：AndroidKeyStore，硬件级密钥存储，密钥不可导出

第4篇 Android系统工具

第23章 IDE和Gradle

Android Studio：

  • Google官方IDE，基于IntelliJ IDEA
  • 集成Android SDK、Gradle、模拟器、布局编辑器、性能分析工具
  • 常用功能：代码编辑、智能补全、重构、调试、布局预览、APK分析、性能分析（Profiler）

Gradle构建工具：

  • 基于Groovy/Kotlin DSL的构建自动化工具
  • Android Gradle Plugin（AGP）封装Android构建流程
  • 核心概念：
    • Project：一个模块（app、library等）
    • Task：构建任务（assemble、install、test等）
    • Plugin：插件（com.android.application、com.android.library）
    • Dependency：依赖管理（implementation、api、compileOnly等）
  • 构建配置文件：
    • settings.gradle：项目模块配置
    • build.gradle（项目级）：全局配置、仓库、依赖版本
    • build.gradle（模块级）：模块构建配置（compileSdk、buildTypes、flavors、dependencies）
    • gradle.properties：Gradle全局属性
    • gradle-wrapper.properties：Gradle版本配置

常用Gradle命令：

  • ./gradlew assembleDebug：编译Debug包
  • ./gradlew assembleRelease：编译Release包
  • ./gradlew installDebug：编译并安装Debug包
  • ./gradlew clean：清理构建产物
  • ./gradlew build：编译所有构建变体
  • ./gradlew tasks：查看所有任务
  • ./gradlew dependencies：查看依赖树

依赖管理：

  • implementation：依赖仅当前模块可用，不传递给依赖当前模块的模块（推荐，减少编译时间）
  • api：依赖传递给依赖当前模块的模块（即旧的compile）
  • compileOnly：仅编译时需要，不打包到APK（如注解处理器）
  • runtimeOnly：仅运行时需要，不参与编译
  • testImplementation：仅测试代码可用
  • androidTestImplementation：仅Android测试代码可用

第24章 软件版本管理

Git版本控制：

  • 分布式版本控制系统，每个开发者本地有完整仓库
  • 核心概念：
    • 工作区（Working Directory）：当前编辑的文件
    • 暂存区（Staging Area/Index）：git add后的文件
    • 本地仓库（Local Repository）：git commit后的提交
    • 远程仓库（Remote Repository）：GitHub/GitLab等托管的仓库
  • 常用命令：
    • git init：初始化仓库
    • git clone：克隆远程仓库
    • git add：添加文件到暂存区
    • git commit：提交到本地仓库
    • git push：推送到远程仓库
    • git pull：拉取远程更新
    • git fetch：获取远程更新（不合并）
    • git merge：合并分支
    • git rebase：变基（将当前分支的提交移到目标分支之后）
    • git branch：管理分支
    • git checkout/git switch：切换分支
    • git log：查看提交历史
    • git status：查看工作区状态
    • git diff：查看差异
    • git stash：暂存当前修改
    • git reset：重置提交
    • git revert：撤销提交（生成新提交）

分支策略：

  • Git Flow：master（生产）、develop（开发）、feature（功能）、release（发布）、hotfix（修复）
  • GitHub Flow：master（生产）+ feature分支，简单流程
  • Trunk-Based Development：主干开发，短生命周期分支，频繁合并

代码审查（Code Review）：

  • Pull Request（PR）/ Merge Request（MR）
  • 团队成员审查代码，确保质量
  • 自动化检查：CI/CD（持续集成/持续交付）、Lint检查、单元测试

SVN（Subversion）：

  • 集中式版本控制系统，中央服务器存储所有版本
  • 与Git的区别：集中式vs分布式、分支是目录vs指针、性能差异
  • Android早期项目可能使用SVN，现主流使用Git

第25章 系统调试辅助工具

Logcat：

  • Android系统日志查看工具
  • 日志级别：Verbose（V）、Debug（D）、Info（I）、Warn（W）、Error（E）、Fatal（F）
  • 常用命令：
    • adb logcat：查看所有日志
    • adb logcat -s TAG：过滤指定标签
    • adb logcat *:E：只显示Error及以上
    • adb logcat -c：清空日志
    • adb logcat -d > log.txt：导出日志到文件
  • 日志格式：日期 时间 PID TID 级别 标签: 消息

ADB（Android Debug Bridge）：

  • Android调试桥，PC与设备通信的命令行工具
  • 常用命令：
    • adb devices：列出已连接设备
    • adb install xxx.apk：安装APK
    • adb uninstall <包名>：卸载应用
    • adb push <本地> <远程>：推送文件到设备
    • adb pull <远程> <本地>：从设备拉取文件
    • adb shell：进入设备shell
    • adb shell am start -n <包名>/<Activity>：启动Activity
    • adb shell am startservice：启动Service
    • adb shell am broadcast：发送广播
    • adb shell pm list packages：列出已安装应用
    • adb shell dumpsys <服务>：查看系统服务状态
    • adb shell top：查看进程CPU/内存占用
    • adb shell ps：查看进程列表
    • adb reboot：重启设备
    • adb root：以root身份重启adbd
    • adb remount：重新挂载/system为可写

dumpsys：

  • 查看Android系统服务状态的工具
  • 常用命令：
    • adb shell dumpsys activity：查看Activity管理器状态（Activity栈、Service、Broadcast等）
    • adb shell dumpsys window：查看窗口管理器状态
    • adb shell dumpsys meminfo <包名>：查看应用内存使用
    • adb shell dumpsys cpuinfo：查看CPU使用
    • adb shell dumpsys gfxinfo <包名>：查看图形渲染性能
    • adb shell dumpsys batterystats：查看电池使用统计
    • adb shell dumpsys notification：查看通知状态
    • adb shell dumpsys package <包名>：查看应用包信息

Android Studio Profiler：

  • Android Studio内置的性能分析工具
  • CPU Profiler：分析CPU使用、方法调用、线程状态
  • Memory Profiler：分析内存使用、对象分配、堆转储
  • Network Profiler：分析网络请求
  • Energy Profiler：分析能耗

Systrace：

  • 系统级性能分析工具，查看短时间内系统各部分的活动
  • 结合内核、系统服务、应用的事件，分析性能瓶颈
  • 可通过Android Studio的CPU Profiler或命令行systrace.py使用
  • 适合分析卡顿、启动慢、渲染延迟等问题

Hierarchy Viewer / Layout Inspector：

  • 分析View树层级和布局性能
  • Layout Inspector是Android Studio提供的现代工具，替代Hierarchy Viewer
  • 可实时查看应用的View树、布局属性、绘制时间

GPU过度绘制调试：

  • 开发者选项中开启”调试GPU过度绘制”
  • 屏幕颜色表示过度绘制次数：
    • 原色：无过度绘制
    • 蓝色：1次（可接受）
    • 绿色：2次
    • 淡红：3次
    • 深红：4次及以上（需优化）

GPU呈现模式分析：

  • 开发者选项中开启”GPU呈现模式分析”
  • 屏幕上显示柱状图，每根柱子表示一帧的渲染时间
  • 绿色线表示16.67ms（60fps基准）
  • 柱子超过绿线表示掉帧

ANR日志分析：

  • ANR发生后，系统在/data/anr/traces.txt保存堆栈信息
  • 通过adb pull /data/anr/traces.txt导出
  • 分析主线程堆栈，找到阻塞点
  • 关键信息：进程名、主线程状态、各线程堆栈、CPU使用率

Bugreport：

  • adb bugreport导出完整的系统状态报告
  • 包含日志、系统服务状态、进程信息、内存信息、电池信息等
  • 用于全面分析设备状态和问题

读书笔记总结

《深入理解Android内核设计思想》是一部Android系统原理的鸿篇巨著，全书2156页（上下册），从编译系统、系统原理、应用原理到系统工具，全方位深入Android内核设计。

全书知识脉络：

第1篇 编译篇（第1-3章）：

  • Android系统架构与设计思想
  • 源码下载与编译环境搭建
  • 编译系统演进（Make → Soong/Android.bp/Ninja）

第2篇 原理篇（第4-13章）：

  • 操作系统基础（进程/线程/内存/文件系统）
  • Android进程/线程模型与内存优化
  • Binder IPC机制（核心）
  • Android完整启动流程（init → Zygote → SystemServer → Launcher）
  • AMS（四大组件与进程管理）
  • SurfaceFlinger（图形合成）
  • WMS（窗口管理）
  • View体系（测量/布局/绘制/事件分发）
  • InputManagerService（输入事件）
  • 音频系统（AudioFlinger/AudioPolicyService）

第3篇 应用原理篇（第14-22章）：

  • Intent匹配规则
  • 资源适配机制
  • 字符编码（UTF-8/UTF-16/MUTF-8）
  • OpenGL ES图形渲染
  • SystemUI系统界面
  • App Widget机制
  • APK编译打包流程
  • Dalvik/ART虚拟机
  • 安全机制（沙箱/权限/签名/SELinux）

第4篇 系统工具篇（第23-25章）：

  • Android Studio与Gradle构建
  • Git/SVN版本管理
  • 调试工具（Logcat/ADB/dumpsys/Profiler/Systrace）

学习建议：

  • 本书内容极为丰富，建议按篇分阶段学习，不必一次读完
  • 第2篇是核心，建议结合AOSP源码深入学习
  • Binder（第6章）、启动流程（第7章）、AMS（第8章）、View体系（第11章）是面试高频考点
  • 第3篇的虚拟机（第21章）和安全机制（第22章）是进阶必备知识
  • 第4篇的工具是日常开发和调试的实用技能
  • 学习时建议动手实践：编译AOSP、阅读源码、使用调试工具分析问题

这本书适合希望深入理解Android系统原理、从应用开发向系统开发进阶的开发者阅读，是Android领域最全面的系统原理书籍之一。
