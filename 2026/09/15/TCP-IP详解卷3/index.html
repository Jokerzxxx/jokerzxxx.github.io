TCP/IP详解 卷3：TCP事务协议、HTTP、NNTP和UNIX域协议

TCP/IP详解 卷3：TCP事务协议、HTTP、NNTP和UNIX域协议

作者：W. Richard Stevens（W·理查德·史蒂文斯）
全书共271页，TCP/IP详解系列的第三卷，深入讲解T/TCP（TCP事务协议）的协议设计与实现，以及HTTP、NNTP和UNIX域协议三个应用层/特殊协议的细节，是理解TCP扩展和经典应用层协议的重要参考。

第一部分：TCP事务协议（T/TCP）

第1章 T/TCP概述

事务协议的需求

传统TCP的问题：

  • TCP面向连接，需要三次握手建立连接
  • 每次事务（请求-响应）都需要建立和关闭连接
  • 最小事务需要9个报文段（SYN、SYN+ACK、ACK、请求、ACK+响应、ACK、FIN、ACK、FIN）
  • 对于短事务（如DNS查询、RPC），连接建立开销占比大
  • UDP无连接但不可靠

事务协议的目标：

  • 结合TCP的可靠性和UDP的高效
  • 最小化事务的报文段数量
  • 最小化事务延迟
  • 保持TCP的可靠性（确认、重传、排序）
  • 向后兼容普通TCP

T/TCP（TCP for Transactions）：

  • Bob Braden设计的TCP扩展
  • RFC 1644定义
  • 允许在一个报文段中同时携带SYN和数据
  • 利用TAO（TCP Acceleration Option，CC选项）跳过三次握手
  • 最小事务只需3个报文段（请求+SYN、响应+SYN+ACK、ACK）
  • 甚至可以2个报文段（请求+SYN、响应+SYN+ACK+FIN）

UDP上的客户-服务器

UDP事务示例：

  • 客户端发送请求数据报
  • 服务器处理并发送响应数据报
  • 2个报文段完成事务
  • 但不可靠：请求或响应可能丢失
  • 应用层需要自己处理超时重传
  • 无流量控制、拥塞控制

TCP上的客户-服务器

传统TCP事务示例：

  1. 客户端：SYN
  2. 服务器：SYN+ACK
  3. 客户端：ACK（连接建立）
  4. 客户端：请求数据
  5. 服务器：ACK+响应数据
  6. 客户端：ACK
  7. 客户端：FIN（关闭）
  8. 服务器：ACK
  9. 服务器：FIN
  10. 客户端：ACK
  • 至少9-10个报文段
  • 至少3个RTT延迟（握手+请求响应+关闭）
  • 对于短事务效率极低

T/TCP上的客户-服务器

T/TCP事务示例（最小情况）：

  1. 客户端：SYN + 数据（请求） + CC选项
  2. 服务器：SYN + ACK + 数据（响应） + FIN + CC选项
  3. 客户端：ACK
  • 3个报文段完成事务
  • 1.5个RTT延迟
  • 如果客户端不需要后续数据，第3个ACK可以省略（2个报文段）

TAO（TCP Acceleration Option）：

  • CC选项：连接计数（Connection Count），单调递增的32位计数器
  • CCnew选项：首次使用的CC
  • CCECHO选项：回显对方的CC
  • 服务器缓存客户端的CC值（按IP地址）
  • 如果收到的CC大于缓存值，说明是新连接，跳过三次握手（TAO测试通过）
  • 如果CC小于等于缓存值，可能是旧的重复报文，执行正常三次握手

T/TCP的应用场景

适合T/TCP的应用：

  • 短事务：请求-响应模式，数据量小
  • DNS查询（虽然DNS通常用UDP）
  • RPC（远程过程调用）
  • HTTP/1.0请求（每个请求一个连接）
  • 数据库查询
  • 任何需要可靠性但事务短的应用

不适合T/TCP的应用：

  • 长连接、大数据传输（普通TCP更好）
  • 批量数据传输
  • 流媒体（UDP更合适）

T/TCP的现状：

  • T/TCP在实际中部署有限
  • 实现复杂，安全问题（CC伪造、SYN洪水）
  • HTTP/1.1的持久连接和管道化减少了对T/TCP的需求
  • 现代替代：TCP Fast Open（TFO，RFC 7413），类似思想但更安全
  • QUIC协议（基于UDP）提供0-RTT连接建立

第2章 T/TCP协议

T/TCP中的新TCP选项

CC选项（Connection Count）：

  • 种类：11（CC）、12（CCnew）、13（CCECHO）
  • 长度：6字节（种类1+长度1+值4）
  • CC值：32位单调递增计数器，每个主机维护
  • 每个SYN段携带CC选项
  • 服务器缓存每个客户端IP的最新CC值

CCnew选项：

  • 客户端首次连接某服务器时使用（没有缓存的CC）
  • 服务器收到CCnew后，执行正常三次握手（不跳过）
  • 服务器在SYN+ACK中回显CCECHO
  • 后续连接使用普通CC选项

CCECHO选项：

  • 服务器在SYN+ACK中回显客户端的CC值
  • 客户端验证回显的CC值
  • 防止CC伪造

T/TCP实现所需变量

每个主机的变量：

  • cc_global：全局CC计数器，单调递增
  • 每次发送SYN时递增
  • 32位，回绕处理

每个路由条目的变量：

  • 路由表中为每个目标主机缓存CC值
  • rtcache：路由缓存中的CC值
  • 用于TAO测试

每个TCPCB的变量：

  • cc_send：发送的CC值
  • cc_recv：接收的CC值
  • 标志位：是否使用T/TCP、TAO测试是否通过

状态变迁图

T/TCP的扩展状态：

  • 在传统TCP状态基础上扩展
  • 新增状态或标志：
    • T/TCP连接标志
    • TAO测试通过标志
    • 半同步状态

客户端状态变迁：

  • CLOSED → SYN_SENT（发送SYN+数据+CC）
  • 如果TAO通过（服务器响应SYN+ACK+数据）：
    • SYN_SENT → ESTABLISHED（收到SYN+ACK）
    • 同时接收数据
  • 如果TAO不通过：
    • 执行正常三次握手
  • 发送FIN后进入FIN_WAIT_1

服务器状态变迁：

  • LISTEN → 收到SYN+CC
    • TAO测试通过：
      • 直接发送SYN+ACK+数据（不进入SYN_RCVD）
      • 进入ESTABLISHED
    • TAO测试不通过：
      • 进入SYN_RCVD
      • 发送SYN+ACK+CCECHO
      • 等待ACK后进入ESTABLISHED

T/TCP的扩展状态

T/TCP与普通TCP的兼容：

  • T/TCP可以与普通TCP互操作
  • 如果对方不支持T/TCP（没有CC选项），退化为普通TCP
  • 三次握手正常进行
  • 向后兼容是T/TCP设计的重要目标

T/TCP的安全性考虑：

  • CC值可能被伪造
  • 攻击者可以发送伪造的高CC值，使服务器跳过握手
  • 可能导致连接注入攻击
  • T/TCP的安全问题是其未广泛部署的原因之一
  • TCP Fast Open（TFO）使用Cookie机制提高安全性

第3章 T/TCP使用举例

客户重新启动

客户端重启场景：

  • 客户端崩溃后重启，cc_global重置
  • 新连接的CC值可能小于服务器缓存的值
  • 服务器TAO测试失败（CC不大于缓存值）
  • 执行正常三次握手
  • 服务器更新缓存的CC值
  • 后续连接恢复T/TCP加速

常规的T/TCP事务

正常事务流程：

  1. 客户端发送SYN+请求数据+CC
  2. 服务器TAO测试通过（CC大于缓存值）
  3. 服务器发送SYN+ACK+响应数据+FIN+CC
  4. 客户端发送ACK（确认响应和FIN）
  5. 事务完成，3个报文段
  • 服务器进入TIME_WAIT（主动关闭）
  • 客户端进入CLOSED

服务器收到过时的重复SYN

重复SYN场景：

  • 网络中存在旧的重复SYN报文
  • 旧SYN的CC值小于服务器缓存值
  • TAO测试失败
  • 服务器不跳过握手，发送RST或正常SYN+ACK
  • 防止旧报文建立错误连接

服务器重启动

服务器重启场景：

  • 服务器崩溃重启，丢失CC缓存
  • 收到客户端SYN+CC
  • 没有缓存的CC值，TAO测试无法进行
  • 执行正常三次握手（使用CCnew/CCECHO）
  • 建立CC缓存
  • 后续连接恢复T/TCP加速

请求或应答超出MSS

大数据事务：

  • 请求或响应超过一个MSS
  • 需要多个报文段传输
  • T/TCP仍然可以跳过握手
  • 第一个报文段携带SYN+数据
  • 后续报文段正常传输
  • 大数据事务的握手开销占比小，T/TCP优势不明显

向后兼容性

与普通TCP互操作：

  • T/TCP客户端连接普通TCP服务器：
    • 发送SYN+CC
    • 服务器不识别CC选项，忽略
    • 正常三次握手
    • 退化为普通TCP
  • 普通TCP客户端连接T/TCP服务器：
    • 发送SYN（无CC选项）
    • 服务器不执行TAO测试
    • 正常三次握手
  • 完全向后兼容

第4章 T/TCP协议（续）

客户的端口号和TIME_WAIT状态

TIME_WAIT的问题：

  • 传统TCP中，主动关闭的一方进入TIME_WAIT（2MSL）
  • T/TCP中，服务器通常主动关闭（发送FIN）
  • 服务器进入TIME_WAIT
  • 大量短事务导致服务器大量TIME_WAIT状态
  • 消耗服务器资源

T/TCP对TIME_WAIT的优化：

  • T/TCP可以截断TIME_WAIT状态
  • 利用CC选项验证连接唯一性
  • 如果收到的CC值大于缓存值，可以安全重用TIME_WAIT状态的连接
  • 减少TIME_WAIT状态的资源消耗
  • 提高服务器处理短事务的能力

设置TIME_WAIT状态的目的

TIME_WAIT的两个作用：

  1. 可靠终止TCP全双工连接
    • 最后一个ACK可能丢失
    • TIME_WAIT期间可以重传ACK
  2. 让旧的重复分节在网络中消逝
    • 防止旧连接的报文被新连接（相同四元组）错误接收

T/TCP中TIME_WAIT的变化：

  • T/TCP通过CC选项提供了另一种验证连接唯一性的机制
  • 可以在一定条件下安全地缩短或跳过TIME_WAIT
  • 但需要谨慎处理，确保不破坏TCP的可靠性

TIME_WAIT状态的截断

截断TIME_WAIT的条件：

  • 收到新的SYN，CC值大于当前缓存的CC值
  • 新SYN的序号在合理范围内
  • 可以直接从TIME_WAIT进入SYN_RCVD或ESTABLISHED
  • 不需要等待2MSL
  • 提高连接重用效率

截断TIME_WAIT的风险：

  • 如果旧连接的报文仍在网络中，可能被新连接接收
  • CC值提供一定保护，但不是绝对安全
  • 需要权衡性能和安全性

利用TAO跳过三次握手

TAO测试的详细过程：

  1. 服务器收到SYN+CC
  2. 查找客户端IP的路由缓存，获取缓存的CC值
  3. 比较收到的CC与缓存的CC：
    • 收到CC > 缓存CC：TAO测试通过，跳过握手
    • 收到CC ≤ 缓存CC：TAO测试失败，正常握手
  4. TAO通过时：
    • 直接发送SYN+ACK（可携带数据和FIN）
    • 更新缓存的CC值
    • 进入ESTABLISHED状态
  5. TAO失败时：
    • 发送SYN+ACK+CCECHO
    • 进入SYN_RCVD
    • 等待ACK

TAO的优势：

  • 减少一个RTT的握手延迟
  • 减少报文段数量
  • 对短事务性能提升显著

第5-10章 T/TCP实现

插口层修改

sosend函数：

  • 发送数据时，如果连接未建立且支持T/TCP
  • 可以在SYN中携带数据
  • 修改插口层的发送逻辑
  • 支持在连接建立前发送数据

connect函数：

  • T/TCP的connect可以立即返回（不等待握手完成）
  • 数据可以随SYN一起发送
  • 非阻塞connect的行为变化

路由表修改

路由缓存扩展：

  • 路由表条目增加CC缓存字段
  • 为每个目标IP缓存最新的CC值
  • TAO测试时查询路由缓存
  • 路由缓存的过期和更新

rtentry结构扩展：

  • 增加CC相关字段
  • rtcache_cc：缓存的CC值
  • 路由表操作函数修改

协议控制块修改

inpcb扩展：

  • 增加T/TCP相关标志
  • 本地CC值、对端CC值
  • TAO测试结果

tcpcb扩展：

  • cc_send：发送的CC值
  • cc_recv：接收的CC值
  • 标志位：TF_T/TCP（使用T/TCP）、TF_TAO（TAO通过）
  • 状态机扩展

TCP输出修改

tcp_output函数：

  • SYN段可以携带数据
  • SYN段添加CC选项
  • 支持在SYN+ACK中携带数据和FIN
  • 状态判断逻辑修改

TCP选项处理：

  • 发送时添加CC/CCnew/CCECHO选项
  • 接收时解析CC选项
  • 选项长度计算

TCP函数修改

tcp_input函数：

  • 处理T/TCP的SYN+数据
  • TAO测试逻辑
  • 状态机扩展
  • 从TIME_WAIT直接建立新连接

tcp_usrreq函数：

  • 用户请求处理
  • connect、send、close的T/TCP特殊处理
  • 状态转换

第二部分：HTTP、NNTP和UNIX域协议

第11章 HTTP：超文本传输协议

HTTP概述

HTTP的历史：

  • HTTP/0.9（1991）：简单的GET请求，只有HTML
  • HTTP/1.0（1996，RFC 1945）：增加请求头、响应头、状态码、POST方法
  • HTTP/1.1（1999，RFC 2616，更新RFC 7230-7235）：持久连接、管道化、分块传输、缓存控制、内容协商
  • HTTP/2（2015，RFC 7540）：二进制帧、多路复用、头部压缩、服务器推送
  • HTTP/3（2022，RFC 9114）：基于QUIC，0-RTT、连接迁移、改进的拥塞控制

HTTP的特点：

  • 应用层协议，基于TCP（HTTP/1-2）或QUIC（HTTP/3）
  • 请求-响应模式
  • 无状态（服务器不保存客户端状态）
  • 可扩展（头部、方法、状态码可扩展）
  • 媒体无关（可传输任何类型数据）

HTTP请求

请求报文格式：

请求行：

  • 方法（Method）：GET、POST、PUT、DELETE、HEAD、OPTIONS、PATCH、TRACE、CONNECT
  • 请求URI（Request-URI）：资源路径
  • HTTP版本：HTTP/1.0、HTTP/1.1

常用HTTP方法：

  • GET：获取资源
  • POST：提交数据（创建资源）
  • PUT：替换资源（完整更新）
  • DELETE：删除资源
  • HEAD：获取资源头部（无响应体）
  • OPTIONS：获取支持的方法/选项
  • PATCH：部分更新资源
  • TRACE：回显请求（测试）
  • CONNECT：建立隧道（HTTPS代理）

常用请求头：

  • Host：目标主机（HTTP/1.1必需）
  • User-Agent：客户端标识
  • Accept：可接受的媒体类型
  • Accept-Language：可接受的语言
  • Accept-Encoding：可接受的编码（压缩）
  • Content-Type：请求体类型
  • Content-Length：请求体长度
  • Authorization：认证凭证
  • Cookie：客户端Cookie
  • Referer：来源页面
  • Connection：连接管理（keep-alive/close）
  • Cache-Control：缓存控制
  • If-Modified-Since/If-None-Match：条件请求

HTTP响应

响应报文格式：

状态行：

  • HTTP版本
  • 状态码（3位数字）
  • 原因短语（状态码的文本描述）

常见状态码：

  • 1xx：信息
    • 100 Continue：继续
    • 101 Switching Protocols：切换协议
  • 2xx：成功
    • 200 OK：成功
    • 201 Created：已创建
    • 204 No Content：无内容
    • 206 Partial Content：部分内容
  • 3xx：重定向
    • 301 Moved Permanently：永久重定向
    • 302 Found：临时重定向
    • 303 See Other：查看其他
    • 304 Not Modified：未修改
    • 307 Temporary Redirect：临时重定向
    • 308 Permanent Redirect：永久重定向
  • 4xx：客户端错误
    • 400 Bad Request：错误请求
    • 401 Unauthorized：未授权
    • 403 Forbidden：禁止访问
    • 404 Not Found：未找到
    • 405 Method Not Allowed：方法不允许
    • 408 Request Timeout：请求超时
    • 409 Conflict：冲突
    • 413 Payload Too Large：负载过大
    • 414 URI Too Long：URI过长
    • 415 Unsupported Media Type：不支持的媒体类型
    • 429 Too Many Requests：请求过多
  • 5xx：服务器错误
    • 500 Internal Server Error：内部服务器错误
    • 501 Not Implemented：未实现
    • 502 Bad Gateway：错误网关
    • 503 Service Unavailable：服务不可用
    • 504 Gateway Timeout：网关超时
    • 505 HTTP Version Not Supported：HTTP版本不支持

常用响应头：

  • Date：响应时间
  • Server：服务器标识
  • Content-Type：响应体类型
  • Content-Length：响应体长度
  • Content-Encoding：内容编码（gzip等）
  • Content-Language：内容语言
  • Last-Modified：最后修改时间
  • ETag：实体标签
  • Location：重定向目标
  • Set-Cookie：设置Cookie
  • Cache-Control：缓存控制
  • Expires：过期时间
  • Connection：连接管理
  • Transfer-Encoding：传输编码（chunked）
  • Access-Control-Allow-Origin：CORS

HTTP连接管理

非持久连接（HTTP/1.0默认）：

  • 每个请求/响应对使用一个TCP连接
  • 请求完成后关闭连接
  • N个资源需要N次TCP连接
  • 开销大（每次握手、慢启动）

持久连接（HTTP/1.1默认）：

  • 一个TCP连接可以传输多个请求/响应
  • Connection: keep-alive
  • 减少连接建立开销
  • 减少慢启动影响
  • 服务器或客户端可以随时关闭连接

管道化（Pipelining）：

  • 在等待前一个响应的同时发送下一个请求
  • 多个请求排队，服务器按顺序响应
  • 减少等待时间
  • 限制：响应必须按请求顺序返回（队头阻塞）
  • 只有幂等请求（GET、HEAD）可以管道化
  • HTTP/1.1支持但浏览器默认禁用（实现问题）

队头阻塞（Head-of-Line Blocking）：

  • HTTP/1.x中，一个连接上的请求必须按顺序响应
  • 如果第一个请求很慢，后续请求都要等待
  • 管道化不能根本解决队头阻塞
  • HTTP/2通过多路复用解决

HTTP/2和HTTP/3

HTTP/2的改进：

  • 二进制帧协议（而非文本）
  • 多路复用：一个连接上多个流并行传输，解决队头阻塞
  • 头部压缩（HPACK）：减少头部开销
  • 服务器推送：服务器主动推送客户端可能需要的资源
  • 流优先级：客户端指定资源优先级
  • 基于TCP，仍有TCP层的队头阻塞（一个丢包影响所有流）

HTTP/3的改进：

  • 基于QUIC（UDP上的可靠传输协议）
  • 0-RTT连接建立（类似T/TCP思想）
  • 连接迁移：网络切换时保持连接
  • 流级别的流量控制和拥塞控制，无TCP队头阻塞
  • 内置TLS 1.3加密
  • 更快的连接建立和更好的丢包恢复

第12章 NNTP：网络新闻传输协议

NNTP概述

NNTP的作用：

  • Network News Transfer Protocol（网络新闻传输协议）
  • RFC 977定义，更新RFC 3977
  • 用于Usenet新闻组的文章分发和读取
  • 基于TCP，端口119
  • 类似SMTP的命令-响应模式

Usenet新闻组：

  • 分布式讨论系统
  • 新闻组（Newsgroup）：按主题分类的讨论区
  • 文章（Article）：类似邮件，有头部和正文
  • 文章在新闻服务器之间传播（洪水填充）
  • 已被Web论坛、社交媒体取代，但仍有部分用户

NNTP命令

常用NNTP命令：

  • ARTICLE：获取文章全文（头部+正文）
  • HEAD：获取文章头部
  • BODY：获取文章正文
  • STAT：获取文章状态
  • GROUP：选择新闻组
  • LIST：列出所有新闻组
  • NEWGROUPS：列出新增新闻组
  • NEWNEWS：列出新增文章
  • NEXT：转到下一篇文章
  • LAST：转到上一篇文章
  • POST：发布文章
  • IHAVE：服务器间文章传播
  • QUIT：断开连接
  • HELP：获取帮助
  • MODE READER/MODE STREAM：切换模式

NNTP响应码：

  • 1xx：信息
  • 2xx：成功
  • 3xx：需要进一步操作
  • 4xx：命令正确但执行失败
  • 5xx：命令错误或未实现
  • 类似FTP/SMTP的响应码模式

NNTP文章格式

文章格式：

  • 类似邮件（RFC 822/5322格式）
  • 头部字段：
    • From：作者
    • Subject：主题
    • Date：日期
    • Newsgroups：所属新闻组
    • Message-ID：唯一标识
    • References：引用的文章（线程）
    • Path：传播路径
    • Xref：交叉引用
  • 正文：文本内容
  • 文章通过Message-ID唯一标识

文章传播：

  • 服务器之间使用IHAVE/SENDME命令传播文章
  • 洪水填充算法：每个服务器将新文章转发给邻居
  • 文章有过期时间，到期删除
  • 分布式系统，无中心服务器

第13章 UNIX域协议

UNIX域协议概述

UNIX域套接字（Unix Domain Socket）：

  • 用于同一主机上进程间通信（IPC）
  • 使用套接字API，但不经过网络协议栈
  • 地址是文件系统路径（如/tmp/mysocket）
  • 比TCP/IP回环更快（不经过网络层、不计算校验和、不分片）
  • 支持SOCK_STREAM（类似TCP）和SOCK_DGRAM（类似UDP）
  • 可靠、有序（SOCK_STREAM）

UNIX域协议的特点：

  • 仅本机通信，不能跨网络
  • 使用文件系统路径作为地址
  • 支持文件描述符传递（特殊能力）
  • 支持凭据传递（用户ID、组ID）
  • 比TCP回环性能高约2倍
  • 常用于本地服务（如MySQL的socket连接、X Window、Docker）

UNIX域套接字编程

地址结构：

服务器流程：

  1. socket(AF_UNIX, SOCK_STREAM, 0)
  2. bind：绑定到文件路径
  3. listen：监听
  4. accept：接受连接
  5. read/write：通信
  6. close：关闭

客户端流程：

  1. socket(AF_UNIX, SOCK_STREAM, 0)
  2. connect：连接到服务器路径
  3. read/write：通信
  4. close：关闭

文件系统权限：

  • 套接字文件有文件权限
  • 客户端需要对套接字文件有写权限才能连接
  • 可以通过文件权限控制访问

文件描述符传递

传递文件描述符：

  • UNIX域套接字的特殊能力
  • 可以在进程间传递打开的文件描述符
  • 使用sendmsg/recvmsg和辅助数据（ancillary data）
  • 传递的不是文件描述符数字，而是内核文件表项的引用
  • 接收方获得一个新的文件描述符，指向同一个内核文件表项

使用场景：

  • 特权进程打开文件，将描述符传给非特权进程
  • 进程池：主进程接受连接，将连接描述符传给工作进程
  • 避免重新打开文件或重新建立连接
  • 是Unix编程的高级技巧

实现细节：

  • 使用struct cmsghdr辅助数据
  • SCM_RIGHTS类型
  • sendmsg发送，recvmsg接收
  • 内核在发送时复制文件表项引用，接收时分配新描述符

UNIX域协议与TCP回环的比较

性能对比：

  • UNIX域套接字：
    • 不经过IP层、TCP层
    • 不计算校验和
    • 不分片
    • 不使用拥塞控制、流量控制（简化）
    • 延迟低、吞吐量高
  • TCP回环（127.0.0.1）：
    • 经过完整TCP/IP协议栈
    • 计算校验和
    • 拥塞控制、流量控制
    • 延迟较高、吞吐量较低
  • UNIX域通常比TCP回环快1.5-2倍

功能对比：

  • UNIX域：仅本机、文件描述符传递、凭据传递
  • TCP回环：可跨网络（改地址即可）、标准网络API、可抓包调试
  • 选择：仅本机通信用UNIX域，可能跨网络用TCP

读书笔记总结

《TCP/IP详解 卷3》是TCP/IP详解系列的第三卷，由W. Richard Stevens编写，深入讲解T/TCP（TCP事务协议）的协议设计与实现，以及HTTP、NNTP和UNIX域协议三个应用层/特殊协议的细节。

全书知识脉络：

部分 章节 主题 核心内容
第一部分 第1章 T/TCP概述 事务协议需求、UDP/TCP/T/TCP对比、TAO加速、应用场景
第2章 T/TCP协议 CC/CCnew/CCECHO选项、状态变迁、扩展状态、安全性
第3章 T/TCP使用举例 常规事务、客户端/服务器重启、重复SYN、MSS超限、向后兼容
第4章 T/TCP协议（续） TIME_WAIT截断、TAO跳过握手的详细过程
第5-10章 T/TCP实现 插口层、路由表、协议控制块、TCP输入输出的修改
第二部分 第11章 HTTP 请求/响应格式、方法、状态码、头部、持久连接、管道化、HTTP/2/3
第12章 NNTP 新闻组、命令、响应码、文章格式、文章传播
第13章 UNIX域协议 本地IPC、文件路径地址、文件描述符传递、性能对比

学习建议：

  • T/TCP部分虽然协议本身未广泛部署，但其思想（跳过握手、0-RTT）在现代协议（TCP Fast Open、QUIC、HTTP/3）中得到延续和发展，理解T/TCP有助于理解现代协议设计
  • HTTP部分是Web开发的基础，必须掌握请求/响应格式、方法、状态码、头部、连接管理
  • HTTP/2和HTTP/3是现代Web性能优化的关键，理解多路复用、头部压缩、QUIC等特性
  • NNTP已较少使用，但了解其命令-响应模式和文章格式有助于理解其他应用层协议（SMTP、FTP）
  • UNIX域协议是Unix/Linux系统编程的重要IPC机制，理解文件描述符传递是高级Unix编程的关键
  • 本书基于较老的协议版本（HTTP/1.1、NNTP v1），学习时应结合最新RFC了解协议演进
  • 配合卷1（协议原理）和卷2（内核实现）学习，形成完整的TCP/IP知识体系
  • T/TCP的实现部分（第5-10章）较深入，适合内核开发者和协议研究者，普通读者可略读

这本书是TCP/IP详解系列的收尾之作，虽然T/TCP未成为主流，但其中的协议设计思想和三个应用层协议的细节仍然具有重要的学习价值，是理解现代网络协议演进的重要参考。
